# Agent × CoDelphi 咨询指南

本仓库已配置名为 `codelphi` 的 MCP 服务，提供软件的用户行为、行为关系及对应代码证据。**任务涉及既有产品行为、行为关系或其代码证据时，必须在形成设计结论、制定实施方案或修改文件前，实际调用 MCP 的 `ask_behavior` 工具（Kimi Code 中为 `mcp__codelphi__ask_behavior`），使用对应项目的 `slug` 和具体问题参数。** 新功能只要依赖、扩展或改变既有行为，也属于必问范围。必要时先调用 `list_projects` 确认 slug；计划修改文件时还需调用 `lookup_by_files` 反查影响面。纯机械修改且不涉及既有行为语义的改动可以不咨询。

**没有产生 `ask_behavior` 的真实工具调用记录，就不算完成咨询。** 不得把阅读源码、自行推断或询问其他模型当作“已咨询 CoDelphi”。若当前仅提供 `authenticate` 或连接失败，应先处理认证/连接问题，不得伪造咨询结果。

CoDelphi 提供证据与边界，不替你读代码，不替用户或产品负责人做产品决策，也不保证覆盖整个软件。你可以要求它说明证据、未覆盖范围、快照和未知项。它提供的信息可能不完整或过期，你需要独立判断。

## 使用回答

按以下顺序检查每次回答：

1. **直接结论**：它是否回答了当前问题，还是只提供了相关材料？
2. **适用范围**：结论属于哪个源码快照、状态、身份、权限和路径？
3. **证据**：是否能独立复核，而不是只引用摘要？
4. **未知项**：覆盖不足、意图未知、过期、外部验证或产品待裁决分别是什么？
5. **决策影响**：它改变了哪个假设、默认、范围、架构或验证？
6. **下一步**：选择 `verify`、`escalate`、`may_proceed` 或 `none`，并记录原因。

后续动作的含义：

- `verify`：可通过源码、测试、官方文档或真实响应验证的技术事实。
- `escalate`：影响用户可见行为、数据权益、安全、权限或核心产品语义，需要授权。
- `may_proceed`：低风险、可逆的工程选择，可以记录临时假设继续。
- `none`：没有额外行动。

不要把“为了安全起见”当作 `escalate` 的答案，也不要把“可逆”当作跳过验证的理由。普通机械修改或不涉及既有产品行为语义的改动不必咨询；源码能够直接回答问题不构成跳过必问场景的理由。

### 回答不完整或快照过旧时

- 将已直接回答的分支与未回答的分支分开列出。只确认部分行为时，不得写成“CoDelphi 已确认完整行为”，也不得把未覆盖或没搜到解释为“没有该行为”。
- 回答基于旧快照时，只能把结论视为该快照的行为说明；对照当前源码和测试验证，快照差异及无法确认的分支写入 `unknowns`。
- 结果被截断或只返回相关材料时，按未决分支缩小范围继续追问，要求直接回答缺失分支；不能用确定语气自行补齐回答。
- 无法继续追问或 MCP 不可用时，如实记录覆盖限制，以当前源码、测试、官方文档或真实响应完成验证，并据此选择 `verify`；涉及产品语义或数据权益的未决项选择 `escalate`。

## 记录有效问答

每次有效问答后，将原始问题、实际回答、证据、unknown 和决策影响写入 JSON：

```json
{
  "project": "project-slug",
  "repository": "owner/repo",
  "branch": "feature/example",
  "sha": "0584769",
  "task": "实现功能级订阅邮件",
  "question": "email_enabled=0 但订阅了功能 A 的用户是否会进入当前投递路径？",
  "answer": "不会。当前收件查询要求 email_enabled=1；没有功能订阅场景，watch-only 是否构成 opt-in 是产品决策。",
  "evidence": ["lib/notifications.ts:213-229"],
  "unknowns": ["订阅是否本身构成邮件 opt-in", "空订阅语义", "零命中是否留审计记录"],
  "decisionImpact": "不能把订阅实现为全量邮件偏好之上的过滤器，需先裁决 watch-only 与空集语义",
  "nextAction": "escalate"
}
```

然后执行：

```bash
npx tsx "$CODELPHI_HOME/scripts/log-agent-consultation.ts" --file /tmp/<project>-consultation.json
```

如果回答来自协调者而不是自动 MCP，要保留其实际表述和覆盖限制，不要事后改写成更理想的答案。

## 记录边界

- 不记录 token、`.env`、用户隐私或完整敏感代码。
- 不记录无决策影响的机械修改或重复问题。
- 不把 unknown/product decision 写成默认答案。
- 不把“没搜到”写成“没有该行为”。
- 不把历史实现自动提升为新功能规则。
- 不伪造账本覆盖、stableKey 或产品意图。
- 不用 CoDelphi 回答替代源码阅读、测试或外部官方文档。
- 不要求所有问题都阻塞开发；可逆工程选择应明确假设并继续。

## 阶段评审

定期回看 `<project>.md` 与 `<project>.jsonl`：

- Agent 是否在正确的时机问了正确类型的问题。
- 回答是否改变计划、实现或验证。
- 是否仍存在静默默认、过度阻塞、盲信 CoDelphi 或形式化修订。
- 哪些问题反复出现，说明 CoDelphi 的知识模型需要补充。
- 咨询与裁决成本是否低于避免的返工。

如果大多数问题都能由普通代码搜索直接回答，或回答没有改变决策，应提高问题的针对性并检查咨询是否真正影响设计，不要以此跳过上述必问场景；纯机械修改仍无需咨询。
