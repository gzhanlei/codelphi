# 产品空间可理解性与信噪比整改设计

日期：2026-11-12
状态：已实施（2026-11-12，未部署；commits caf95b8..b97280a）。§10.2 规格质量复核已按用户拍板执行完毕（生产 DB：归档「定向 Gold 评估」+ 8 条摘要修订置 source='manual'，生产 spec.json 验证 24 功能、零逐字重复摘要）。
输入：ChatGPT 与 WorkBuddy 对 RepoMap 公开页面的评审、代码与线上页面核对、`docs/demo-four-roles-walkthrough.md`、`docs/product-capability-maturity-roadmap.md`

## 1. 背景与问题

RepoMap 产品空间已经具备功能规格、场景、源码证据、行为 diff、回归任务、发布稿和知识健康等资产，但首次访问者需要自行理解信息架构，才能找到这些资产回答的实际问题。当前主要问题不是视觉风格，而是：

1. 被分析产品与 CoDelphi 的关系不够直接，页面价值需要访客自行推导。
2. 用户影响、前后差异和回归清单已经存在，但概览优先展示时间线、工程术语和能力卡。
3. 连续零行为变化发布、近似功能和重复摘要降低信噪比。
4. 覆盖率同时展示字节比例与文件数量，却未解释两种口径。
5. 只读状态下的写操作仍占据主按钮位置，操作预期不一致。
6. 移动端标签逐字换行，部分元数据字号和对比度不足。

整改必须同时保护现有产品边界：证据可溯不等于结论正确，共享证据面不等于调用依赖，回归推荐不等于完整测试覆盖，维护记录不等于团队掌握知识。

## 2. 已确认的产品决策

### 2.1 采用通用产品能力，不做 Demo 专用功能

用户已明确裁决：**不为 Demo 专门做功能，权限限制除外。**

因此，本设计中的上下文说明、用户影响摘要、任务入口、零变化折叠、覆盖率解释、规格质量治理和移动端修复，均为所有产品空间共用的能力，对匿名公开产品和登录产品使用同一套数据选择、组件和展示规则。

不得引入：

- 匿名专用页面或匿名专用信息架构；
- RepoMap 专用文案、数据、布局、选择规则或硬编码；
- 仅在 Demo 中展示的用户影响、任务入口或折叠逻辑；
- 为展示效果增加的第二套 AI 摘要生成链路。

Demo 仅可在既有只读权限限制下有不同的写操作可用性、权限说明和登录引导。公开只读数据继续沿用现有公开 Demo 权限策略，成员隐私数据不因此扩大匿名暴露面。

### 2.2 保留产品工作台，不做落地页化重构

不采用全站四角色重构，也不把完整发布页复制到概览。所有用户继续共用产品工作台；概览只增加少量可下钻的任务导向内容，保留登录用户需要的审计密度。

### 2.3 保持 live 数据策略

沿用 `docs/demo-improvement-plan.md` A2 的既有裁决：公开产品继续随真实仓库演进，不冻结快照。可以选择和深链已有真实发布，但不得伪造、硬编码或为 RepoMap 固定展示内容。

## 3. 目标与非目标

### 3.1 目标

首次访问者应能快速理解：

1. 当前页面展示的是哪个仓库的产品空间，以及 CoDelphi 与该仓库的关系。
2. 产品现在有哪些已提取能力。
3. 最近发布对用户有什么影响。
4. 从哪里查看前后差异、回归建议和源码证据。

同时：

- 登录工作台的现有规格、地图、回归、导出与编辑流程不回归。
- 所有摘要继续可追溯到既有发布、规格或证据。
- 移动端不通过逐字换行压缩导航。
- 指标名称和统计口径可以被普通用户正确理解。

### 3.2 非目标

本轮不做：

- 四套角色专用界面；
- 新营销落地页；
- 技术架构图、完整调用图或运行时依赖分析；
- 自动判断系统不支持的功能；
- 测试覆盖充分性、失效测试识别或测试执行；
- 团队知识掌握评分、Bus Factor 或人员能力推断；
- 自动语义去重引擎；
- 为概览新增 AI 生成请求；
- 生产部署。

## 4. 总体设计

采用“同一产品工作台 + 通用任务导向概览 + 权限驱动操作”的方案。

概览仍使用 `buildProductOverview` 作为唯一视图数据组装入口，使用 `ProductOverview` 渲染。新增内容均来自已经持久化的发布、AI 变更说明、行为变化和规格数据，不在浏览器中新增分析，不在展示层推断新事实。

信息顺序调整为：

1. 产品身份与通用来源说明；
2. 本次发布的用户影响；
3. 规格问答；
4. 轻量任务入口；
5. 发布时间线；
6. 当前核心能力；
7. 覆盖与知识健康事实。

任务入口是现有视图的导航，不是新的角色数据系统。完整发布变化、规格和回归任务仍由原有视图承担。

## 5. 产品身份与来源说明

在产品页头使用所有产品通用的来源说明，明确当前产品空间由 CoDelphi 根据所连接仓库持续生成。说明使用现有产品、仓库和分析数据，不出现匿名专用文案，也不提及特定仓库名作为代码常量。

建议文案模式：

> CoDelphi 根据此仓库的持续分析形成功能规格、行为变化与回归建议；结论附源码证据，采纳前经人工核实。

页头保留产品名、仓库链接、分析状态和现有操作。该说明用于建立产品与工具的关系，不替代产品自身简介。

## 6. 用户影响摘要

### 6.1 数据来源

使用最新发布已经落库的 `changes.user_impact`，对应现有 `ChangeRow.userImpact` 与 `components/change-item.tsx` 的“用户影响”展示。不得使用新的 AI 请求生成概览专用文本。

`getProductDetails` 已经返回发布变化所需的 `changes`。`buildProductOverview` 的输入需要显式接收这些数据，并只选择最新发布所属条目。

### 6.2 选择与展示规则

新增纯数据投影，规则如下：

1. 只使用最新发布的变更说明。
2. 过滤空白 `userImpact`。
3. 保持确定的原始顺序，最多取 3 条。
4. 每条展示功能名、用户影响和最新发布深链。
5. 深链使用现有 `?view=changes#release-{id}`，不新建详情页。
6. 证据核查在发布变化页完成，概览不复制完整证据列表。

最新发布没有任何非空用户影响时：

- 有行为变化：展示现有确定性功能级变化统计，并提供发布深链；
- 无行为变化：展示“本次未发现规格行为变化”及瘦身回归边界；
- 不使用更早发布冒充最新发布，不生成替代性用户影响。

历史发布存在用户影响而最新发布没有时，可以另提供“查看最近一次有行为变化的发布”导航，但必须明确日期和发布身份，不与“本次发布”混称。

### 6.3 空态与异常

无发布、无变更说明、无用户影响、用户影响为空字符串均为正常数据状态，不报错。数据读取失败沿用页面现有错误处理，不在客户端隐藏整页错误。

## 7. 通用任务入口

在概览提供轻量导航，任务文案优先于角色标签：

| 主任务 | 目标 | 可用数据 |
| --- | --- | --- |
| 这个产品现在能做什么？ | 产品规格或核心能力 | 当前规格 |
| 这次发布改变了什么？ | 用户影响与前后差异 | 最新发布 |
| 这次建议重新验证什么？ | 最新发布回归清单 | 回归任务 |
| 最近有哪些可追溯的变化？ | 30 天变更索引；登录用户可继续查看知识健康 | 发布与事实统计 |

角色名只能作为辅助说明，不决定数据可见性，不形成四套界面。

入口必须根据数据是否存在显示真实空态或禁用原因，不得链接到不存在的数据。权限不足时只调整需要权限的目标，公开只读内容继续可访问。

不得出现“团队掌握程度”“完整影响面”“系统不能做什么”“哪些测试已经失效”等超出当前能力的承诺。

## 8. 发布时间线降噪

### 8.1 分组规则

仅折叠时间线中**连续**的零行为变化发布：

> N 次提交均未发现规格行为变化 · 展开提交记录

展开后保留每个原始发布的标题、日期、commit、摘要和链接。

零行为变化以该发布没有行为变化条目为准，不使用发布摘要字符串匹配。AI 变更说明是否存在不决定行为变化计数。

### 8.2 保留审计语义

- 不删除零变化发布；
- 不合并非连续发布；
- 不把零变化计入行为变化数量；
- 分组只影响概览时间线，不改变发布变化页、API 或持久化数据；
- 单个零变化发布可以直接展示，连续多条才分组。

## 9. 覆盖率与可信边界

### 9.1 统一口径

当前 `coverageRatio = implBytesAssembled / implBytesTotal`，而 `implFilesAssembled/implFilesTotal` 是文件数量。展示统一改为：

> 源码装配覆盖率（按文件字节）12.1% · 已装配实现文件 70/79 个 · 证据文件 35 个

同时保留：

> 覆盖率描述本次分析实际读取的源码范围，不代表结论正确率；规格未覆盖不等于产品不支持。

数字仅为示例，实际渲染使用当前回执，不硬编码。

### 9.2 实现边界

提取共用的纯展示格式化逻辑，供概览与规格工作台复用，避免两处文案漂移。不修改覆盖率计算算法，不增加第二个文件数量百分比，不把“源码装配覆盖率”改名为“规格正确率”或“证据可信度”。

无可用回执时继续显示明确的缺失状态，不按文件数量推算字节覆盖率。现有版本链回执继承机制保持不变，但展示必须对应当前规格实际关联的回执，不得为填补空白另作推断。

## 10. 规格质量治理

### 10.1 问题处理原则

名称相近、摘要逐字相同或证据高度重叠的功能，先进入人工复核，不在 UI 中直接合并。

- 职责不同但摘要相同：修订摘要，使其说明各自职责，并保留证据。
- 确认为重复：在规格层人工去重，保留必要的历史与人工保护语义。
- 无法确认：保留并标记待核实，不自动删除或合并。
- 概览不得通过隐藏重复功能伪装成规格已经去重。

### 10.2 本轮范围

只复核 RepoMap 当前暴露出的近似功能与重复摘要，作为真实规格质量整改；不为 RepoMap 编写特殊展示规则，不建设自动语义去重引擎。

优先核对：

- 架构事实检测与覆盖评估；
- Targeted corpus Gold 评估；
- 定向 Gold 评估；
- Python SQL 操作与 Python SQL 操作提取；
- 其他摘要逐字相同的核心能力卡。

人工编辑继续遵守 `source='manual'` 不被自动分析覆盖的既有红线。

## 11. 权限与操作预期

### 11.1 权限驱动，而非 Demo 专用功能

写操作的展示和可用性应由有效权限决定。匿名公开产品与登录只读成员均不能执行写操作；编辑者和管理员继续沿用现有权限。

可以将“是否可写”与“是否展示工作台编辑控件”拆开，避免当前公开 Demo 为展示控件而传入 `canEdit=true` 造成语义混淆。Demo guard 继续负责匿名只读提示与登录引导，服务端权限校验仍是最终边界。

### 11.2 按钮表现

只读状态下：

- “立即分析”“发布产品”等写操作降为次要按钮；
- 明示“登录后可用”或“只读权限”；
- 点击不得发出实际写请求；
- 匿名用户可看到登录引导，登录只读成员看到权限说明；
- 不只依赖点击后的弹窗解释不可写状态。

搜索、证据、规格、公开回归清单与允许的导出保持只读可用。成员姓名、维护分布等数据是否匿名展示继续由现有权限策略决定，本设计不扩大其公开范围。

## 12. 移动端与可访问性

修改共用样式，不做 RepoMap 专用媒体查询。

### 12.1 导航与布局

- `.view-tabs a` 不换行、不收缩；
- `.view-tabs` 自身允许横向滚动；
- 页面主体不得出现整体横向溢出；
- 发布时间线标题、操作按钮、仓库链接和元数据在窄屏合理换行；
- 搜索框和表单控件不得被固定宽度挤压；
- 保留键盘焦点与可点击区域。

### 12.2 字号与对比度

- 元数据和小字正文原则上不低于 12px；
- 普通文本对比度至少 4.5:1；
- 不仅增大字号，同时调整当前浅灰颜色；
- 不用低对比度表达关键空态、权限限制或证据边界。

至少验收 1440×900、390×844、360×800 三种视口。

## 13. 组件与数据边界

预计职责分配如下，具体文件级任务在实施计划中展开：

- `lib/product-details.ts`：提供概览所需既有发布变更说明，不增加分析调用。
- `lib/product-overview.ts`：用户影响投影、零变化连续分组、任务入口数据、统一空态。
- `components/product-overview.tsx`：通用来源说明、用户影响、任务导航和分组时间线。
- `components/product-navigation.tsx` / 页面访问控制组装：向操作区传递明确的有效写权限。
- `components/analyze-button.tsx` 与发布操作组件：只读状态文案、样式和拦截。
- `components/spec-workspace.tsx` 及共用覆盖展示逻辑：统一覆盖率口径。
- `app/globals.css`：通用移动端和对比度修复。

不新增数据库表，不修改规格版本、发布、回归任务或权限数据模型。

## 14. 测试与验收

### 14.1 单元与组件测试

覆盖：

1. 用户影响只取最新发布、过滤空白、最多 3 条、顺序稳定。
2. 无发布、无行为变化、无用户影响和大发布的回退行为。
3. 不使用更早发布冒充最新发布。
4. 零变化只按连续区间分组，展开数据完整，非连续发布不合并。
5. 覆盖率明确展示字节口径和文件数量口径，无回执时不推断。
6. 任务入口在数据缺失和权限不足时不产生虚假链接。
7. 匿名与登录只读均不能发写请求；编辑者流程不回归。
8. 通用组件不包含 RepoMap 硬编码或匿名专用数据分支。

### 14.2 端到端走查

匿名公开产品：

> 打开产品空间 → 理解产品来源 → 查看用户影响 → 打开发布变化 → 查看前后差异 → 打开源码证据 → 查看回归清单 → 导出允许的 Markdown

同时验证写操作无实际请求、搜索失败有可见提示、无私有成员数据泄露。

登录编辑者：

> 产品概览 → 规格 → 发布变化 → 回归状态更新 → 发布稿 → 导出

确认通用展示变更不破坏既有编辑和审计流程。

### 14.3 视觉与可访问性验收

- 桌面与手机标签均不逐字换行；
- 页面无整体横向溢出，标签容器可独立横滚；
- 元数据可读，普通文本对比度达到 4.5:1；
- 用户影响、权限限制、空态和证据边界在移动端完整可读；
- 保留桌面审计密度，不把全部发布内容堆入概览。

### 14.4 首次理解验收

以 5 名未见过页面的 PM、QA、研发混合测试者进行走查，至少 4 人能在 30 秒内回答：

- 当前产品空间与 CoDelphi 的关系；
- 最近发布对用户有什么影响；
- 从哪里查看回归建议和源码证据。

该测试衡量可理解性，不以角色自评替代功能验收。

### 14.5 工程验收

实施完成后运行并通过：

- `npm run typecheck`
- `npm test`
- `npm run build`

生产验证仅在用户另行明确要求部署后执行。

## 16. 假设与约束

1. 不为 Demo 专门做功能是唯一新增的展示层约束；权限限制除外。
2. 所有产品共用本次新增概览能力，RepoMap 只是首个验收案例。
3. 继续采用 live 公开数据，不冻结快照。
4. 用户影响只复用已落库文本，展示层不补充事实、不增加 AI 请求。
5. 规格去重需要人工核实，UI 合并不视为规格治理。
6. 公开权限策略不因为可理解性整改而扩大，成员隐私数据不匿名开放。
7. 本轮不包含生产部署、DNS、Webhook 配置或 Docker 镜像操作。
