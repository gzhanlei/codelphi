# 工作区自己的模型配置：服务端不为没配模型的工作区调模型

状态：已实现，**未推送、未部署**（分支 `feat/organization-model`，提交 `eee93dd`、`62edc14`、`62697b7`、`38775e7`、`df915c9`，等产品负责人发话）。2026-11-27。

## 1. 规则

产品负责人 2026-11-27 的原话：

> 如果打开服务端分析开关，应当让用户输入自己的模型配置。codelphi不替用户支付模型费用。

此前把所有产品改成客户端分析之后，我说过「哪个产品想回来，告诉我，改一个开关就行」。这句话作废：切回服务端分析的前提是那个工作区先配置了自己的模型（服务地址、API key、模型名），之后它的服务端分析都用这份配置跑，费用由工作区直接付给模型服务商。

## 2. 范围

| 事项 | 做法 | 谁定的 |
|---|---|---|
| 服务端分析 | 产品由服务端分析时，它的工作区必须先有自己的模型。入队、执行、webhook、定时扫描、手动分析各有一道闸门 | 产品负责人的规则 |
| 网站上面向用户、会在服务端调模型的功能 | 理解层刷新、发布稿单块润色、发布稿草稿的文案改写、规格问答的综合回答，都改用工作区自己的模型 | 我的默认（方案批准时列明，产品负责人没有改） |
| CoDelphi 自己的内部流程 | 反馈裁决、业务分组候选照旧用 CoDelphi 的 key | 我的默认（同上） |
| SAU 计费 | 照旧。SAU 买的是分析服务；模型费用由工作区付给它的模型服务商 | 我的默认（同上） |
| 粒度 | 每个工作区一份配置，同一工作区的产品共用 | 我的默认（同上） |
| 谁能配置、谁能切换 | 工作区的 editor 和 owner | 沿用设置页的做法 |
| 模型服务地址 | 只接受 https 的公网地址 | 我定的，安全需要 |
| temperature | 对工作区自己的模型不发；CoDelphi 自己的 key 照旧发 0 | 依据 Kimi coding 接口对 `temperature: 0` 回 400 的教训 |

## 3. 设计

### 3.1 存储（迁移 `086_organization_models.sql`，只加不改）

- `organization_models`：`organization_id`（主键，外键到 `organizations`，删组织时级联）、`base_url`、`api_key_encrypted`、`model`、`verified_at`、`created_by`、时间戳。
- `llm_call_receipts.model_source`（可空）：`organization` 表示这次调用用的是工作区的 key；留空表示 CoDelphi 自己的。
- key 用 `lib/secret-box.ts` 加密（AES-256-GCM），主密钥是 `SESSION_SECRET`，和 GitHub 集成的 secret 同一个。明文只在保存前验证那一次用到。

### 3.2 地址防护（`lib/organization-model.ts`）

地址是用户填的，服务器却要替他连过去，所以有三道，缺一不可：

1. 只接受 https；不许带用户名密码、查询串、片段；主机不能是 `localhost` 或内网地址的字面量。
2. 连接之前解析域名，解析出来的每个地址都必须是公网地址。只查字面量挡不住「公网域名指向内网」。
3. 连接钉在校验过的那些地址上（`node:https` 加自定义 `lookup`）。只做第 2 步，校验和连接之间域名还能再变一次。

没有这三道，任何能改设置的人都能让服务器去请求它内网里的服务，再从报错里读应答。

### 3.3 出口与绑定

服务端所有模型调用都走 `lib/ai.ts` 的 `requestStructuredCompletionDetailed`。它现在看两把 key：

- 当前这次干活绑定了一个工作区模型（`withOrganizationModel`，AsyncLocalStorage）：请求发到那个地址，用那个 key 和模型名，不发 temperature；回执记 `model_source = 'organization'`。同一个工作区同时在途的请求数上限是 2（租户的套餐常限制并发），多出来的排队。
- 没有绑定：发出的请求和以前逐字节相同（测试钉住了请求体），回执照旧。

绑定找不到配置时抛 `model_not_configured`，**不会退回 CoDelphi 的模型**。工作区的模型拒绝时，原因并成一行、key 换成占位符、截到 300 个字符带出来（和客户端同一条规则）。

### 3.4 闸门

规则只在 `lib/analysis-executor.ts` 一个判断点。一条查询同时回答「产品由谁分析、工作区有没有模型」。

| 入口 | 没配模型时 |
|---|---|
| 入队（`enqueueRunWithReservation`） | 在锁计费账户、写任何东西之前被拒，没有 run、没有预留 |
| 执行（`runAnalysisSafely`） | 已排队的 run 被标失败，原因 `model_not_configured`，不认领 |
| webhook（两阶段投递） | 记一条跳过，回 202，不入队、不预留、不累加待处理的推送数 |
| 定时扫描 | 不捞这个仓库，待处理的计数留着，配好模型后下一轮带上 |
| 手动分析、补分析 | 409，提示去设置页 |
| 理解层刷新（定时清扫） | 不捞这个产品 |
| 理解层刷新（手动） | 409，提示去设置页 |
| 发布稿单块润色 | 409，提示去设置页 |
| 发布稿草稿生成 | 草稿照常生成，**不做**文案改写；应答里 `copyRewrite: "skipped"`，页面提示没有做 AI 润色 |
| 规格问答 | 检索到的规格条目照常返回，没有 AI 综合回答；应答里 `aiUnavailableReason` 说明原因 |

后两行不是 409：它们的主体功能不需要模型，模型只是锦上添花，拒掉整个请求比说明清楚更糟。匿名访客看公开演示产品时也是这样。

### 3.5 界面

- 设置页「07 模型配置」：服务地址、API key（密码框）、模型名，「验证并保存」。保存前服务端用填的配置真调一次模型，通过了才加密入库；不通过什么都不保存，并说出服务商拒绝的原因。之后只显示地址、模型名和验证时间，key 不再出现。删除要先确认；还有产品由服务端分析时服务端拒绝，并说出是哪些。
- 产品设置「06 分析方式」：客户端分析 / 服务端分析。工作区没配模型时「服务端分析」不可选，并写明原因、给出设置页的链接。`PATCH /api/products/[slug]` 接受 `analysisExecutor`，没配模型时 409。界面上的限制是给人看的，这一道才是绕不过的。当前就是服务端分析、但工作区没模型的产品（配置后来被删了），仍然选中「服务端分析」并显示提示，不偷偷改选。
- 上传 key 的权限改叫「客户端分析上传」（原来叫「本地快照导入（BYO）」，早就名不副实）；MCP 面板的介绍补了上传用途。
- 数据说明加了两句（中英）：模型 key 加密保存、只用于替这个工作区调用它指定的模型服务；工作区配了模型时，服务端分析所需的代码发到它指定的地址，不经过部署方的网关。

## 4. 没有做的、已知的限制

- **业务分组候选、反馈裁决仍用 CoDelphi 的 key。** 这是我的默认，产品负责人没有逐项确认过。
- 理解层刷新、发布稿、规格问答的调用回执里 `account_id` 本来就是空的（「免费口径」），所以成本报表能看出「是工作区的 key」（`model_source`），看不出是哪个工作区。
- 删除模型配置前问的「还有没有产品在用服务端分析」和切换分析方式之间不是原子的。两头同时操作可能留下一个「由服务端分析、但没有模型」的产品：无害，闸门会拒绝它的分析，页面会提示。
- 生产上的 `airecord`（#20）是 `server` 且没有仓库。它不影响任何分析，但会让「删除模型配置」被拒，要先把它的分析方式改成客户端分析。
- 保存前的验证调用、以及之后每一次真实的模型调用，**没有在真实的模型服务商上跑过**：单元测试用的是替身，演练把 `fetch` 换成了会报错的替身。第一次真实运行可能遇到服务商的其它限制（并发、参数、模型名）。
- 真实 MySQL 的演练都跑在本机的 MySQL 9.6 上，生产是 8.0.30。迁移 086 还没有在 8.0 上执行过。
- 为了新闸门，三个原有测试的数据库替身补了「工作区配了模型」这件事（没有改任何断言）：`tests/billing-enqueue.test.ts`、`tests/analysis-run.test.ts`、`tests/full-analysis.test.ts`。

## 6. 部署与回滚

- 迁移 086 只加不改，回滚只回滚镜像：新表和新列留着无害。
- 上线那一刻行为不变：所有绑了仓库的产品都是客户端分析，在有人配置模型并把产品切到服务端分析之前，没有任何东西走新的路径。网站上的功能在没有模型时按 3.4 的表降级。
- 上线后产品负责人要做的两件事，都在页面上：设置页「模型配置」填一份；想让哪个产品回到服务端分析，就在它的设置里改「分析方式」。第一次真实运行建议拿一个不重要的产品试。
