# 行为账本正确性契约与 Golden Validation v1

日期：2026-11-23
状态：契约待书面审阅；不授权大规模重构、生产启用或部署

## 1. 目标与边界

本契约定义 CoDelphi 如何维护可信的行为账本、解释行为变化，并验证 MCP 能否用于开发决策指导。

优先顺序：

1. P0：行为存在性、生命周期与最终账本正确性；
2. P0：跨 Run 身份与增量 Diff 正确性；
3. P1：证据与场景级影响关系精确性；
4. P1：发布、freshness 与对账完整性。

本契约不引入新的全量提取架构，不继续投入 batch、fused、通用 Code Facts 或 GUARD，不要求先建立全仓人工真值集。

## 2. 行为、场景与身份

### 2.1 行为与场景

- **行为**：某类 Actor 在明确业务条件下，能够观察到的产品能力或结果。
- **场景**：行为在特定前置条件、角色、输入或错误路径下的具体表现。
- 行为身份与场景身份分别维护，不能用功能名、函数名、文件路径或模型临时措辞替代。

### 2.2 同一行为/场景的判定

同一身份必须同时满足：

- Actor 与业务目标相同；
- 外部可观察结果相同；
- 关键业务条件与边界相同；
- 实现证据能够支持该语义关系。

函数改名、文件移动、函数拆分、格式化、左右回执合并等实现变化本身不改变身份。

`stableKey` 只是名称级投影，不是身份权威。功能名、函数名、路径和 AI 重述只能作为匹配线索，不能单独决定身份。

### 2.3 不允许的身份处理

- 不因函数改名自动产生 removed + added；
- 不因两次 AI 使用不同措辞自动判为不同行为；
- 不因同一文件中存在多个场景就把它们全部视为同一行为；
- 不把角色、权限或关键前置条件不同的场景合并为同一场景；
- split / merged 无法证明身份时保持 Uncertain，不强行匹配。

## 3. 生命周期分类契约

每次分析必须分别输出 **最终账本状态** 与 **变化分类**。不得只检查本次 AI 输出。

| 分类 | 判定条件 | 禁止事项 |
| --- | --- | --- |
| Added | 新证据确认此前不存在的身份，且外部行为成立 | 重提取偶然发现不得直接等同新增 |
| Modified | 身份保持，但关键条件、权限、流程或外部结果改变 | 措辞、结构或证据位置变化不得误作 Modified |
| Removed | 有充分证据确认行为已不存在 | 未提取、未命中、证据失效或身份丢失不得判 Removed |
| Unchanged | 身份与行为语义均不变 | 不要求源码文本或证据位置不变 |
| Uncertain | 无法确认新增、修改、删除或不变 | 不得强行 Added/Removed/Unchanged |
| Conflict | 相同 Actor 与条件下存在互斥且同时激活的结果 | 不得激活，不得静默保留双方 |

Removed、Uncertain 与 Unchanged 必须严格区分。证据失效只表示需要重锚或复核，不等于 Removed。

## 4. 沿用、失效与冲突处理

### 4.1 允许沿用的条件

旧场景只有在其身份与语义均被确认不变时才可沿用。以下情况不得直接沿用：

- 权限、角色、关键条件或外部结果已变化；
- 证据指向的实现已发生语义变化；
- 无法确认 split / merged 身份；
- 当前证据不足且未标 Uncertain。

### 4.2 证据状态与行为状态分离

- `current`：证据仍支持当前行为；
- `re-anchored`：行为不变，证据已重新定位；
- `stale`：原证据失效，需要复核；
- 行为状态独立为 Added / Modified / Removed / Unchanged / Uncertain / Conflict。

### 4.3 冲突处理

同一 Actor 与条件下出现互斥结果时：

- 标记 Conflict 并阻止激活；
- 保留冲突两侧及证据供复核；
- 不以新结果覆盖旧结果，不以旧结果阻碍新结果，不静默去重；
- 冲突解决前不得将该版本声明为可信。

人工规格与人工裁决不得被自动覆盖。

## 5. 可信 Release 契约

Release 只有同时满足以下条件才可标记完整、可信：

1. 绑定确定的 afterSha、run、base spec version 与当前 spec version；
2. `specSnapshot.sha == afterSha`，freshness 不回退；
3. 最终账本状态满足本契约，无未处理 Conflict；
4. Added / Modified / Removed / Unchanged / Uncertain 与实际证据一致；
5. 证据路径、行号和语义支持关系有效；
6. `missingExpected` 不含应被发现而未发现的行为，`unexpected` 不含计划外行为变化，人工规格未被覆盖；
7. 覆盖率、Unknown、未决项和降级如实披露；
8. 不被更新的 run supersede；被 supersede 的 run 不得激活或冒充完整 Release。

后续快照可以修复证据，但不能 retroactively 证明某个丢失的 Release 曾经完整。

对账必须支持 Added / Modified / Removed / Unchanged / Uncertain 意图。纯重构应能显式表达 `expect_no_change`，不得因 stableKey 不出现在零 Delta changes 中而误报 `identity_not_found`。路径 intent 只能做路径验收，不能单独证明行为身份。

## 6. MCP 两类能力分别验收

### 能力 A：项目知识检索

包括功能、场景、证据和历史查询。允许披露覆盖不足后提供辅助价值，但不得把未覆盖解释为不存在。

### 能力 B：开发决策指导

包括爆炸半径、回归建议、意外变化识别和删除判断。必须满足更高的最终账本、影响精确率、增量身份和 Release 完整性要求，不能由能力 A 的正常工作推定能力 B 可靠。

MCP 的差异化价值应是跨版本身份、历史变化、已验证证据、前后对账与可追溯知识状态，而不仅是比 Agent 多返回几个文件。

## 7. Golden Validation v1

### 7.1 验收原则

- 使用真实提交和小型明确 fixtures，不建立全仓人工真值集；
- Truth Card 在查看任何 CoDelphi 输出前冻结；
- 同时检查最终账本、Delta、证据、MCP 反查和 Release 对账；
- 同一提交多次重放，不能只接受一次偶然正确；
- 不用单元测试、34/34 或功能/场景数量增长代替产品验收。

### 7.2 行为变化组

| 案例 | 必须验证的最终账本与变化 |
| --- | --- |
| 新增行为 | Added 正确，原行为不误删 |
| 修改行为 | 身份保持，Modified 的条件和结果正确 |
| 删除行为 | Removed 被记录，旧行为退出激活 |
| 共享权限守卫 | 只影响真正调用方，不扩大无关场景 |
| 删除旧入口但保留其他入口 | 只移除目标路径，不误删剩余能力 |
| 不同角色不同表现 | 角色条件保持独立，不产生冲突或误合并 |

首个真实案例：`8b6a0c07c8ab852209ef0cc7f70da480e229a9ef`。必须同时检查匿名 CTA 的 Removed、登录用户其他入口的 Unchanged，以及最终账本不存在显示/隐藏冲突。

### 7.3 行为不变组

| 案例 | 必须验证的结果 |
| --- | --- |
| 纯函数拆分 | 身份不变，证据正确重锚 |
| 文件移动 | 身份不变，路径证据更新 |
| 函数重命名 | 无 removed + added 假 Delta |
| 回执合并重构 | 无行为变化，冲突语义不变 |
| 格式调整 | 无行为变化 |

首个真实案例：`d96ae8e36f7b177f1659b2795be69e137de75d49`。预期 59/59 场景身份保持、零 Delta、全部 afterSha 证据有效，纯重构对账使用 `expect_no_change` 而非 stableKey 出现在 changes 中。

### 7.4 账本稳定性组

必须覆盖：

- 同一代码重复分析；
- 同一提交多次重放；
- 跨 Run 身份保持；
- run superseding；
- 空窗口与旧快照回退；
- 证据失效与重锚；
- 拆分/合并无法确认时保持 Uncertain。

### 7.5 通过条件

- 所有必需案例的最终账本状态与 Truth Card 一致；
- 不允许激活 Conflict；
- 删除被记录，未提取不得误删；
- 不变案例零虚假 Delta；
- 共享文件变化时，全部预期受影响场景必须命中，全部预期不受影响场景不得被扩大；
- 重复分析的最终账本一致，不接受偶然命中；
- 证据、freshness、Unknown 和 Release 对账满足本契约；
- 任一必需项失败即 not fit，不以其他指标抵消。

## 8. 当前基线与后续顺序

当前证据：

- 权限线存在漏报、误报和生命周期错误，不能用于决定回归范围；
- 纯重构线的身份保持和证据重锚有效，证明无需推倒重来；
- freshness、coverage、零变化对账和 release superseding 仍存在明确缺陷。

后续只能按以下顺序推进：

1. 先修复最终账本存在性、生命周期与冲突处理；
2. 再修复跨 Run 身份与增量 Diff；
3. 然后提高场景级影响关系精确性；
4. 最后补齐发布、freshness 与对账完整性，并重放 Golden Validation v1。

在契约与 Golden Validation 通过前，不新增全量分析架构，不将实验结果升级为生产机制。
