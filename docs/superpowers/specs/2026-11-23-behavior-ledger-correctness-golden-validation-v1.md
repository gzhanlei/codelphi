# 行为账本正确性契约与 Golden Validation v1.1

日期：2026-11-23
状态：书面冻结评审；暂不批准实施、架构重构、生产启用或部署

## 1. 目标与质量原则

本契约定义 CoDelphi 如何维护行为的身份、存在性、语义、证据和历史状态，并验证 MCP 能否用于开发决策指导。

核心原则：

> 在证据不足时宁可不做确定判断，在证据充分时必须正确维护行为状态。

优先顺序：

1. P0：行为存在性、生命周期与最终账本正确性；
2. P0：跨 Run 身份与增量 Diff 正确性；
3. P1：证据与场景级影响关系精确性；
4. P1：发布、freshness 与对账完整性。

本契约不引入新的全量提取架构，不继续投入 batch、fused、通用 Code Facts 或 GUARD，不要求建立全仓人工真值集，不以召回率替代正确性。

## 2. 身份连续性与行为语义

### 2.1 四类概念

| 概念 | 作用 |
| --- | --- |
| Behavior Identity | 追踪同一业务能力的历史连续性 |
| Behavior Semantics | 描述当前实际行为及其外部结果 |
| Scenario Identity | 追踪具体条件下场景的历史连续性 |
| Scenario Semantics | 描述当前场景的 Actor、前置条件和结果 |

**行为**：某类 Actor 在明确业务条件下，能够观察到的产品能力或结果。

**场景**：行为在特定前置条件、角色、输入或错误路径下的具体表现。

行为身份与场景身份分别维护，不能用功能名、函数名、文件路径或模型临时措辞替代。

### 2.2 身份连续性判定

身份判断依据业务能力的历史连续性、Actor、业务目标及证据关系综合判断。

身份连续性**不要求当前行为语义完全相同**。外部结果、权限、关键条件或流程发生变化时，可以且通常应当分类为 Modified，不得仅因此自动拆分为 Removed + Added。

例如“匿名访客的发布入口”：

- Actor 和业务目标保持；
- 权限条件和外部结果发生变化；
- 身份连续，分类为 Modified。

只有原业务能力被替换为另一种无关能力时，才可形成 Removed + Added。

`stableKey` 只是名称级投影，不是身份权威。功能名、函数名、路径和 AI 重述只能作为匹配线索。

### 2.3 不允许的身份处理

- 不因函数改名、文件移动、函数拆分、格式化或回执合并自动产生 removed + added；
- 不因两次 AI 使用不同措辞自动判为不同行为；
- 不因同一文件存在多个场景就把它们全部视为同一行为；
- 不把角色、权限或关键前置条件不同的场景合并为同一场景；
- split / merged 无法证明历史连续性时保持 Uncertain，不强行匹配。

## 3. 生命周期分类与 Removed 正向证据

每次分析必须分别输出 **最终账本状态** 与 **变化分类**，不得只检查本次 AI 输出。

| 分类 | 判定条件 | 禁止事项 |
| --- | --- | --- |
| Added | 新证据确认此前不存在的身份，且外部行为成立 | 重提取偶然发现不得直接等同新增 |
| Modified | 身份保持，但关键条件、权限、流程或外部结果改变 | 不得因结果改变而自动拆分身份 |
| Removed | 有充分正向证据确认行为已不存在 | 未提取、未命中、证据失效或身份丢失不得判 Removed |
| Unchanged | 身份与行为语义均不变 | 不要求源码文本或证据位置不变 |
| Uncertain | 无法确认新增、修改、删除或不变 | 不得强行 Added/Removed/Unchanged |
| Conflict | 条件重叠时，同一业务目标出现互斥结果 | 不得激活，不得静默保留双方 |

### 3.1 Removed 的必要证据

Removed 是关于行为不存在的**正向结论**，不是“当前分析没有发现行为”的结论。必须同时满足：

1. **原实现路径已检查**：能够解释原行为为什么不再成立；
2. **替代路径已考虑**：没有遗漏仍能实现同一业务行为的其他入口或路径；
3. **行为边界已验证**：有足够证据支持该 Actor 在指定条件下已经无法获得原结果。

删除组件、函数或文件本身不足以证明整个业务行为 Removed；组件仍存在也不足以证明行为仍可达。无法满足全部条件时必须进入 Uncertain。

必须区分：

- `Removed`：已确认行为不存在；
- `Not observed`：当前分析没有观察到行为；
- `Evidence stale`：旧证据不再有效；
- `Uncertain`：无法判断行为是否仍然存在。

## 4. 沿用、证据状态与 Conflict

### 4.1 允许沿用的条件

旧场景只有在其身份与语义均被确认不变时才可沿用。以下情况不得直接沿用：

- 权限、角色、关键条件或外部结果已变化；
- 证据指向的实现已发生语义变化；
- 无法确认 split / merged 身份；
- 当前证据不足且未标 Uncertain。

### 4.2 证据状态与行为状态分离

- `current`：证据仍支持当前行为；
- `re-anchored`：行为不变，证据已重新定位；
- `stale`：原证据失效，需要复核；
- 行为状态独立为 Added / Modified / Removed / Unchanged / Uncertain / Conflict。

证据失效只表示需要重锚或复核，不等于 Removed。

### 4.3 Conflict 的条件重叠判定

Conflict 基于条件的逻辑关系，而不是条件字符串是否一致，也不受功能归属限制。

对同一 Actor，在存在可满足的共同前置条件时，两个激活行为对同一业务目标给出互斥的外部结果，且不存在明确的优先级、覆盖关系或条件细分规则，即为 Conflict。

| 条件关系 | 处理 |
| --- | --- |
| 条件不相交 | 不构成冲突 |
| 条件重叠且结果互斥 | Conflict |
| 条件关系无法判断 | Uncertain，不能默认无冲突 |

不同功能的场景也可能对同一业务目标构成冲突。人工规格与人工裁决不得被自动覆盖；冲突解决前不得将版本声明为可信。

## 5. Release、零变化对账与历史状态

### 5.1 可信 Release 的必要条件

Release 只有同时满足以下条件才可标记 Trusted：

1. 绑定确定的 afterSha、run、base spec version 与当前 spec version；
2. `specSnapshot.sha == afterSha`，freshness 不回退；
3. 最终账本满足本契约，无未处理 Conflict；
4. Added / Modified / Removed / Unchanged / Uncertain 与证据一致；
5. 证据路径、行号和语义支持关系有效；
6. `missingExpected` 不含应发现而未发现的行为，`unexpected` 不含计划外行为变化，人工规格未被覆盖；
7. 覆盖率、Unknown、未决项和降级如实披露；
8. 未被更新 Run 在验收完成前 supersede；被 supersede 的 Run 不得激活或冒充 Trusted Release。

后续快照可以修复证据，但不能 retroactively 证明某个丢失的 Release 曾经完整。

### 5.2 Release 状态机与历史保留

| 状态 | 含义 |
| --- | --- |
| Created | 已绑定 afterSha 和分析 Run，尚未开始验收 |
| Validating | 正在检查账本、证据、freshness 和对账 |
| Trusted | 所有必要契约通过，可用于 MCP 开发决策 |
| Review | 存在 Uncertain、证据不足或其他需要复核的情况 |
| Superseded | 被更新版本替代，不再是当前有效 Release，但历史记录保留 |
| Failed | 出现完整性、身份或其他硬性契约失败 |

Release 是不可变历史记录。Superseded 不意味着删除，也不意味着历史 Release 不可追溯。

必须区分：

- 已完成并可信，后来被更新版本替代；
- 尚未完成就被 supersede；
- 已完成但尚未通过可信性验收就被 supersede。

Golden 测试所需的不可变快照和运行记录必须提前具备；Release 最终可信性修复可以在后续阶段完成。

### 5.3 变化与不变意图

对账意图区分：

- `expect_added`；
- `expect_modified`；
- `expect_removed`；
- `expect_unchanged`；
- `expect_no_change`。

`expect_unchanged` 用于指定行为或场景；`expect_no_change` 用于整个提交。`expect_no_change` 是提交级断言，要求：

- 无 Added / Modified / Removed；
- 既有 Behavior Identity 与 Scenario Identity 保持；
- 必要时证据正确 re-anchor；
- 无未解释的身份丢失；
- 无新 Conflict。

`expect_no_change` 不等于没有生成 Delta、没有提取到变化或没有发生错误。以下状态必须区分：

| 状态 | 含义 |
| --- | --- |
| `unexpected_change` | 出现预期之外的行为变化 |
| `unverified_no_change` | 没有发现变化，但证据不足以证明行为不变 |

不得通过漏提取获得虚假的零 Delta。路径 intent 只能做路径验收，不能单独证明行为身份。

## 6. MCP 两类能力及端到端验收

### 6.1 能力 A：项目知识检索

包括功能、场景、证据和历史查询。允许在披露覆盖不足后提供辅助价值，但不得把未覆盖解释为不存在。

端到端任务：

- 查询匿名用户能否看到发布入口；
- 查询管理员和普通用户的权限差异；
- 查询某行为的实现证据；
- 查询某行为在两个版本之间发生了什么变化。

要求回答与最终账本一致，并明确披露 Uncertain 和证据失效状态。

### 6.2 能力 B：开发决策指导

包括爆炸半径、回归建议、意外变化识别和删除判断，必须满足更高的最终账本、影响精确率、增量身份和 Release 完整性要求。

端到端任务：给定待修改文件，要求回答：

- 哪些行为可能受影响？
- 哪些场景需要回归？
- 哪些行为不应受影响？
- 是否存在已知冲突？
- 哪些结论尚未得到验证？

必须验证：

1. 影响范围与 Truth Card 一致；
2. 文件关联不直接等同行为影响；
3. 已确认的 Removed 不得遗漏；
4. Uncertain 不得表述成确定事实；
5. 所有结论具有可追溯证据。

MCP 的差异化价值是跨版本身份、历史变化、已验证证据、前后对账与可追溯知识状态，而不仅是比 Agent 多返回几个文件。

**两类端到端验收都必须保存 MCP 原始响应**，不能只记录人工最终判断，否则无法证明 MCP 正确消费了账本。

## 7. Golden Validation v1.1

### 7.1 Truth Card 契约

每个案例必须在查看任何 CoDelphi 输出前冻结以下字段：

| 字段 | 内容 |
| --- | --- |
| Base SHA / After SHA | 修改前后代码版本 |
| Actor | 涉及的用户角色 |
| Business intent | 真实业务意图 |
| Preconditions | 行为成立的前置条件 |
| Expected behavior | 修改前后的行为描述 |
| Expected classification | Added / Modified / Removed / Unchanged |
| Expected identities | 应保持或变化的身份关系 |
| Expected evidence | 可人工核验的代码路径与行号 |
| Expected impact | 应受影响和不应受影响的场景 |
| Expected final ledger | 最终激活、失效、冲突和未决状态 |
| Author / frozenAt | 制作人与冻结时间 |
| Independent reviewer / verdict | 独立复核人及复核结论 |

不得根据模型输出反写或放宽 Truth Card。

历史观察“59/59 场景文本一致”只证明文本一致，不能自动升级为身份或语义一致。只有经过 Truth Card 独立确认的身份映射才能作为 Golden Truth。

### 7.2 行为变化组

| 案例 | 必须验证的最终账本与变化 |
| --- | --- |
| 新增行为 | Added 正确，原行为不误删 |
| 修改行为 | 身份保持，Modified 的条件和结果正确 |
| 删除行为 | Removed 被记录，旧行为退出激活 |
| 共享权限守卫 | 只影响真正调用方，不扩大无关场景 |
| 删除旧入口但保留其他入口 | 只移除目标路径，不误删剩余能力 |
| 不同角色不同表现 | 角色条件保持独立，不产生冲突或误合并 |

首个真实案例：`8b6a0c07c8ab852209ef0cc7f70da480e229a9ef`。必须同时检查匿名 CTA 的 Removed、登录用户其他入口的 Unchanged，以及最终账本不存在显示/隐藏冲突。

### 7.3 行为不变组

| 案例 | 必须验证的结果 |
| --- | --- |
| 纯函数拆分 | 身份不变，证据正确重锚 |
| 文件移动 | 身份不变，路径证据更新 |
| 函数重命名 | 无 removed + added 假 Delta |
| 回执合并重构 | 无行为变化，冲突语义不变 |
| 格式调整 | 无行为变化 |

首个真实案例：`d96ae8e36f7b177f1659b2795be69e137de75d49`。使用 `expect_no_change`，要求身份保持、零 Delta、全部 afterSha 证据有效，不要求 stableKey 出现在 changes 中。

### 7.4 重复运行与语义一致性

**重复 Run 一致性**：相同代码重新分析，以下语义结果一致：

1. 激活行为集合；
2. Behavior Identity 与 Scenario Identity 映射；
3. 行为变化分类；
4. 冲突集合；
5. 未决事项集合；
6. 对账结果。

**重放一致性**：同一提交重新处理，不产生重复身份、额外变化或额外冲突。

**顺序一致性**：不同提交处理顺序或 Run superseding 不得改变最终有效版本的语义。

证据位置可以变化，但必须重新验证有效性；运行 ID、时间戳和分析耗时不要求一致。

### 7.5 指标与通过条件

| 指标 | 计算方式 | 目的 |
| --- | --- | --- |
| Impact Recall | 命中的预期受影响场景 / 全部预期受影响场景 | 是否漏报 |
| Impact Precision | 命中的预期受影响场景 / 全部被报告为受影响的场景 | 是否误扩 |
| Identity Retention | 正确保持身份的预期场景 / 全部预期保持身份的场景 | 是否漂移 |
| False Delta Rate | 虚假 Delta / 全部报告 Delta | 是否制造噪声 |
| Removal Accuracy | 正确删除的行为 / 全部预期删除行为 | 删除是否正确 |
| Conflict Detection | 检出的真实冲突 / 全部预期冲突 | 是否漏掉矛盾 |

Golden Validation v1.1 采用严格 fixture 级验收：

- 预期影响场景全部命中，非预期影响场景全部不命中；
- 预期删除全部正确退出激活状态；
- 不变案例零虚假 Delta；
- 不允许漏掉已知冲突；
- 所有必需案例的最终账本与 Truth Card 一致；
- 重复 Run、重放和顺序一致性满足本契约；
- 任一必需项失败即 `not fit`，不得以其他指标抵消。

小型 fixture 全部通过只证明这些明确场景通过，不能直接推导全仓覆盖率或生产可靠性。

## 8. 实施约束与顺序

后续只能按以下顺序推进：

1. 最终账本存在性、生命周期与冲突处理；
2. 跨 Run 身份与增量 Diff；
3. 场景级影响关系精确性；
4. Release、freshness 与对账完整性。

每个阶段必须：

1. 先写失败测试，确认现有系统确实违反契约；
2. 只做最小修复，不顺便引入新架构；
3. 最后用真实提交和固定 fixture 重放。

Golden 测试所需的不可变快照和运行记录应尽早具备。修复代码与验收标准不得由同一个模型根据实验结果不断互相调整，避免针对样例过拟合。

当前证据表明：权限线存在漏报、误报和生命周期错误；纯重构线的身份保持和证据重锚有效，无需推倒重来；freshness、coverage、零变化对账和 release superseding 仍存在明确缺陷。

在本契约与 Golden Validation 通过前，不新增全量分析架构，不将实验结果升级为生产机制。
