# 定向增量分析与无分区上限设计

日期：2026-11-17
状态：已获用户方向确认，进入实施

## 1. 背景与问题

当前 `runAnalysisBody` 无论全量还是增量，都通过 `getPartitionedAnalysisSources` 在全仓执行 BFS 装配，并受 `ANALYSIS_MAX_PARTITIONS`（默认 6）限制。

生产 run 342（SalesBuddy，Spec v240）证明了这个口径问题：

- 本次 diff 只有 3 个文件，3 个均已读取；
- 全仓 BFS 继续装配其他文件，最终 6 个分区触顶；
- 回执显示 102/2797 个实现文件、2.9%，`sourceCoverage=partial`；
- 2.9% 是单次 run 装配率，不是 Spec v240 的累计证据覆盖率，却被并排展示，容易被理解为整份规格只分析了 2.9% 的代码。

这带来两个独立问题：

1. 增量任务仍承担全仓读取和 AI 调用成本，失去增量节省时间与 token 的意义。
2. 固定的 6 分区上限让全量或大型增量任务静默停止在部分代码上，以平台预设成本止损线代替用户决定。

## 2. 目标

- 增量分析只读取本次 diff 与受影响功能的既有证据文件；相关的未变更代码仍包含在内，无关代码不进入 AI。
- 全量分析继续覆盖完整实现面。
- 分区仅约束单次模型调用的上下文大小，不限制一个 run 的总分区数。
- 取消主分析路径上等效的 run 级总读取量止损，不以其他隐性上限替代 6 分区限制。
- 保持未受影响功能沿用、手动条目不覆盖、证据校验、规格坍缩防护和发布变化计算不变。
- 从用户界面移除装配覆盖率、装配文件数和提取趟数等内部诊断指标。

## 3. 非目标

- 不取消单文件大小、单分区文件数、行区间数和内容字节数等技术限制。
- 不改变 SAU 结算和 `llm_call_receipts` 的真实逐趟记账方式。
- 不改变影子全量对比的显式诊断开关；默认增量路径不得因此额外执行全量对比。
- 不重跑或改写历史 run、历史 Spec 版本和历史覆盖率回执。
- 不在本次实现中引入异步全仓发现或新的定时全量任务。

## 4. 核心决策

### D1：增量采用定向装配

当 `affectedKeys !== null` 时，读取范围为：

```text
requiredPaths = 本次 change.files 路径
              ∪ 受影响功能在最新 spec_file_index 中的全部证据路径
```

- diff 中未归属既有功能的文件仍在范围内，用于发现新功能。
- 受影响功能相关的未变更证据文件也在范围内，避免多文件功能因缺少上下文而被错误重建。
- 未受影响功能继续由 carry-forward 原样沿用，不重新读取或提取。
- 增量路径不再执行全仓 BFS。

### D2：全量回退保持不变

以下情况继续走全仓 BFS：

- 首次分析或没有上一版规格；
- 无法可靠确定受影响功能；
- diff 过宽或受影响比例超过现有阈值；
- 输出语言切换；
- 其他现有全量回退分支。

`getRemoteAnalysisSources` 的单窗口用途（例如显式影子对比）保持单窗口语义，不把它误改为无限分区入口。

### D3：分区数量不设上限

`getPartitionedAnalysisSources` 的主入口不再接受 `maxPartitions`，循环只在以下条件停止：

- 没有新的候选路径；
- 当前分区没有可读取内容；
- 发生现有错误。

每个分区仍受 `analysisSliceBudgets` 的文件数、行区间数和内容字节数约束。分区数量由实际范围决定，不再由 `ANALYSIS_MAX_PARTITIONS` 决定。

本地快照全量分析也遵循同一规则，不保留另一套分区上限。

### D4：清理等效的 run 级总量止损

主分析索引不再使用固定的总目录展开数、总 blob 读取数和总内容字节数作为 run 级截断：

- `maxTreeExpansions`；
- `maxBlobFetches`；
- `maxTotalContentBytes`。

这些预算在主分析路径改为无限值；单 blob 大小、单次行数等读取安全限制保留。全量实现面枚举不再默认限制 1000 个目录。

行为枚举是额外分析增强层，不改变其现有独立开关与指标语义；主提取所需的 diff 和受影响证据文件不得依赖该增强层才能读取。

### D5：覆盖率回执按实际装配范围解释

- 全量 run：仍以完整实现面为分母。
- 定向增量 run：以 `requiredPaths` 中实际存在且属于 implementation 的文件为分母，不再为了计算展示比例遍历全仓。
- `diffTotalPaths / diffSelectedPaths / diffOmittedPaths` 始终针对真实 diff，不受定向证据文件并集影响。
- 新 run 不再因分区数量产生 `partitionsCapped=true`；字段保留用于历史兼容，新值恒为 false。
- 不可读、缺失或被清洗的文件继续通过现有错误和完整性维度披露，不因取消分区上限而隐藏。

不新增数据库迁移，历史回执保持不变。

### D6：用户界面不再展示内部装配指标

- 产品总览移除整条 `TrustLine`，包括覆盖率、装配文件数、证据文件数、人工条目和 Spec 版本。
- 规格工作台移除覆盖率、装配文件数和提取趟数；保留静态分析边界与人工补充入口。
- 后台回执和完整性账本继续用于诊断，不设置“低于某百分比才隐藏”的展示阈值。

## 5. 模块设计

### 5.1 `lib/spec-file-index.ts`

新增按 stable key 读取受影响功能证据路径的查询：

```ts
loadAffectedEvidencePaths(repositoryId, affectedKeys): Promise<string[]>
```

查询当前 `spec_file_index` 与 `spec_features`，去重并稳定排序。它只扩大相关代码范围，不改变 affected keys 的计算和全量回退判断。

### 5.2 `lib/slice-planner`

在规划输入中增加：

- `discovery?: "full" | "required_only"`，默认 `full`；
- `requiredPaths?: readonly string[]`，缺省回退到 `diffPaths`。

规划顺序：

1. 按路径序装配 `requiredPaths ?? diffPaths`；
2. `discovery === "full"` 时继续 `walkScopeDirectories`；
3. `required_only` 时直接完成规划，不执行全仓 BFS。

多趟之间继续使用 `excludePaths` 去重，保证每个相关文件最多装配一次。

### 5.3 `lib/remote-analysis.ts`

- 透传 `discovery` 与 `requiredPaths`。
- 主分区入口持续规划直到范围耗尽，不接收数值型分区上限。
- 单窗口入口通过独立的单窗口选项或直接单次规划实现，不暴露成本上限配置。
- 主分析索引的总读取预算改为无限，保留单 blob 和单次读取限制。

### 5.4 `lib/analysis.ts`

在现有 affected keys 解析之后构造定向请求：

- `affectedKeys === null`：全量请求，行为不变；
- `affectedKeys !== null`：加载受影响证据路径，构造 `requiredPaths`，设置 `required_only`。

覆盖率计算与请求使用同一范围，避免规划范围和回执范围漂移。日志分别记录实际模式、定向路径数、分区数和真实 diff 覆盖数，不再把单次全仓百分比当成 Spec 累计覆盖率。

### 5.5 `lib/analysis-coverage.ts` 与快照分析

- 增加定向实现面元数据读取，避免增量时为覆盖率执行全树枚举。
- 移除新回执的分区触顶推导；保留字段兼容历史。
- 快照全量分析取消 `maxPartitions` 选项及 `partition_limit_reached` 新告警。
- 清理 `analysisMaxPartitions` 和 `ANALYSIS_MAX_PARTITIONS` 的当前文档与调用。

## 6. 正确性与回归红线

CoDelphi 行为账本反查命中“AI 规格分析与发布变化”（49 条原始场景、11 条 canonical 场景），必须重点验证：

- 未受影响 generated 功能及场景保持上一版措辞；
- `source = 'manual'` 的功能和场景不被自动分析覆盖；
- 多证据文件功能重提取时上下文完整；
- diff 中未归属文件仍可形成新功能；
- 连续小步 push 不会使工作台功能数或规格场景数坍缩；
- 发布变化继续来自合并后的规格事实，不制造计划外移除；
- 全量回退路径、重试、证据清洗和发布持久化保持原行为。

`lib/remote-analysis.ts` 与 `lib/slice-planner/index.ts` 在账本中未覆盖，不能以“未搜到场景”推断没有回归风险，必须用直接单元测试补齐。

## 7. 测试与验收

### 7.1 定向范围

- 构造包含大量无关文件的索引、3 个 diff 文件和一个多证据受影响功能：AI 只收到 diff 与相关证据路径，不收到无关文件。
- 断言增量不调用全仓 BFS，也不为覆盖率执行全树实现面枚举。
- 断言相关但未变更的证据文件仍被读取。
- 断言未归属 diff 文件继续进入提取。

### 7.2 无分区上限

- 构造需要超过 6 个分区的定向范围和全量范围：全部分区均被规划并提取，最终范围无遗漏。
- 第 7 个及更多分区仍执行，`partitionsCapped=false`。
- 单窗口调用仍只返回一个窗口。
- 主分析路径不再读取 `ANALYSIS_MAX_PARTITIONS`。

### 7.3 既有契约

- 更新旧的“增量与全量共用全仓分片”测试为“增量仅对相关范围分片”。
- 保留并运行 carry-forward、手动条目、规格坍缩、全量回退、发布变化、影子对比和快照测试。
- 保留全量分析的多分区合并与证据校验测试。

### 7.4 界面与交付验证

- 总览不再渲染 `overview-trust-line`。
- 规格页不再渲染装配百分比、装配文件数或提取趟数，静态边界链接仍存在。
- 运行 `npm run typecheck`、`npm test`、`npm run build`。
- 不用生产重跑代替自动化验收；历史 run 342 只作为问题证据，不在本次实施中改写。

## 8. 实施假设

- 用户已明确接受完整读取所产生的实际时间与 token 成本，不由平台预设总分区或总读取量止损线。
- 成本透明仍通过真实调用回执提供，不通过强制截断提供。
- 工作区存在其他未提交的快照和产品改动；实施时只修改本规格需要的代码，并保留这些已有改动。
