# 客户端形态与发布触发方式讨论整理

日期：2026-11-24  
状态：讨论整理稿，已按两轮外部评审修订，并按产品负责人的七条决定更新。决定已并入《客户端增量分析与 Delta Merge Contract 设计》，记录在那份规格的 §24.7。七条决定之后又确认了四件事（§8），也已并入。产品负责人决定不再送外部评审，按文档开工。

## 1. 讨论的问题

《客户端增量分析与 Delta Merge Contract 设计》定义了 `publish` 命令和合并契约，但没有回答它以什么形态交付、由谁在什么时候触发。本文整理 2026-11-24 围绕这几件事的讨论：

- 客户端是命令行、TUI 还是 GUI。
- 模型怎么调用，凭证从哪里来、怎么配置。
- 账本跟踪哪个分支，何时发布由谁决定，agent 如何发现账本落后。
- 自动发布的许可记在哪里，要不要专门的确认。
- 发布检查在时序上能保证什么，命令行如何确定自己操作的是哪个仓库。
- 支持哪些代码托管平台。

增量分析算法与合并契约本身不在讨论范围内，那部分已通过终审。

## 2. 当前方案

1. **形态**：独立的单文件命令行程序，可以被脚本和 agent 调用。不做 TUI，不做原生 GUI。
2. **发布是一次性命令**：跑完就退出。不做常驻服务，不做 watch 模式。
3. **账本只跟踪一个分支，不要求仓库有远端。** 有远端时，它是代码托管平台上配置的默认分支，不假定为 `main`；没有远端时，它是首次发布时登记的本地分支，也就是当时检出的那个。纯本地的仓库也能用。推送 feature branch 不触发。任意分支的账本不在首期范围内。下文把这个分支叫跟踪分支。
4. **发布对象是跟踪分支的最新提交。** 有远端时，它是远端默认分支的最新提交，本地检出的提交必须与它一致，只发布已经推送的提交；没有远端时，它是本地跟踪分支的最新提交。
5. **三件事分开定义。**
   - 模型调用机制，已定：命令行用独立配置的模型 API key 直连模型服务商。不复用宿主 agent 的模型或订阅授权，也不调用宿主厂商的无头命令行。
   - 命令行由谁启动：agent，或用户手动执行。
   - CI：延后支持，首期不做（已定）。将来需要时另行设计，由用户自行承担把密钥存进 CI 的风险。
6. **凭证**：命令行按顺序查找模型 key，先看环境变量，再看仓库之外的凭证环境文件，再看各 harness 的本地凭证，用户填写的优先于自动找到的。都没有时进入接入步骤：选服务商、粘贴 API key，结果写进凭证环境文件。接入步骤借鉴 Cindy 的做法。详见 §4。
7. **触发与许可**：agent 在两种时机询问用户是否发布。用户说过“以后不用问”之后，这条许可记在本机的仓库配置里，不随仓库提交，也不依赖远端地址。不做专门的确认机制，需要用户决定的事由 agent 在对话里说明并等待回答。
8. **发布检查分三个时点。** 命令行在开始分析前按状态矩阵检查一次，上传前再复查一次；服务端在提交事务里校验账本基线没有变化，不查远端（已定）。见 §3.11。
9. **平台范围分阶段**：GitHub 首期正式支持；GitLab、Gitee、Gitea 在对应工作完成并通过验证后开放；其他内部 git 服务不承诺。发布本身不依赖平台，因为命令行在本地读远端的默认分支和最新提交；这个范围只影响新鲜度、账号连接和证据链接。
10. **命令行必须能唯一确定本地仓库**，见 §3.12。

## 3. 逐项讨论

### 3.1 形态

| 方案 | 结论 | 原因 |
|---|---|---|
| 独立命令行 | 采用，作为核心 | agent 是通过 shell 调用它的，所以必须可脚本调用、有机器可读的输出；其余界面只能是附加层 |
| TUI | 现阶段不做 | TUI 的主要价值是给长时间运行的任务提供常驻进度面板；增量让日常发布变成秒级到分钟级，结果本来在网页端看 |
| 原生 GUI | 现阶段不做 | 成本最高，并且与网页端重复 |

现状已经是这个形态：Radar 是用 esbuild 打出的 `snapshot.cjs`，放进技能包由 agent 驱动；仓库里没有终端界面或桌面界面的依赖。现有技能文档（SKILL.md）明确写着不要把 Radar 变成持续分析，所以持续客户端应当是独立入口。

用户真正会感受到的问题，以及不靠 TUI 或 GUI 的解法（建议，未展开）：

- 上传前想知道什么会离开这台机器：用 `--dry-run` 生成可读的审阅产物，边界见 §3.13。
- 出错后不知道下一步：每个错误码对应一个动作，能自动恢复的自动恢复。
- 安装和登录麻烦：单文件可执行，加浏览器设备码登录。

什么时候重新考虑：用户经常在本地跑很长的全量分析，并且现有进度输出不够用时，考虑 TUI；使用者是不用终端的合规或团队管理者，或者需要可视化审批哪些数据可以离开机器时，优先做本地网页或菜单栏小应用。

### 3.2 发布的运行方式

| 方式 | 结论 | 原因 |
|---|---|---|
| 一次性命令，由事件触发 | 采用 | 跑完就退出，不留进程；agent 和用户手动调用的是同一条命令 |
| 常驻服务 | 不采用 | 一个一直在后台读源码、往外传数据的进程，用户和合规都会警惕；git 和 CI 本来就会在推送时执行任务；排查“它在不在跑”很麻烦 |
| watch 模式 | 不采用 | 需要终端一直开着，关掉就停 |

### 3.3 CI、本地 hook 与 webhook

CI 延后支持，首期不做（已定）。讨论得到的结论保留如下，供将来设计时参考：

- **CI 不需要本地起服务。** GitHub 上的 CI（GitHub Actions）在 GitHub 的服务器上运行，不经过用户电脑。PR 合并进主分支同样会触发。
- **CI 的凭证代价。** 要用它需要把发布用的 key 和模型 API key 都存成 GitHub 密钥，由用户自行承担凭证托管的风险。
- **本地 hook 不推荐。** git 没有“推送之后”触发的 hook，只有 `pre-push`。它在推送发出之前运行，非零退出会中止推送。在它里面启动发布，推送随后被拒绝时，账本会推进到一个远端不存在的提交。它只适合做预检。
- **本地接收 webhook**：需要常驻的 HTTP 服务和公网可达地址，等于 §3.2 否决的常驻服务。
- **服务端收到推送后自己分析**：这是现有的托管模式，服务端跑模型、按 SAU 计费，不是客户端模式。两种模式按仓库选择，可以并存。

### 3.4 模型凭证与调用方式

**把模型 key 交给 CI 是接受度障碍。** 原因有两条：

- 模型 key 是计费凭证。放进 GitHub 等于多托付一方，而且能被这个仓库里的任何一个工作流读到。
- 很多用 agent 的人根本没有能放进 CI 的 key。他们用的是包月订阅，按条款只能在这些工具里用。

**“由 agent 会话提供模型”其实是三件事。** agent 能启动命令行；命令行能用上 agent 的模型调用能力；命令行能合法使用 agent 的订阅授权。三者并不等价。初稿只写了“模型凭证只留在本机，由 agent 会话提供”，表达了目标，没有定义机制。

Radar 现有的通道（`lib/snapshot/host-ai.ts`）：

| 通道 | 机制 | 状态 |
|---|---|---|
| standalone | 命令行用 `AI_API_KEY`、`AI_MODEL`、`AI_BASE_URL` 直连 OpenAI 兼容接口 | 已有，此前的实测记录显示可用 |
| 宿主注入的桥 | 宿主通过 `CODELPHI_HOST_AI_*` 环境变量注入当前模型的访问通道 | 取决于宿主是否提供 |
| 宿主厂商的无头命令行 | 命令行启动 `claude -p`、`codex exec` 等，由它们使用自己的登录态 | 本机实测未跑通，见下 |
| agent 自己执行工作单 | 命令行只准备工作单和校验结果，模型部分由 agent 完成 | 可用，但按此前的实测记录，token 消耗比直连高一个数量级以上 |

本机探测结果（2026-11-24）：Claude Code 的通道能探测到；Codex 未安装；ZCode 没有对应的通道档案。经 Claude Code 的无头命令行发一句最小提示，挂起超过 3 分钟没有返回，原因没有查明。

**决定：模型调用只用 standalone 这一种机制。** 理由是机制明确、不经手任何订阅凭证、也不涉及厂商对无头调用的条款，而且是已有实测记录的通道。

评审指出，初稿把这个决定写成了“只用 agent 调用 standalone 命令行这一种方式”，与 §3.1、§3.3 里保留的 CI 内容冲突。实际上这是三个独立的维度：

| 维度 | 定义 |
|---|---|
| 模型调用机制 | 命令行使用独立配置的 API key，直连模型服务商（已定） |
| 命令行由谁启动 | agent，或用户手动执行 |
| CI 的定位 | 延后支持，首期不做（已定）。将来需要时另行设计，由用户自行承担把密钥存进 CI 的风险 |

这样既不让人误以为 CI 可以使用 agent 的订阅授权，也不必为“只用 agent 调用”这句话删掉 CI 的讨论。

代价：用户要有一把模型 API key。只有不提供 API key 的订阅、又找不到可用凭证的用户用不了。国内几家的包月编程套餐一般也提供 API key，见 §4.4。凭证从哪里来，见 §4。

### 3.5 发布时机与跟踪分支

发布时机：

| 方案 | 结论 | 原因 |
|---|---|---|
| 完全由用户决定何时发布 | 留作可选项 | “记得发布”是额外负担，账本只在用户想起来时才更新。适合模型额度很紧、只在里程碑发布、每次上传都需要审批的团队 |
| agent 适时询问 | 默认 | 把问题带到用户已经在的地方，也就是 agent 会话里。时机要收窄，否则一天推送多次就是噪音 |
| agent 推送后直接发布 | 用户授权后 | 相当于用户说过“以后不用问” |

询问的时机：

- agent 把提交推送到默认分支成功之后。这是主要时机，增量窗口最小、成本最低。没有远端的仓库，改为本地跟踪分支有了新提交之后。
- agent 要用账本之前，发现默认分支领先于账本。先问要不要发布，再做计划。这一条只对有代码托管连接的仓库成立。
- 代价大或情况异常时，agent 要先说明：需要全量重同步、首次发布、与人工内容冲突。

用户给过自动发布的许可后，前两种不再问；第三种仍然要先说明。

跟踪分支：评审指出，初稿把“agent 推送成功”当作触发时机，却没有区分推的是默认分支还是 feature branch。agent 成功推送 feature branch，并不意味着默认分支前进。规格 §7 本来就规定首期只接受单一分析分支，其他分支返回 `branch_not_tracked`。方案按同一口径明确：账本只跟踪默认分支，推送 feature branch 不触发。将来要支持任意分支，需要另行设计分支级的账本身份。

默认分支不能写死成 `main`。它可能叫 `main`、`master` 或别的名字，也可能被仓库管理员修改。命令行按代码托管平台上配置的默认分支判断，AGENTS.md 也按同样的说法写，否则命令行和 agent 会各按一套语义判断。命令行在本地读这个默认分支（§3.10），不需要平台适配，所以内部 git 服务器上的仓库同样能发布。

多人协作的流程里，同事推的是 PR，不是直接推默认分支。所以默认分支自己前进，主要来自本人推送或 PR 被合并。走 PR 流程的用户，默认分支更新后本地要先更新，再发布。

### 3.6 发现账本落后

推送可能是用户自己在终端做的。发现机制因此必须与“谁推送”无关。两个触发都只看默认分支。

这个信号已经有了。MCP 的三个读取工具（`get_project_summary`、`search_scenarios`、`lookup_by_files`）都带新鲜度块（`lib/mcp/freshness.ts`）：取最新 release 的 sha，经代码托管平台的接口与远端默认分支比较。比较失败时如实返回 `available=false`，不伪装成新鲜。AGENTS.md 已要求 agent 在计划阶段读 MCP，所以发现动作不需要新增，只需要在那一眼上多看一个字段。

现状是：比较可用时只有仓库、已分析提交、分支名和两个变更文件计数，没有远端最新提交，也没有检查时间（已核对 `lib/mcp/freshness.ts`）。

三处要调整，已写进规格 §17.1：

1. **比较对象要说清。** 新鲜度响应至少给出：仓库、默认分支、已分析的提交、远端默认分支的最新提交、检查时间、是否成功取得远端状态、是否新鲜。提交号不相等只能说明两个提交不同；落不落后、能不能发布，由 §3.10 的状态矩阵在本地用提交图判断。
2. **缓存。** 结果按（仓库，已分析提交）缓存 5 分钟。刚推送完就读，可能拿到推送前的结果。普通读取可以用缓存；agent 刚把提交推送到默认分支之后，必须能强制刷新。
3. **只比提交号。** 新鲜度块目前会从平台拉 diff 来数变更文件，这与规格 §2.1 第 7 条“客户端模式下服务端不主动拉取源码”冲突。客户端模式下只取远端默认分支的最新提交号来比，变更文件数由 agent 在本地数。

没有远端的仓库没有新鲜度。这类仓库只靠“本地跟踪分支有了新提交”来触发。

网页端和命令行的分工：远端状态的查询可以复用同一个函数，网页端也能借此按需提示账本落后。但默认分支的解析和缓存策略只能有一份实现；Git 提交图的判断只由拥有本地仓库的命令行负责，网页端不做。

### 3.7 平台范围

讨论经过三种范围：

| 范围 | 结论 | 取舍 |
|---|---|---|
| 任何 git 远端都同等支持 | 未采用 | 发现账本落后必须在本地做；网页端和 MCP 都提示不了账本过期；现有实现有多处默认 GitHub（见下表） |
| 不理会远端，agent 认为有必要就提示 | 部分采纳 | 发布本身不依赖远端，纯本地的仓库也能用（已定）；但发现账本落后仍然用新鲜度，不在本地另做检查命令 |
| 公共服务分阶段支持，发布不依赖平台 | 当前方案 | 发现账本落后不需要新的机制；平台范围只影响新鲜度、账号连接和证据链接 |

第三种是讨论中以“太复杂了”收窄出来，再按“纯本地用户也应该能用”调整的。

现状（已核对代码）：

| 环节 | 现状 |
|---|---|
| 连接管理 | 已支持 GitHub、Gitee、GitLab、Gitea；自建的 GitLab 和 Gitea 由管理员通过 `REPOSITORY_HOST_ALLOWLIST` 白名单放行 |
| 读仓库的适配器 | 只有 GitHub 和 GitLab（`lib/code-hosting/registry.ts`）。Gitee 和 Gitea 缺适配器，接口共八个方法 |
| 自建实例与企业版 | 适配器不读连接里的服务地址，GitLab 只认全局的 `GITLAB_API_BASE`，所以实际不通 |
| 推送通知 | 只有 GitHub 的 webhook |
| 导入时的仓库绑定 | 只有远端是 github.com 的仓库会建仓库记录。规格 §16.3 已改为不要求有远端 |
| 证据链接 | 生成时地址写死为 github.com |

新鲜度检查依赖适配器，所以目前只对 GitHub 和全局配置的那一个 GitLab 实例可用。

第一版修订稿把“GitHub、Gitee、GitLab 及兼容内部服务”整体列为首期支持，评审指出这与上表的交付能力不匹配。产品承诺改为分阶段，顺序已确认：

| 平台 | 承诺 | 开放条件 |
|---|---|---|
| GitHub | 首期正式支持 | 走通一次端到端验证 |
| GitLab | 验证后开放 | 适配器按连接读取实例地址；认证和证据链接在 gitlab.com 与自建实例上验证通过 |
| Gitee | 适配完成后开放 | 补读仓库的适配器，并完成认证和证据链接的验证 |
| Gitea | 适配完成后开放 | 同上 |
| 其他内部 git 服务 | 不承诺新鲜度和账号连接 | 发布仍然可用：命令行在本地读远端的默认分支和最新提交，不依赖平台适配 |

远端地址不需要用户手填。本地仓库的 git 配置里就有，Radar 已经在读（`readOriginRemote`：读 `origin`，把 `git@host:path` 转成 https，去掉地址里的凭证）。现有归一化只认 https 和 `git@host:path` 两种写法，带个人用户名或带端口的 ssh 地址读不出来。

### 3.8 账号连接

新鲜度比较需要服务端能访问平台。托管模式本来就要连（GitHub 走 GitHub App 安装，其他平台走令牌），这不是新增要求。

它只影响一类用户：通过 Radar 快照导入、从没连过账号的产品。这类产品只要一把发布用的 key 就能用，这也是导入路线的特点。它们的仓库记录上没有连接，服务端访问平台时只能走匿名接口：公开仓库可以比，但有频率限制；私有仓库比不了，新鲜度如实返回“不可用”。

已定：对这类用户，页面和 agent 都提示“想用自动提醒，请连接账号”。没有连接时，发布由用户主动发起。降级时要说清楚原因，不能把“比不了”显示成“最新”。已写进规格 §17.1。

### 3.9 自动发布的许可

AGENTS.md 是提交进仓库的内容，可能被其他协作者、PR 或外部贡献者修改。所以它只写流程：什么时候问，什么时候调用命令。它本身不是许可。

已定：

- **许可只记在本机。** 用户在对话里说过“以后不用问”之后，agent 把这条许可写进本机的仓库配置。它不随仓库提交，也不依赖远端地址，纯本地的仓库同样适用。
- **不做专门的确认机制。** 需要用户决定的事，例如全量重同步、首次发布，由 agent 在对话里说明并等待回答。全量重同步可能消耗较多模型额度，agent 必须先说明原因和代价。

评审曾建议用终端确认码或浏览器确认，让确认不经过 agent。产品负责人判断不需要。

要接受的风险：agent 有 shell 权限，技术上可以不经询问直接运行发布；如果 AGENTS.md 被改动，它也可能不按流程问。首期接受这一点。

两种权限仍然要分开理解：凭证权限是命令行持有发布 key，技术上能调用发布接口；用户许可是用户允许 agent 不再询问。持有发布 key 不等于用户许可过自动发布。

### 3.10 本地、远端与账本的状态矩阵

它们的关系必须用 Git 提交图判断，也就是祖先关系，不能只比较提交号字符串。下文把跟踪分支的最新提交叫目标提交：有远端时是远端默认分支的最新提交，没有远端时是本地跟踪分支的最新提交。

判定按固定顺序进行，一次只落到一个状态。表里几行可能同时成立，例如本地既落后于远端又落后于账本，先命中的一行决定处理方式（已写进规格 §7）：

前提是本地检出的提交在跟踪分支的历史上，detached HEAD 也允许。在别的分支上不进入下面的判断。

1. 取目标提交。有远端时先 fetch，再在本地读远端跟踪引用。读不到返回 `remote_unavailable`，不做发布判断。没有远端时，目标提交是本地跟踪分支的最新提交。
2. 本地是否已有需要的提交，包括目标提交和账本对应的提交（base）。有远端而缺对象时，fetch 后回到第 1 步。fetch 之后仍然缺 base，按下面“本地缺 base”一行处理。
3. 本地提交与 base 相同：一致，空操作。
4. 本地提交与目标提交不同：不发布。有远端时，本地领先提示先推送，本地落后提示先拉取，两者分叉提示先协调；没有远端时，提示先检出跟踪分支的最新提交。
5. 到这一步本地提交就是目标提交。base 是它的祖先，进入增量发布，窗口是 `base..head`。它是 base 的祖先，空操作：没有远端时提示本地落后，有远端时说明账本领先于远端。两者互不为祖先，需要全量重同步，由用户确认。

有远端时：

| 状态 | 判断 | 处理 |
|---|---|---|
| 一致 | 本地提交与 base 相同 | 没有待发布的变更，空操作 |
| 可发布 | 本地与远端相同，base 是本地提交的祖先 | 进入发布资格检查，窗口是 base 到本地提交 |
| 本地有未推送的提交 | 本地领先远端 | 提示先推送，不发布 |
| 本地落后 | 远端领先本地 | 提示先拉取，不发布 |
| 本地与远端分叉 | 互不为祖先 | 提示先协调，不发布 |
| 账本领先远端 | 本地与远端相同，远端最新提交是 base 的祖先 | 远端历史被改写，或此前发布过未推送的提交。不发布；需要全量重同步时由用户确认 |
| 账本与远端分叉 | 本地与远端相同，base 与远端最新提交互不为祖先 | 需要全量重同步，由用户确认 |
| 本地缺 base | 本地没有 base 对应的提交对象 | 先 fetch；fetch 后仍缺，不增量，也不自动转全量。先提示更新本地；确认该提交已经不可达，例如远端被改写、本地是改写之后的新克隆，再由用户确认全量重同步 |

没有远端时：

| 状态 | 判断 | 处理 |
|---|---|---|
| 一致 | 本地提交与 base 相同 | 空操作 |
| 可发布 | 本地提交是跟踪分支的最新提交，base 是它的祖先 | 进入发布资格检查 |
| 本地检出落后于跟踪分支 | 本地提交是跟踪分支最新提交的祖先，例如 detached 在旧提交上 | 提示先检出跟踪分支的最新提交，不发布 |
| 本地落后于账本 | 本地提交是跟踪分支的最新提交，它是 base 的祖先 | 空操作，提示本地落后 |
| 分叉 | 本地提交是跟踪分支的最新提交，它与 base 互不为祖先 | 需要全量重同步，由用户确认 |

本地缺 base 的处理与有远端时相同，只是没有 fetch 这一步。

没有远端的仓库，跟踪分支取首次发布时检出的那个分支，产品负责人已确认。命令行把它登记到仓库记录上，并写回本地 git 配置，在输出里说明。之后在其他分支上发布会被拒绝。

本地领先不等于可以直接发布：有远端时还要确认目标提交已经在远端默认分支上，所以“可发布”要求本地与远端相同。

fetch 的行为约束：fetch 只更新远端跟踪引用，不改工作区，也不切换当前检出的分支。命令行不能为了让状态矩阵通过，擅自对用户的工作区执行检出、合并、变基或重置。命令行要说明自己执行了哪些 Git 操作。

目标提交由命令行在本地读取，不经服务端，也不依赖平台适配。已实测（Git 2.54.0）：

- 克隆会把远端的默认分支记在 `refs/remotes/origin/HEAD`；没有这条记录时，`git fetch` 会补上。
- fetch 只更新远端跟踪引用，本地提交、当前分支和未提交的改动都不动。
- 远端不可达时 fetch 以非零退出。
- 平台之后改了默认分支，本地这条记录不会跟着变，要用 `git remote set-head origin --auto` 刷新，它同样要访问远端。所以命令行每次发布都刷新一次。

规格 §7 原来只有两行：head 与 base 相同是空操作；base 不是 head 的祖先就需要全量重同步。“本地落后”“本地缺 base”“账本领先远端”三种情况都会被归到需要全量重同步，是误判。并入规格时已经补上，并补了判定顺序。并入时还修掉一个漏洞：本地缺 base 时如果 fetch 也补不齐，只提示“更新本地”会让产品卡住，因为那个提交已经不在任何地方；现在是不自动转全量，由用户确认后显式执行。
### 3.11 发布检查的时序与保证

状态矩阵描述的是检查那一刻的状态。从检查到真正发布，中间隔着一次分析，可能要几分钟。初稿没有处理这个窗口，评审把它列为阻塞问题。

真实场景比初稿设想的窄：多人协作走 PR，没有人直接推默认分支。所以这段时间里默认分支被别人改写的可能性很低；更可能遇到的是一个 PR 被合并，默认分支向前推进。

处理办法是在三个时点各查一次，前两个已写进规格 §7：

| 时点 | 谁来查 | 查什么 | 不通过时 |
|---|---|---|---|
| 开始分析前 | 命令行 | 状态矩阵（§3.10） | 按矩阵处理，不开始分析 |
| 上传前 | 命令行 | 再取一次目标提交，有远端时重新 fetch。分析开始时的目标提交仍是它的祖先或与它相等，才上传 | 不上传，提示远端历史被改写 |
| 提交事务里 | 服务端 | 账本基线没有变化（规格 §14.1 已有） | `base_changed`，客户端重取基线、重新规划 |

远端只是向前推进时不放弃：目标提交仍是默认分支历史上的提交，这次发布有效，账本只是落后一截，下一次发布补上。只有历史被改写才放弃。评审建议“默认分支已经前进就拒绝提交”，没有采纳。

服务端不查远端（已定）。评审要求在“服务端提交时再查一次远端”和“如实说明只是客户端的乐观检查”之间选一个，选了后者。理由是前者只能缩小窗口，消不掉，而且只能放在事务前面，规格规定事务内不做网络调用。

所以保证的边界是：“目标提交在默认分支历史上”是客户端的乐观检查，两次检查之间仍有窗口。服务端保证的是账本自身的一致性：基线链、原子事务、幂等。远端被改写而账本已经推进时，下一次发布会判为账本与远端分叉，要求用户确认后全量重同步。文档和界面都不能把它说成强一致。

### 3.12 命令行如何定位仓库

agent 调用命令行时，必须能确定它操作的是哪个本地仓库。容易出错的情况：

- agent 的当前目录不是目标仓库。
- 同一个仓库有多个 worktree。
- agent 在一个 feature branch 的 worktree 里读了 MCP。
- 同一个项目有两个本地副本。
- agent 读的是远端产品，本机根本没有检出。

规则：

- 命令行必须唯一确定本地仓库。
- 默认使用当前目录所在的仓库。有远端时，验证它的远端地址与 CoDelphi 产品绑定的仓库一致；首次发布之后，改用本地 git 配置里记下的仓库标识核对（规格 §16.3）。
- 有远端指仓库有名为 `origin` 的远端，与 Radar 现在读远端地址的做法一致。没有 `origin` 的仓库按没有远端处理，命令行在输出里说明。
- 有多个 worktree 或无法唯一识别时，不猜，要求显式指定仓库路径。
- 本地仓库不存在、不可访问或身份不匹配时，返回明确的错误，不去别的目录找仓库。

### 3.13 `--dry-run` 的无副作用保证

承诺：不调用模型，不上传，不推进账本，不修改工作区。

| 行为 | 是否允许 |
|---|---|
| 读取本地源码和 Git diff | 允许 |
| 有远端时取远端状态。fetch 只更新远端跟踪引用 | 允许 |
| 调用模型服务商 | 不允许 |
| 向 CoDelphi 上传 delta | 不允许 |
| 创建 release，推进账本 | 不允许 |
| 修改本地 Git 状态，包括检出、合并、变基、重置 | 不允许 |
| 写入正式发布状态或持久化分析结果 | 不允许 |

它展示的是预计内容，不是最终的 delta。工作单要经过模型分析才生成最终内容，而 `--dry-run` 不调用模型。所以它给出的是本地可以确定的输入范围、两个数据出口各自的接收方和预计数据量。预计字节数不能说成实际字节数。

数据有两个出口：发给模型服务商的是工作单内容，包括 diff、受影响的证据源码和基线里的规格文本；发给 CoDelphi 的是 delta，包括规格文本、证据锚点和只在传输中存在的补丁。`--dry-run` 对两个出口分别列出接收方、内容和数据量。

查代码时发现一个原先没看到的事实：`repositories` 表没有远端地址这一列。它的身份是 `provider`、`owner`、`name` 三列，都非空且三者唯一，`provider` 只有四家托管平台的取值，多处代码直接读这三列来拼地址。所以“没有远端的仓库也能绑定”需要一次迁移，不是改一句约束就行。

规格 §16.3 按下面的默认写了。这是我补的设计，未经评审：

- 新增一种 `provider` 取值 `client`，表示仓库身份来自客户端登记，CoDelphi 不接入它的托管平台。这种行的 `owner`、`name` 取组织和产品的 slug，原有的唯一键照常成立。
- 首次发布按固定顺序确定仓库行：本地 git 配置里已有这个产品的仓库标识就用它；产品下恰有一条仓库行就复用；没有才新建，远端是 GitHub 时建 `github` 行，其余建 `client` 行；产品下有多条时不猜，要求显式指定。
- 复用之前只做能确定的核对，例如仓库行登记的是 GitHub 而本地远端不是同一个仓库，就拒绝。核对不了的情况只提示，因为选错产品的后果有界：全量重同步要用户确认之后才执行。
- `client` 行的证据链接返回空。界面在没有链接时本来就直接显示路径和行号。

## 4. 模型 key 从哪里来

命令行用 standalone 方式调模型，就必须拿得到模型 API key。要求是人工和 agent 都能配置。

现状：standalone 方式只从环境变量读取，`AI_API_KEY` 和 `AI_MODEL` 必填，`AI_BASE_URL` 可选；也可以用 `--env-file` 指定一个包含这几项的文件。没有固定位置的配置文件。`AI_BASE_URL` 不填时指向本地网关 `127.0.0.1:4000`。

### 4.1 查找顺序

产品负责人定的是：各 harness 的本地凭证都可以找，不限于 ZCode；实在找不到，就交互式问用户，或者请用户在凭证环境文件里填写。

“凭证环境文件”与仓库的约定一致：密钥只通过环境变量配置，不引入新的密钥存储方式。它是一个放在仓库之外、由用户填写的文件，里面是 `AI_API_KEY`、`AI_MODEL`、`AI_BASE_URL` 这些变量，命令行启动时读取。

规格正文按下面的顺序写（规格 §17.1）。查找的先后和优先级产品负责人已确认：用户填写的优先；先找 agent 工具的凭证与此不矛盾，找不到才接入，接入之后以用户填写的为准。

| 顺序 | 来源 | 说明 |
|---|---|---|
| 1 | 环境变量 | agent 启动命令行时会继承环境。按常见变量名自动识别，包括现有的 `AI_API_KEY`，以及各家 agent 常用的名字 |
| 2 | 凭证环境文件 | 用户明确填写的，所以优先于自动找到的。第一次使用时它还不存在，等于没有 |
| 3 | harness 的本地凭证 | 不限于 ZCode。Cindy、DSH 等都在查找范围内，每个 harness 存放的位置和格式不同，要逐个适配 |
| 都没有 | 接入步骤（§4.4） | 用户选服务商、粘贴 API key，结果写进凭证环境文件。用户手动运行命令行时可以交互；agent 调用时不能交互，命令行把接入命令交给用户，并以非零退出 |

把凭证环境文件排在 harness 凭证之前，是为了避免一种意外：用户已经在文件里填了自己的 key，命令行却因为先找到了某个 harness 的凭证而用了另一个。

接入时填写的 key 写进凭证环境文件，之后不用再问。产品负责人已确认。不写的话，agent 启动的命令行每次都卡在这里。

它与 standalone 机制不冲突：命令行仍然是拿一把 key 直接调模型接口，只是 key 的来源变了。
### 4.2 能不能读到，取决于 harness 存的是什么

| harness 的凭证形式 | 是否适合 |
|---|---|
| API key 放在环境变量里 | 适合，第 1 步就能读到 |
| API key 存在 harness 的配置文件里 | 可以做，每种 harness 要单独适配 |
| 登录令牌或端点令牌，比如用浏览器登录得到的账号令牌 | 不确定。它可能只对那个应用自己的端点有效，会过期；按各家条款，也可能只允许它自己的应用使用 |

本机查到的情况（2026-11-24，只看了位置和字段名，没有读取任何值，也没有拿任何令牌试调模型）：

| harness | 凭证在哪 | 存的是什么 |
|---|---|---|
| ZCode | 配置文件里没有模型凭证。命令行继承到的环境里有三个相关变量 | `ZCODE_BASE_URL`、`ZCODE_OFFICIAL_ENDPOINT_TOKEN`、`ZAI_BUSINESS_BASE_URL`。看起来模型经 ZCode 自己的端点访问，令牌是访问这个端点用的 |
| DSH | `~/.dsh/.credentials.yaml`，仅本人可读 | 浏览器会话密钥、设备 ID、账号平台的令牌（带签发方）。是登录令牌 |
| Cindy | 桌面应用。服务商认证的文件里只有一个归属标记 | 没有找到明文的凭证配置，可能在它的应用数据库或加密存储里 |

也就是说，在这台机器上，三个 harness 的本地凭证里都没有一把现成的模型 API key，读到的是端点令牌和登录令牌。所以第 3、4 步会是实际走得最多的路径，除非这些令牌本身可以当模型接口用。

### 4.3 配置与保护（部分已定）

| 方面 | 规则 |
|---|---|
| 管什么 | 两类凭证共用一个配置入口：模型 API key（服务商地址、key、模型），以及 CoDelphi 发布 key（服务地址、key） |
| 接入 | 走 §4.4 的接入步骤，结果写进凭证环境文件。人工可以直接用；agent 调用时不能交互，见 §4.1 |
| 凭证环境文件 | 放在仓库之外，命令行启动时读取。文件权限仅本人可读，权限过宽时提示 |
| 禁止的做法 | 不接受把 key 直接作为命令行参数，避免它出现在进程列表和 shell 历史里。不写进仓库里的文件，也不写进 git 配置 |
| 优先级 | 环境变量高于凭证环境文件，凭证环境文件高于 harness 的本地凭证。已经配好环境的终端不用动已保存的配置 |
| 服务商地址 | 由服务商目录补齐（§4.4）；自定义网关仍然可以填地址 |

之前的稿子建议存系统钥匙串，没有采用。规格 §3 的约束是不引入新的密钥存储方式，仓库的约定是密钥只通过环境变量配置，凭证环境文件与两者都一致。

**查看与检查是两件事，检查不能暗中变成数据上传。** 查看命令只显示掩码、服务商地址、模型和存放位置。检查命令的边界：

| 检查对象 | 允许 | 不允许 |
|---|---|---|
| 模型 API key | 发送一个明确标记的最小测试请求 | 发送真实源码、diff 或项目规格 |
| CoDelphi 发布 key | 认证和权限检查 | 创建 release、上传 delta、推进账本 |

模型 key 的最小调用也可能产生费用，检查命令要事先说明。

**显示实际的数据接收方。** 允许配置自定义地址，意味着实际接收方未必是用户熟悉的服务商，也可能是公司内部代理、本机模型网关、第三方兼容接口，或用户自己部署的转发服务。`--dry-run` 和检查命令都显示实际请求的目标主机，不能只显示模型品牌。

**新配置不再隐式默认到本地网关。** `AI_BASE_URL` 不填时现在指向 `127.0.0.1:4000`，对已有本地网关的用户合理，但不适合作为新用户的默认值。新配置必须明确选择服务商或填写网关地址；已有的配置沿用旧行为。

### 4.4 接入步骤：借鉴 Cindy 的做法

产品负责人提出，Cindy 引入 Kimi、智谱 GLM 这类模型端点的做法比“让用户填 key”好，可以借鉴。

我看了 Cindy 应用包里的静态定义和界面文案（2026-11-24；只看应用包，没有读它的用户数据目录）。它的做法是：

- **服务商目录。** 内置一份服务商清单，例如智谱 GLM、Kimi、MiniMax、阿里云百炼、硅基流动、腾讯云。每家是一条完整记录：名称、文档地址、各个运行环境对应的服务地址、接口协议、模型清单（型号、上下文长度、是否支持图片输入）。
- **鉴权方式三选一。** 添加服务商时选“API 密钥”“订阅登录”或“无须鉴权”。产品负责人实际使用时，Kimi 和智谱 GLM 走的是 API 密钥这一种。目录记录本身不带鉴权方式，鉴权方式是在表单里选的。
- **模板速填和自动识别。** 可以从模板选一家服务商，把表单填好；也可以先填服务地址和密钥，由它识别是哪一家。识别不出，或者有多家匹配时，继续按自定义处理。
- **保存前验证。** 可以取服务商的模型清单再挑选，不必手填模型 ID。可以“试连接”，发一个最短的生成请求，并事先提示可能产生少量费用。

它比“让用户在文件里填 key”好在两点：用户只需要选服务商、粘贴 key，不必知道服务地址和模型 ID；保存之前就知道 key 能不能用。

搬到命令行上的做法，已写进规格 §17.1：

| 环节 | 命令行的做法 |
|---|---|
| 选服务商 | 列出目录里的服务商，用户选一家 |
| 粘贴 key | 输入不回显 |
| 服务地址和模型 | 由目录补齐。目录里没有的，用户填服务地址，命令行取模型清单来选 |
| 验证 | 保存前取一次模型清单，并发一个最短的请求试连接，事先说明可能产生少量费用 |
| 保存 | 写成 `AI_API_KEY`、`AI_BASE_URL`、`AI_MODEL` 三个变量，放进凭证环境文件。standalone 方式读取的变量不变 |
| 不能交互时 | agent 调用命令行而找不到 key，命令行把接入命令交给用户自己运行，并以非零退出 |

不借鉴的两处：订阅登录，它与“模型调用只用 standalone”冲突；把凭证存在应用的加密存储里，它与仓库“密钥只通过环境变量配置”的约定冲突。

留到接口设计时定的两处：服务商目录是只随命令行分发，还是也能由服务端下发以便更新；按服务地址自动识别服务商要不要在首期做。

顺带修正 §3.4 的一处说法。Cindy 的目录里有几家的包月编程套餐，例如智谱 GLM Coding Plan、Kimi Code、阿里云百炼 Coding Plan。这类套餐一般也提供 API key，这一点没有逐家核实条款。我们的命令行算不算套餐条款允许的工具，要看各家的条款。
## 5. AGENTS.md 规则（建议稿）

这是准备采用的建议稿。

```markdown
## 账本同步（客户端模式）

本仓库的行为账本由客户端发布，只跟踪一个分支：有远端时是默认分支，没有远端时是首次发布时登记的分支。

- 出现以下任一情况时，先问我是否同步账本：你把提交成功推送到默认分支之后；你通过 MCP 读账本，freshness 显示默认分支领先于账本。
- 不要把 feature branch 的推送当作默认分支更新。
- 需要全量重同步时，先说明原因和代价，等我决定。
- 我说过“以后不用问”之后，把这条许可记进本机的仓库配置，之后不再询问。
- 发现没有配置模型时，把接入命令给我（选服务商、粘贴 API key），让我自己运行。不要让我把 key 贴进对话，也不要把它写进仓库里的任何文件。
```

## 7. 对规格的影响：已并入的部分

产品负责人定下七条之后，下面的改动已经写进《客户端增量分析与 Delta Merge Contract 设计》，记录在那份规格的 §24.7。这次修订还没有经过外部评审。

| 规格位置 | 改动 |
|---|---|
| §7 | 状态判定补全：本地落后于账本是空操作；本地缺 base 时不自动转全量，fetch 也补不齐时由用户确认后显式全量。补判定顺序、fetch 约束和上传前的复查；目标提交由命令行在本地读取；支持没有远端的仓库；默认分支不写死 |
| §16.2、§16.3 | 仓库绑定不再要求有远端，也不要求远端是 GitHub；完全本地的仓库也能用客户端模式，跟踪分支在首次发布时登记。规格里“密钥不落盘”一句改为允许仓库之外的凭证环境文件 |
| §17 | 新增 §17.1：发布由 agent 在推送后和读账本发现落后时询问；自动发布的许可只记在本机；没有专门的确认机制；模型调用只用 standalone，并写明 key 的查找顺序和接入步骤；CI 延后支持；新鲜度只比提交号；只导入没连账号的用户提示连接账号；平台分阶段 |
| §14、§17、§20、§22、§23 | 远端观察值机制移出首期范围，原文保留在规格附录 A |
| §18、§19.1、§24.2 | 失败处理与验收用例相应增删；新增两条，记录并入时的默认和随后的确认 |

并入时另外补严了四处。它们不在七条决定里，是并入时定的默认，列在规格 §24.2 第 12、13 条。其中凭证环境文件、没有远端时登记跟踪分支两项，产品负责人随后已确认：

- 状态表里几行会同时成立，例如本地既落后于远端又落后于账本。规格写了固定的判定顺序，先命中的一行决定处理方式。
- 本地缺 base 时如果 fetch 也补不齐，例如远端被改写、本地是改写之后的新克隆，只提示“更新本地”会让产品卡住。改为不自动转全量重同步，由用户确认后显式执行。
- “取远端默认分支的最新提交”原来没说由谁取。改为命令行在本地读远端跟踪引用，这样内部 git 服务器不必等平台适配也能发布。
- 没有远端的仓库没有默认分支可取。改为首次发布时登记当前检出的分支。

产品负责人随后答复了四件事，都已并入规格，记录在规格 §24.7：接入时填写的 key 写进凭证环境文件；用户填写的优先于 agent 工具的凭证；接入步骤借鉴 Cindy 的做法（§4.4）；没有远端的仓库在首次发布时登记当前检出的分支。登录令牌和端点令牌能否当模型凭证，产品负责人不清楚，规格按只认 API key 写。

规格随后做了一次自洽性复查，把这次的修订和规格其余部分、现行代码逐条对了一遍，又改了四处。它们不在七条决定和四条答复里，是按代码事实补的，未经评审，记录在规格 §24.7：

- §16.2 原来写 delta 沿用 Radar“宿主 agent 逐个执行工作单”的分步通道，与“模型调用只用 standalone”冲突。改为两步落盘、可以续跑，那条通道不用于 delta。
- §16.3、§20 原来写“远端地址可选，有就登记”，但表里没有这一列。按现行表结构重写了绑定规则，见 §3.12。
- §17.1 的新鲜度只写了目标态。补上现状和要改的三处，见 §3.6。
- §21 的改动面和红线没有覆盖这次修订新增的文件。已补，并按当日的账本快照重新反查。

远端观察值为什么可以移出：它在这份规格里的作用是让网页端提示“远端已前进”，并处理推送通知乱序带来的歧义。发现账本落后现在由新鲜度承担，网页端可以复用同一个函数按需计算。

移出之前做了核对：`repository_remote_heads` 是规格提出的新表，代码里不存在；规格里引用它的只有 client 模式的 webhook 分支、发布事务收尾的条件删除、模式切换时的一句说明，以及对应的验收用例和决策。托管模式的触发路径不读它。原文保留在规格附录 A，将来如果要在没有代码托管连接的仓库上做网页端提示，可以从那里恢复。

## 8. 收敛状态与待拍板

已定：

- 模型调用机制只用 standalone，命令行用独立配置的 key 直连模型服务商。
- CI 延后支持，首期不做。
- 发布前服务端不查远端，只校验账本基线。
- 自动发布的许可只记在本机，不依赖远端地址；纯本地的仓库也能用。
- 模型 key 的查找扩大到各 harness 的本地凭证，找不到时交互式询问，或请用户填写凭证环境文件。
- 不做专门的确认机制。
- 平台顺序：GitHub 首期，之后 GitLab、Gitee、Gitea，逐个验证后开放。
- 只导入快照、没连托管平台账号的用户，提示连接账号。
- 规格已按以上决定修订。
- 模型 key：用户填写的凭证环境文件优先于 agent 工具的凭证。第一次找不到 agent 工具的凭证时才接入，接入之后以用户填写的为准。
- 接入时填写的 key 写进凭证环境文件。
- 接入步骤借鉴 Cindy：选服务商、粘贴 API key，服务地址和模型由目录补齐，保存前取模型清单并试连接。
- 没有远端的仓库，首次发布时把当前检出的分支登记为跟踪分支。

已经成熟、可以进入规格细化的部分：

| 部分 | 评价 | 下一步 |
|---|---|---|
| 独立命令行，一次性运行 | 合理 | 进入接口设计 |
| 不做常驻服务、watch、TUI | 合理 | 暂不投入 |
| 只跟踪默认分支，不要求有远端 | 合理 | 已写进规格 |
| 只发布已推送的默认分支提交 | 合理 | 已写进规格 |
| 命令行用独立配置的 key 直连模型服务商 | 机制清楚 | 完善凭证查找、配置和安全 |
| AGENTS.md 不构成自动许可，许可只记在本机 | 已定 | 已写进规格 |
| GitHub 首期，其他平台分阶段开放 | 合理 | 按平台的开放条件逐个验收 |
| 私有仓库没连账号时新鲜度不可用 | 可以接受 | 已写进规格 |
| 没有托管平台的仓库用 `client` 行绑定 | 按现行表结构写的默认 | 未经评审，随规格 §24.7 一起评审 |
| 状态矩阵 | 方向正确 | 已写进规格 |

没有结论的一件：

1. **ZCode 的端点令牌、DSH 的登录令牌，能不能让命令行当模型接口用？** 产品负责人的答复是不清楚。它不影响实施：规格按只认 API key 写，这类用户走接入步骤。要有结论，需要平台方答复，或者由产品负责人授权拿令牌做一次最小试调；没有授权不做。

## 附录：讨论中核实的数据

没有人直接统计过“由 agent 执行推送”的比例，GitHub 也不公布默认分支上直接推送的来源。查到的是相邻的数据。它们说明 agent 参与开发的趋势，不能直接证明“agent 推送后自动同步”应当成为默认触发时机。产品方向不依据这组数据调整。

| 数据 | 出处与口径 | 局限 |

| agent 自己开的 PR，多数行业不到 3% | 同上，按行业统计，只算可识别的 agent | 官方说明这是下界 |
| 在工作中使用 AI agent 的约 31%，近 38% 不打算用 | [Stack Overflow 开发者调查 2025](https://survey.stackoverflow.co/2025/ai)。题目是“Are you using AI agents in your work (development or otherwise)?”：每天 14.1%，每周 9%，每月或更少 7.8% | 是“使用 agent”，不是由 agent 执行 Git 操作 |

| 约 47% 的代码由 agent 完整写出 | [JetBrains Research 2026](https://blog.jetbrains.com/research/2026/08/how-much-code-do-developers-really-let-agents-write)，1.5 万名开发者，2026 年 5 至 7 月 | 自我报告 |

本仓库的样本：近 90 天 `main` 上有 693 个提交，其中只有 2 个是合并提交，带 agent 署名的有 15 个。这只是本仓库的观察，不是对 agent 推送比例的估计。
