# 客户端分析修订：全量 + 增量、零源码外传、提案式合并

日期：2026-11-26  
状态：**待产品负责人终审，未开工。** 本文取代 `2026-11-24-client-incremental-analysis-design.md`（下称「原规格」）里与它冲突的部分；逐节的去留见 §7。  
依据：产品负责人 2026-11-26 的方向与五条决定（§1.3）。文中标注「我的默认」的地方是我补的设计，未经评审。

## 1. 为什么修订

### 1.1 目的

客户端分析是给人类租户的产品能力，不做给 coding agent 用。它要达成三件事：

1. **多租户环境下减少服务端的模型成本。**
2. **降低租户对「你们读得到产品源代码」的顾虑。**
3. **分析在客户端跑，分析期间服务端可以照常更新。**

全量分析和增量分析都要做。

### 1.2 原规格的前提变了

| 原规格的前提 | 现在的事实 |
|---|---|
| 只设计增量；首分析沿用雷达快照，并把它当作「已能在本地完成全量」 | 雷达快照导入只是草稿：不写规格版本、发布和分析记录，没有历史也接不上增量（`lib/snapshot-import.ts:256-275`） |
| 雷达快照可以原样上传 | 快照的 `evidenceSnippets[].lines[].text` 是真实源码行，每条最多 80 行，总量可达 2,000,000 字节（`lib/snapshot/report-data.ts:22-25`） |
| diff 文本随 delta 上传，只作当次校验、不保存（原规格 §10.3 末段） | 与目的 2 冲突，产品负责人决定改为完全不上传 |
| 客户端交「操作 + 校验」，服务端用 diff 重算直接影响（原规格 §8.4、§9） | 改为客户端交提案，服务端用现有的合并逻辑处理 |
| 客户端模式下流程图不出（原规格 §15） | 流程图生成不读源码，只用了功能名、摘要、场景文本和证据路径（`lib/feature-flow-generation.ts:6-15`），可以搬到客户端；它占服务端模型开销的 15.6%，不搬就没达成目的 1 |

### 1.3 产品负责人的决定（2026-11-26）

1. **隐私口径**：完全不上传任何源码文本。服务端只按文件路径做保守核验，精确的影响判断和行号重映射由客户端算。
2. **合并方式**：客户端交提案，服务端用现有的合并逻辑处理。原规格的操作式契约修订。
3. **CI 触发**：放到增量分析做完之后。
4. **客户端形态**：先做 Node 单文件，但要有地方填模型 API Key。自包含可执行文件放到最后。
5. **计费**：本地分析不扣 SAU。

## 2. 目标与非目标

**目标**

- 全量：客户端产出的账本与服务端托管分析同一提交的账本对等，且上传内容里没有任何源码文本。
- 增量：只分析受影响的范围；人工编辑、墓碑、身份的规则与托管分析完全一致。
- 服务端对本地分析的产品不调用模型、不读源码、不扣 SAU。
- 本地分析的产品在分析、上传期间不阻塞服务端部署。
- 账本如实披露「由租户的本地分析产出，未经服务端核验」。

**非目标**

- 不改托管分析的行为。
- 不做常驻进程、文件监听。
- 首期不做 CI，不做自包含可执行文件，不支持多实例部署。
- 不把现有的托管产品迁到本地分析。

## 3. 现状事实（2026-11-26 核对，行号对应 main `5594e60`）

**服务端成本构成**（生产库近 14 天，合计约 1.735 亿 token）

| 调用 | 占比 | 要不要读源码 |
|---|---|---|
| 分析内的提取 | 83.9% | 要 |
| 流程图生成 | 15.6% | 不要 |
| 理解层、发布稿、反馈裁决、规格问答 | 约 0.4% | 不要 |

**服务端分析管线**

- 在 Next.js 进程内跑（`after()`），没有独立 worker；部署重启时在跑的分析会被重排（`lib/analysis-recovery.ts:42-48`）。这是「分析期间不能部署」的根因。
- 调模型的步骤：逐分区提取（`lib/analysis.ts:591-631`）、收敛轮（`:636-666`，只在多分区、全量且轮数大于 1 时进入）、行为面枚举（`:670-689`）；落库之后还有流程图、理解层、发布稿。
- **收敛轮在生产上默认不跑**：`ANALYSIS_CONVERGENCE_ROUNDS` 未配置，默认 1（`lib/env.ts:57-62`；生产容器里没有这一项）。所以「对等」不需要搬收敛轮，需要搬的是行为面枚举。
- 行为面枚举默认开启，每组 6 个文件、最多 8 组（`lib/env.ts:82-93`）。
- 落库走 `saveResult`（`lib/analysis.ts:237-306`）一个事务，核心是 `insertSpecVersion`（`lib/spec-versions.ts:420-514`）。

**合并入口需要什么**

- `saveResult` 的输入里，模型输出 `result` 就是提案；`change` 是变更上下文；`affectedKeys` 是受影响功能；`coverage` 是覆盖率回执。
- `insertSpecVersion` 的各步里，**只有 `preserveUnchangedEvidence` 需要 diff**（`lib/spec-diff.ts:982-1036`），而且它用的只是两样东西：
  - 含行为变更的文件路径集合 `behavioralChangePaths`；
  - 每个文件改动的行号区间 `changedHunksByPath`（判断旧锚点有没有落进改动、把没被改到的锚点挪到新行号）。
- 这两样今天都是从补丁文本算出来的（`behavioralChangePaths`，`lib/patch-scan.ts:105-122`；`parsePatchHunks`，`lib/analysis.ts:256`）。它们本身不含源码文本：一个是路径集合，一个是行号。
- 首次写入时没有上一版：`diffSpec(null, …)` 返回空，提案按原样写入，人工条目照常合并，墓碑照常生效。
- `spec_versions.analysis_run_id` 非空且唯一（`migrations/002_spec_versions.sql:5,8,13`），所以每次写入都要有一行 `analysis_runs`；启动恢复会把 `running` 的 run 重排成托管分析。
- 「哪些功能的证据文件被改了」服务端只凭路径就能算（`loadAffectedFeatureKeys`，`lib/spec-file-index.ts:53-67`）。

**客户端现有的东西**

- `snapshot.cjs` 由 `scripts/snapshot.ts` 打包，复用服务端的切片、提取、合并、覆盖率模块；工作流的注入点在 `lib/snapshot/workflow.ts:31-105`，本地 git 后端在 `lib/snapshot/git-backend.ts:79-104`。
- 现有客户端全量比服务端少行为面枚举，也没有变更窗口（`change.files` 恒为空，`lib/snapshot/workflow.ts:50-55`）。
- 行为面枚举搬到客户端要改四处：它从 `./analysis` 导入 `sanitizeEvidence` 形成循环依赖（实际定义在 `lib/extraction-pass.ts:15`）；组大小和组数读环境变量；`billing` 必填；`analyzeBehavioralGroup` 没有模型客户端注入口（`lib/ai.ts:730-750`）。
- 流程图生成模块没有数据库依赖，运行时只依赖 `lib/ai.ts` 的请求函数（`lib/feature-flow-generation.ts:1,66,77`）；校验器 `validateFeatureFlowGraph` 是纯函数（`lib/semantic-feature-flow.ts:104-166`）；场景指纹只依赖 `node:crypto`（`:53-64`），客户端能算出同样的值。
- 凭证：`--env-file` 已支持注释和引号，只取 `AI_BASE_URL`、`AI_API_KEY`、`AI_MODEL`，进程环境优先（`scripts/snapshot.ts:200-206`）；没有固定的凭证文件路径；上传用的地址和 key 只读进程环境（`:264-265`）。

## 4. 总体设计

### 4.1 一句话

**客户端跑所有要读源码或要调模型的步骤，把结果作为「提案」交给服务端；服务端不读源码、不调模型，用现有的合并逻辑落成规格版本和发布。**

```text
客户端（租户的机器，租户的模型 key）                 服务端
──────────────────────────────────────            ──────────────────────────────
取基线（增量时）            ◀────────────────────  当前规格、契约版本
本地 git：固定提交、算 diff、分类、hunk 行号
切片规划 → 逐分区提取 → 行为面枚举
确定性合并 → 覆盖率回执 → 流程图 → 理解层
组装提案（无源码文本）      ────────────────────▶  校验 → 保守核验 → saveResult
                                                 → 规格版本、发布、索引、通知
打印结果和产品页链接        ◀────────────────────  合并回执
```

### 4.2 隐私边界

**允许上传的**（都是模型产出的描述性文本或结构化数据）

- 功能名、摘要；场景的情境、操作、结果、类别、步骤。
- 证据锚点：仓库相对路径和行号。
- 变更窗口的元数据：前后提交号、提交标题、提交时间、分支；变更文件的路径、状态（新增、修改、删除、改名及原路径）；每个文件的 hunk 行号区间；每个文件是否含行为变更的判定。
- 覆盖率回执里的数字、模型名、契约版本、规则版本。
- 流程图候选（节点和边的文本标签，引用场景编号）、理解层候选（名称和摘要）。

**不得上传的**

- 任何文件的源码行或代码摘录。现有快照的 `evidenceSnippets` 整个去掉；本地生成的 `radar.html` 仍然带摘录，只留在本机。
- diff 的补丁文本。
- 本机的绝对路径、用户名、模型 API Key。

**怎么保证**

- 提案的 schema 里没有能承载源码的字段；带了 `evidenceSnippets` 或补丁文本的产物直接拒绝。
- 客户端上传前自检：从本次读过的源码文件里随机抽 200 行（长度不少于 20 个字符的行），在序列化后的载荷里搜索，命中就中止并报出文件路径。
- 金丝雀断言（沿用原规格 §10.4 的做法）：在一个带唯一标记串的仓库上跑完整条链，断言服务端收到的请求体、落库的数据、日志和错误回执里都没有这个标记串。
- 现有的 `/api/products/import-snapshot` 在本修订上线后拒绝带摘录的 1.0.0 快照，返回明确的升级提示。已发布的雷达 skill 版本会收到这个错误。〔我的默认〕

### 4.3 提案契约

全量和增量共用一个形状。`proposal` 字段与服务端模型输出的结构相同（`lib/ai.ts:29-54`），这是「服务端用现有合并逻辑」的前提。

```jsonc
{
  "contractVersion": "2.0.0",
  "artifactKind": "codelphi-analysis-proposal",
  "mode": "full",                         // full | incremental
  "repository": { "provider": "github", "owner": "...", "name": "...", "defaultBranch": "main" },
  "revision": { "sha": "...", "treeSha": "...", "committedAt": "...", "title": "...", "branch": "..." },
  "base": { "specVersionId": 332, "sha": "..." },          // 增量必填
  "window": {                                              // 增量必填；全量为空
    "files": [
      { "path": "lib/a.ts", "status": "modified", "behavioral": true,
        "hunks": [ { "oldStart": 10, "oldLines": 3, "newStart": 12, "newLines": 4 } ] }
    ],
    "analyzedPaths": ["lib/a.ts"],        // 实际交给模型的工作单范围
    "skipped": [ { "path": "README.md", "reason": "documentation" } ],
    "affectedFeatureKeys": ["..."],       // 客户端按基线算的受影响功能
    "fallbackReason": null                // 增量退回全量时的原因
  },
  "proposal": { "product": {}, "release": {}, "features": [], "changes": [] },
  "coverage": {},                          // 客户端算的覆盖率回执
  "flows": [ { "featureStableKey": "...", "fingerprint": "...", "graph": {} } ],
  "presentation": {},
  "client": { "version": "...", "model": "...", "impactRulesVersion": "impact-v1" }
}
```

- `provider` 取 `github | gitlab | gitee | gitea | client`。没有远端的仓库用 `client`。
- `window.files[].hunks` 只有行号，没有文本。它和服务端今天从补丁解析出来的 `PatchHunk` 同形。
- 规模：CoDelphi 这个量级的产品约 8,000 条场景，载荷几 MB，沿用 4MB 分块上传。

### 4.4 服务端合并

复用 `saveResult`，需要三处小改动。不传新入参时，托管分析的行为逐字节不变。

1. **合并入口接受两个预算好的输入**：`behavioralChangePaths` 和 `changedHunksByPath`。托管分析照旧从补丁算；本地分析的提案直接带。
2. **不预留、不扣费的 run 行**：上传时创建一行 `analysis_runs`，`trigger_type` 用一个新值 `client_upload`，不经过计费的入队。这一列是 `VARCHAR(16)`（`migrations/001_initial.sql:34`），新值 13 个字符，不需要迁移。
3. **恢复逻辑跳过它**：启动恢复和每 10 分钟的补跑都不认领 `client_upload` 的 run，否则一次恰好在部署时到达的上传会被拿去跑托管分析。

合并前的校验，服务端不读源码也能做的：

| 校验 | 做法 |
|---|---|
| 契约 | `contractVersion` 在支持的范围内；严格 schema、长度和枚举；路径必须是仓库相对路径 |
| 绑定 | 提案里的仓库与产品绑定的仓库一致；没有绑定时按 `provider`/`owner`/`name` 确定，规则沿用原规格 §16.3 |
| 基线 | `base.specVersionId` 仍是当前版本，否则返回 `base_changed` 和已成功的版本号，客户端重新取基线 |
| 幂等 | 同一仓库同一 `revision.sha` 已发布过，直接返回原来的回执 |
| 完整性（增量） | 变更文件分成「已分析」和「有确定性跳过理由」两堆，并集必须覆盖全部变更文件 |
| 影响面（增量） | 服务端用文件索引和变更路径算出受影响功能，它必须是「提案里重新分析的功能 ∪ 客户端声明沿用并给了理由的功能」的子集，否则拒绝并返回 `coverage_incomplete` |
| 可引用集 | 沿用原规格 §10.3 的规则。这些规则只看路径，不看内容 |
| 其余 | 现有的坍缩护栏、可见性冲突、身份劫持门禁照常生效 |

合并后照常做：身份分配、墓碑、人工条目优先、变体折叠、不确定消失的保留、文件索引重建、漂移标记、发布、回归任务、确定性通知。这些都不调模型。

### 4.5 服务端核验不了什么

下面这些只能是客户端声明的，在回执里统一标 `clientDeclared`，产品页如实披露：

- hunk 行号是否属实、行为变更的判定是否正确、覆盖率数字、文件是否真的被读过。

原规格 §8.4「服务端用 diff 独立重算直接影响」由此改为 §4.4 的路径级保守核验。代价是：影响面按文件算而不是按行算，被划进来的功能会多一些，客户端多花一些自己的模型用量。

## 5. 客户端

### 5.1 形态与命令

Node 22 单文件 `snapshot.cjs`，打包方式不变。

| 命令 | 作用 |
|---|---|
| `node snapshot.cjs config` | 接入：填服务端地址和上传 key、填模型凭证并试连接，保存到凭证文件 |
| `node snapshot.cjs publish <repo> --slug … [--workdir …] [--language zh-CN\|en] [--full] [--dry-run]` | 判定状态、分析、上传、打印合并回执和产品页链接。`--language` 的约束沿用原规格 §16.2 |
| `node snapshot.cjs status <repo>` | 显示绑定、账本当前提交、本地是否落后 |

`--prepare`、`--finalize` 分步续跑沿用原规格 §16.2。现有的雷达快照命令（`prepare`、`complete`、`show`、`finalize`）保留。

### 5.2 填模型 API Key 的地方

- **凭证文件**：`~/.config/codelphi/credentials.env`（macOS、Linux），`%APPDATA%\codelphi\credentials.env`（Windows），权限 0600，永远不在仓库里。〔路径是我的默认〕
- **文件里放四项**：`AI_BASE_URL`、`AI_API_KEY`、`AI_MODEL`、`CODELPHI_SERVER_URL` 与 `CODELPHI_SNAPSHOT_KEY`。原来后两项只能从进程环境读，现在一并放进文件，人才不用去设环境变量。〔我的默认〕
- **首次运行 `config`** 逐项询问：服务商（给常见服务商的预设地址，也可以自己填）、API Key（输入不回显）、模型名。保存前先试一次连接；失败就不保存，说明原因。
- **优先级**：进程环境 > `--env-file` > 凭证文件。环境变量的用法对 CI 和老用户不变。
- `AI_TIMEOUT_MS` 这类非密钥配置也能写进凭证文件。现在它只认进程环境（`lib/llm-client.ts:82`），和 SKILL.md 的说明不一致，顺手改掉。

### 5.3 状态判定

在客户端做，判定顺序沿用原规格 §7：

1. 固定目标提交。有远端先 fetch，读不到就报 `remote_unavailable`。
2. 没有基线，或者带了 `--full`：全量。
3. 账本当前提交等于目标提交：空操作。
4. 账本当前提交是目标提交的祖先：增量。
5. 互不为祖先：要求全量，由用户确认。
6. 账本领先于本地：不发布，如实报告。

### 5.4 全量流程

和服务端同一套函数，差别只在注入：

- 切片规划、逐分区提取、确定性合并、覆盖率回执：现有客户端已经这样跑，不变。
- **行为面枚举**：搬过来。改四处依赖（§3），然后和服务端一样对窗口里的行为变更文件做两步提取。
- **流程图**：搬过来。给 `generateFeatureFlowGraph` 加模型客户端入参，导出 `parseContent` 和 `normalizeEmptyLabels`；客户端按自己提交的场景算指纹。
- **理解层**：现有客户端已经生成，照旧作为候选上传。

### 5.5 增量流程

1. 取基线：`GET /api/products/{slug}/analysis-baseline`，拿到当前规格全文（含人工编辑的内容）、当前版本号、契约版本。不含任何源码。
2. 本地算 diff：`git diff --unified=0` 解析成 hunk 行号；用 `behavioralChangePaths` 在本地做行为判定。补丁文本不出本机。
3. 算受影响功能：基线里的证据路径与变更路径取交集。
4. 放行判定与托管分析相同（`lib/incremental.ts:17-24`）：diff 不超过 200 个文件、受影响占比不超过 60%、有上一版、受影响集非空。不满足就退回全量，并带上原因。
5. 切片规划只装必选路径（`requiredPaths` = 变更路径 + 受影响证据路径），提示词带增量范围段和上一版措辞锚。
6. 行为面枚举，只针对含行为变更的文件。
7. 合并、覆盖率回执；只为变动的功能生成流程图。
8. 上传。服务端返回 `base_changed` 时回到第 1 步，不重新分析已经完成的工作单。

零行为变更的窗口不调模型，直接上传空提案，由服务端沿用上一版。

### 5.6 上传

`POST /api/products/{slug}/analysis-proposals`，沿用 4MB 分块协议和 `snapshot_write` 权限的 key。分块组装仍在单实例内存里：载荷里已经没有源码，日后要落盘或上对象存储不再有隐私障碍，但首期不做。上传中途服务端重启，整包从第 0 片重传，已完成的提取不重做。

## 6. 服务端的其余规则

**落库之后**

- 理解层：保存客户端候选，通过现有的校验，记为 `client_generated`，人工内容优先。现在的导入把它的 `spec_version_id` 写成 NULL（`lib/snapshot-import.ts:318-333`），改为跟随版本。
- 流程图：用 `validateFeatureFlowGraph` 对合并后落库的场景校验，通过才存。校验不过的不在服务端重生成，记为不可用并写原因。合并后场景与客户端看到的不一致（有人工编辑）时会落到这一步。
- 发布稿润色、发布变化投影改写：不做，用确定性的版本。
- 完整性账本：写入，没有执行的维度如实记未执行。

**计费**

不预留、不扣 SAU、不产生服务端的模型调用回执。经本地分析首次建产品时的赠送，与一次性导入同口径（原规格 §16.3）。

**披露**

产品页、规格页和导出里标明「由租户的本地分析产出，模型是 X，未经服务端核验」。工作台的来源用一个新的 `source` 值，和 `generated` 同属自动条目；版本层两张表的 `source` 列要先加宽（原规格 §20 已列）。

**可更新性（目的 3）**

- 分析不在服务端，上传只有一个短事务，所以本地分析的产品不再受「在途分析不能部署」的约束。托管产品不变。
- **契约版本兼容**：一次全量分析可能跑几十分钟，期间服务端可能更新。服务端同时接受当前版本和上一个版本的提案；再旧的返回 `contract_version_mismatch` 和最低支持版本，客户端提示升级。〔我的默认〕

**分析方式**

产品多一项设置：托管或本地。默认托管。切到本地后，这个产品的 webhook 不再触发托管分析。〔我的默认〕

## 8. 分期与验收

每期做完都要跑 `npm run typecheck`、`npm test`、`npm run build`。

### 第 1 期：客户端全量分析

内容：契约 2.0.0 与隐私边界（§4.2、§4.3）；新端点和 `saveResult` 的三处改动（§4.4）；搬行为面枚举和流程图（§5.4）；仓库绑定支持任何远端和纯本地仓库；同一仓库的新提交写成新版本，不再生成第二个产品；`config` 命令和凭证文件（§5.2）；旧导入端点拒绝带摘录的快照。

验收：

1. **对等**：在同一冻结样本的同一提交上，用同一个模型分别跑客户端全量和服务端托管全量。两者的场景重合度不低于服务端自己跑两次的重合度（之前实测的复现带是 40–52%）。
2. **隐私**：金丝雀断言通过；抓取的上传请求体里没有样本里的源码行。
3. **成本**：这个产品的服务端模型调用回执为 0。
4. **页面**：产品页的各个面（行为清单、理解层、流程图、证据链接）都能打开，并带来源披露。
5. **零回归**：托管分析的现有测试一个不改、全部通过；`insertSpecVersion` 按下标断言的测试不改。

### 第 2 期：客户端增量分析

内容：基线端点；客户端的增量流程（§5.5）；服务端的完整性与影响面核验（§4.4）；`base_changed` 的重取。

验收：

1. 可用率试验的口径在真实仓库上复测：增量窗口的占比不低于原规格 §22.1 的门槛（70% / 50%）。
2. 零行为变更的窗口不调模型。
3. 人工条目不被覆盖、墓碑不复活、身份连续：用冻结的真实窗口重放，结果与托管分析同一窗口的结果逐项相同。
4. 漏报拒绝：构造一个少分析了一个受影响功能的提案，服务端必须拒绝。

### 第 3 期：可更新性与运维

内容：恢复逻辑跳过 `client_upload`；契约版本兼容策略；产品级的「分析方式」设置；上传限流与监控；合并回执在产品页可见。

验收：上传途中部署一次，客户端重传后成功，且没有产生任何托管分析；用上一个契约版本的客户端上传，被接受；用更早的，收到明确的升级提示。

### 第 4 期：接入体验与 CI

内容：安装与文档、设置页的「本地分析」引导、CI 集成（GitHub Actions 优先）、自包含可执行文件。

## 10. 我补的设计默认（未经评审）

1. 凭证文件的路径，以及把上传用的地址和 key 一并放进去。
2. 旧的快照导入端点在第 1 期切换为拒绝带摘录的快照。另一个选择是继续接受，但那样「不上传源码」就不是硬约束。
3. 流程图在客户端生成。另一个选择是留在服务端（没有隐私问题，但占 15.6% 的服务端开销）。
4. `provider` 的取值，以及没有远端时用 `client`。
5. 服务端同时接受当前和上一个契约版本。
6. 「分析方式」是产品级设置，默认托管。
7. 合并后场景与客户端不一致时，流程图记为不可用，不在服务端重生成。
8. 提案上传前客户端抽样自检 200 行。
