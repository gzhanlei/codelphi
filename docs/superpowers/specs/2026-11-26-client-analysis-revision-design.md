# 客户端分析修订：全量 + 增量、不传源码与补丁、提案式合并

日期：2026-11-26（第三版，按同日复审意见修订）  
状态：**已开工。第 1 期的代码已在本地分支 `feat/client-analysis-p1` 写完并提交，没有推送、没有部署；实测数字、与本文字面不一致的地方、验收进度见 §13（2026-11-27）。** 本文取代 `2026-11-24-client-incremental-analysis-design.md`（下称「原规格」）里与它冲突的部分；逐节的去留见 §7。两轮评审意见的逐条处理见 §12。  
依据：产品负责人 2026-11-26 的方向与五条决定（§1.3）。文中标注「我的默认」的地方是我补的设计，未经评审。

## 1. 为什么修订

### 1.1 目的

客户端分析是给人类租户的产品能力，不做给 coding agent 用。它要达成三件事：

1. **多租户环境下减少服务端的模型成本。**
2. **降低租户对「你们读得到产品源代码」的顾虑。**
3. **分析在客户端跑，分析期间服务端可以照常更新。**

全量分析和增量分析都要做。

### 1.2 原规格的前提变了

| 原规格的前提 | 现在的事实 |
|---|---|
| 只设计增量；首分析沿用雷达快照，并把它当作「已能在本地完成全量」 | 雷达快照导入只是草稿：不写规格版本、发布和分析记录，没有历史也接不上增量（`lib/snapshot-import.ts:256-275`） |
| 雷达快照可以原样上传 | 快照的 `evidenceSnippets[].lines[].text` 是真实源码行，每条最多 80 行，总量可达 2,000,000 字节（`lib/snapshot/report-data.ts:22-25`） |
| diff 文本随 delta 上传，只作当次校验、不保存（原规格 §10.3 末段） | 与目的 2 冲突，产品负责人决定改为完全不上传 |
| 客户端交「操作 + 校验」，服务端用 diff 重算直接影响（原规格 §8.4、§9） | 改为客户端交提案，服务端用现有的合并逻辑处理 |
| 客户端模式下流程图不出（原规格 §15） | 流程图生成不读源码，只用了功能名、摘要、场景文本和证据路径（`lib/feature-flow-generation.ts:6-15`），可以搬到客户端；它占服务端模型开销的 15.6%，不搬就没达成目的 1 |

### 1.3 产品负责人的决定（2026-11-26）

1. **隐私口径**：完全不上传任何源码文本。服务端只按文件路径做保守核验，精确的影响判断和行号重映射由客户端算。
2. **合并方式**：客户端交提案，服务端用现有的合并逻辑处理。原规格的操作式契约修订。
3. **CI 触发**：放到增量分析做完之后。
4. **客户端形态**：先做 Node 单文件，但要有地方填模型 API Key。自包含可执行文件放到最后。
5. **本地分析**：不扣 SAU。

### 1.4 评审结论（2026-11-26）与这一版改了什么

评审认可架构方向、分期顺序和「租户自己的模型 Key」，但不批准开工，指出五个核心问题和六个要补充的问题。第二版只修订了这些契约，不扩大范围。下表「本文的处理」一栏按第三版的内容更新过：

|---|---|---|

| P0-2 | 增量核验有漏洞：客户端给个理由就能沿用 | §4.5 重写：功能分三类、沿用声明要与所报 hunk 自洽、质量承诺、验收改写 |
| P0-3 | `base_changed` 后不重新分析会用到过期基线 | §4.6：两种结果、三层处理、谁来判断 |

贯穿实现的一条原则（评审原话的意思）：**服务端可以把客户端的提案当作输入，但不能把客户端声明的事实升级成服务端已验证的事实。**

**复审（针对第二版）的结论**：架构方向通过，尚有少量契约问题，修订后可以批准第 1 期实施；不扩大讨论范围，不重新讨论架构。第三版只改下面这些：

| P1-2 | 只靠隔离级别不能让两次发布串行 | §4.6：按仓库加行锁；并发验收 |
| P1-3 | 提案里缺仓库身份 | §4.3、§6：`{ repositoryId, provider, host, owner, name }`；首次绑定、拷贝与重建的处理 |

| 3.2 | `config` 没定义全 | §5.2：五项；服务端地址和上传 key 怎么填、怎么验证、怎么改单项 |
| 3.3 | 来源信息没分「服务端确认」和「客户端声明」 | §6：分成两组 |
| 4.1 | 变更文件的路径语义 | §4.3：四种状态一张表 |

## 2. 目标与非目标

**目标**

- 全量：客户端产出的账本与服务端托管分析同一提交的账本对等；上传内容里没有源码文件和补丁（结构上保证），源码摘录和代码块由扫描拦截（尽力，边界见 §4.2）。
- 增量：只分析受影响的范围；人工编辑、墓碑、身份的规则与托管分析完全一致。
- 服务端对本地分析的产品不调用模型、不读源码、不扣 SAU。
- 本地分析的产品在分析、上传期间不阻塞服务端部署。
- 账本如实披露每一版的来源：谁分析的、用什么模型、服务端核验到了哪一层。

**非目标**

- 不改托管分析的行为。本修订里所有触及托管路径的改动，在产品不是本地分析时必须不产生任何差别，并且要有测试证明。
- 不做常驻进程、文件监听。
- 首期不做 CI，不做自包含可执行文件，不支持多实例部署。
- 不把现有的托管产品迁到本地分析。

## 3. 现状事实（2026-11-26 核对，行号对应 main `5594e60`）

**服务端成本构成**（生产库近 14 天，合计约 1.735 亿 token）

| 调用 | 占比 | 要不要读源码 |
|---|---|---|
| 分析内的提取 | 83.9% | 要 |
| 流程图生成 | 15.6% | 不要 |
| 理解层、发布稿、反馈裁决、规格问答 | 约 0.4% | 不要 |

**服务端分析管线**

- 在 Next.js 进程内跑（`after()`），没有独立 worker；部署重启时在跑的分析会被重排（`lib/analysis-recovery.ts:42-48`）。这是「分析期间不能部署」的根因。
- 调模型的步骤：逐分区提取（`lib/analysis.ts:591-631`）、收敛轮（`:636-666`，只在多分区、全量且轮数大于 1 时进入）、行为面枚举（`:670-689`）；落库之后还有流程图、理解层、发布稿。
- **收敛轮在生产上默认不跑**：`ANALYSIS_CONVERGENCE_ROUNDS` 未配置，默认 1（`lib/env.ts:57-62`；生产容器里没有这一项）。所以「对等」不需要搬收敛轮，需要搬的是行为面枚举。
- 行为面枚举默认开启，每组 6 个文件、最多 8 组（`lib/env.ts:81-93`）。
- **服务端只有一个发模型请求的地方**：`lib/ai.ts:540`（`requestStructuredCompletionDetailed`）。`lib/llm-client.ts` 只给命令行用。
- 落库事务提交之后还有三件事，都是尽力而为（`lib/analysis.ts:740-790`）：结算捕获（失败由补扫恢复）、分析通知、发布稿润色。回归任务不是通知，它在落库事务里生成（`upsertRelease`，`:179`）。

**合并入口**

- 落库走 `saveResult`（`lib/analysis.ts:237-306`），在一个事务里完成：判断是不是最新的 run、写产品简介、`insertSpecVersion`（`lib/spec-versions.ts:420-514`）、别名、文件索引重建、漂移标记、覆盖率回执、坍缩检查、工作台投影、发布、把 run 置为成功。
- `saveResult` 的输入里，模型输出 `result` 就是提案；`change` 是变更上下文；`affectedKeys` 是受影响功能；`coverage` 是覆盖率回执。
- `insertSpecVersion` 的各步里，**只有 `preserveUnchangedEvidence` 需要 diff**（`lib/spec-diff.ts:982-1036`），而且它用的只是两样东西：
  - 含行为变更的文件路径集合 `behavioralChangePaths`；
  - 每个文件改动的行号区间 `changedHunksByPath`。`PatchHunk` 是 `{ oldStart, oldCount, newStart, newCount }`（`lib/spec-diff.ts:1039-1044`），纯插入的 `oldCount` 为 0，不与任何锚点相交（`:1061-1066`）。
- 这两样今天都是从补丁文本算出来的（`behavioralChangePaths`，`lib/patch-scan.ts:105-122`；`parsePatchHunks`，`lib/spec-diff.ts:1046-1059`、调用点 `lib/analysis.ts:256`）。它们本身不含源码文本。
- 首次写入时没有上一版：`diffSpec(null, …)` 返回空，提案按原样写入，人工条目照常合并，墓碑照常生效。
- 零行为变更的窗口（托管）：不调模型，把上一版的功能原样当作结果，发布说明写「无行为变化」，覆盖率沿版本链继承，然后照常走 `saveResult` 产生新版本（`lib/analysis.ts:521-547`）。
- 「哪些功能的证据文件被改了」服务端只凭路径就能算（`loadAffectedFeatureKeys`，`lib/spec-file-index.ts:53-67`）。它拿到的路径是窗口里每个文件的 `path`，除了迁移脚本不做别的过滤（`analyzedChangePaths`，`lib/evidence.ts:59-66`）。
- **人工编辑不产生新版本**（第三版更正）。`spec_versions` 只有一个写入点（`lib/spec-versions.ts:504`，在 `insertSpecVersion` 里）；人工编辑的内容在每次落库时按现行规则合并进去（`loadManualSpec`，`:422`）。所以客户端分析期间的人工编辑不会让基线过期。能让基线过期的只有一件事：别的发布者写入了新版本。
- 事务里取基线的 `loadPreviousSpec`（`:238-252`）：给了版本号就按号取那一版，**取不到时返回空、不报错**。所以「它是不是当前版本」要由调用方自己核对（§4.6）。
- `saveResult` 现在没有行锁，也没有显式声明隔离级别。它靠「只有最新的 run 才写入」来排序（`loadLatestRunId`，`lib/analysis.ts:67-71`）。托管分析同一个仓库同时只有一个 run 在跑，这样够用；提案不够（§4.6）。
- 证据锚点的 `startLine`、`endLine` 都可以缺省（`lib/ai.ts:9-16`）。现有合并里，缺 `endLine` 按单行算；缺 `startLine` 而路径有行为变更，就不沿用（`lib/spec-diff.ts:1001-1009`）。

**变更窗口在托管侧怎么来的**

- GitHub：增量用 `compare/{before}...{after}`（三点），首次用 `commits/{after}`（`lib/github.ts:44-51`）。
- 文件项只取 `filename`、`status`、`patch`（`lib/github-source.ts:16-19`）。改名时状态是 `renamed`，路径是新路径，**旧路径被丢掉**。GitLab 相同（`lib/gitlab.ts:109`）。所以托管分析今天对改名的处理是：只有新路径算变更路径，旧路径上的锚点原样沿用。
- 拿不到补丁文本时（二进制、纯改名），托管路径会填一个固定的占位串 `(binary or patch unavailable)` 再往下走（`lib/github-source.ts:109`）。占位串不是空串，这会影响行为判定。能识别注释的语言只有九种扩展名：ts、tsx、js、jsx、mjs、cjs、mts、cts、py（`COMMENT_STYLE_LANGUAGES`，`lib/patch-scan.ts:25`）；其它语言一律算行为变更。
- 用 `main` 上的函数逐个跑过的结果（2026-11-26；§4.3 的表据此填写）：修改且带代码行 → 进；只有注释 → 不进；新增、删除且带补丁 → 进；纯改名且填占位串 → 能识别注释的语言不进，其它进；改名且补丁是空串 → 进；**文本文件修改、补丁填占位串 → 不进**（第三版更正，第二版写成「进」）；删除且拿不到补丁（`patch` 为空值）→ 进。
- 行为变更的判定（`behavioralChangePaths`）分两层：路径层只看实现类证据（测试、文档、基础设施、迁移脚本在这一层排除）；内容层在没有补丁、语言不在能识别注释的名单里、补丁过长或解析不了时一律算行为变更，能识别注释的语言再看有没有代码行。下面的数是 2026-11-26 用 `main` 上的函数逐个跑出来的。

**run、模式与触发入口**

- `spec_versions.analysis_run_id` 非空且唯一（`migrations/002_spec_versions.sql:5,8,13`），所以每次写入都要有一行 `analysis_runs`。`trigger_type` 是 `VARCHAR(16)`（`migrations/001_initial.sql:34`）。
- 启动恢复和每 10 分钟的补跑会把 `running`、`queued` 的 run 拿去跑托管分析（`lib/analysis-recovery.ts:42-48, 100, 138`；`lib/billing/sweep.ts:140`）。
- 托管分析的触发入口：GitHub webhook 入队（`lib/github-webhook.ts:91`）、手动分析和补分析（`queueAnalysis`，`lib/analysis.ts:315-322`；`app/api/products/[slug]/analyze/route.ts:45`、`reanalyze-latest/route.ts:39`）、新建产品（`app/api/products/route.ts:12`）、恢复与补跑。
- 托管分析已经支持对同一提交重新分析：补分析入口用新的 run 重跑最新发布对应的提交（`app/api/products/[slug]/reanalyze-latest/route.ts`）。
- `products.analyze_mode` 这一列现在的含义是「全量还是增量」（`lib/analysis.ts:62, 449`；`migrations/019`、`026`），不能拿来表示「托管还是本地」。

**客户端现有的东西**

## 4. 总体设计

### 4.1 三层结构与一句话

**客户端跑所有要读源码或要调模型的步骤，把结果作为「提案」交给服务端；服务端不读源码、不调模型，用现有的合并逻辑落成规格版本和发布。**

```text
租户本地：分析与提案生产                  CoDelphi 服务端：验证与合并              账本与发布
──────────────────────────────           ──────────────────────────────           ─────────────────────
读源码、本地 git 算 diff 与行号            schema 校验、隐私扫描                       规格版本、流程图、理解层
全量 / 增量提取                            仓库身份与绑定                              发布记录、回归任务
行为面枚举、流程图、理解层                  基线版本校验、幂等                          通知、索引
覆盖率、提案隐私检查                        文件级影响核验、三类功能                    来源披露
                                          身份、人工编辑优先、墓碑、行号重映射
只传结构化提案：不传源码与补丁      ──▶    不调模型、不读源码                   ──▶
```

### 4.2 隐私契约

**语义**

- **禁止上传**：原始源码、源码摘录、diff 补丁及连续代码片段。
- **允许上传**：为表达产品行为所必需的技术标识符（函数名、接口路径、环境变量名、仓库相对路径）和语义描述；结构化的元数据（提交号、文件状态、行号区间、判定结果、计数）。
- **客户端扫描是阻断已知泄漏形式的防护措施，不构成对所有语义泄漏的保证。**

**保证分三级。** 对外只承诺前两级，第二级要带上它的边界：

| 级 | 内容 | 靠什么 | 性质 |
|---|---|---|---|
| 一 | 不上传原始源码文件和 diff 补丁 | 提案的 schema 没有承载它们的字段；本地分析的产品，服务端不拉源码、不调模型（§8 有审计） | **可以保证**：结构上没有通道 |
| 二 | 不上传连续的源码摘录和代码块 | 提示词的硬约束；客户端上传前扫描；服务端复查它做得到的三条规则 | **尽力保证**：拦得住已知的形式，证明不了所有形式 |
| 三 | 不上传任何能推断实现细节的内容 | — | **保证不了，不承诺**。行为描述本身就说明系统做了什么；改写成自然语言的内容和正当的描述分不开，也不应该拦 |

第三级不写进任何对外承诺、页面文案或错误提示。〔分三级是复审的要求；对外的措辞是我的默认〕

**为什么第二级只能尽力**：模型输出是自由文本。schema 分得开「有没有摘录字段」，分不开「语义描述」和「代码片段」。

**上传前扫描**。对载荷里每一个字符串值都扫，包括流程图、理解层、覆盖率和回执说明里的文本，不只是 `proposal` 字段。

| 规则 | 检查什么 | 服务端能不能复查 |
|---|---|---|
| 代码块 | 任一字符串值里出现三反引号围栏 | 能 |
| 整行源码 | 本次分析读过的源码文件里，注释和空行以外、长度不少于 30 个字符的一行，原样出现在某个字符串值里 | 不能（服务端没有源码） |
| 代码片段 | 某个字符串值的一行里，有一段代码结构与某个源码的代码行相同。比对前两边都去掉注释、字符串内容、标识符和数字，只留运算符、括号和关键字；连续 4 个记号里要有比较、赋值或逻辑运算符，还要有引号、方括号、花括号、关键字或第二个运算符 | 不能 |
| 连续片段 | 任一字符串值里，出现连续 3 行或更多以 `;`、`{`、`}` 结尾的非空文本行 | 能 |
| 补丁特征 | 以 `@@ -`、`diff --git`、`+++ b/`、`--- a/` 开头的行 | 能 |

- **「代码片段」是这一版新加的规则，第二级能拦到哪由它决定**。它不看空白，去掉空格和换行的源码照样命中；它不看标识符，变量改名后的近似源码照样命中。
- 它只对上面九种扩展名的文件生效，因为去注释要去得准。其它语言的文件不进这条规则的比对（列入下面的能力边界）。
- 「整行源码」和「代码片段」比的源码行，是本次分析读过的**全部**源码文件，不是抽样的。只比对字符串值，不比对路径、行号这类结构化字段。
- 扫描的规则和实现放在客户端与服务端共用的纯模块里，两边跑同一份代码。〔模块放哪里是我的默认〕

**扫描器的能力边界**（隐私测试集，固定在仓库里；每一类写明必须拦、必须放行，还是已知拦不住）

| 泄漏形式 | 例子 | 要求 |
|---|---|---|
| 整行原样 | `if (connection.status !== "ready") {` | 必须拦 |
| 单行的截取 | `connection.status !== "ready"` | 必须拦 |
| 去掉空白的源码 | `if(connection.status!=="ready"){ …` | 必须拦 |
| 变量改名后的近似源码 | `if (conn.state !== "ready") { …` | 必须拦 |
| 改名后的链式表达式 | `ok = rows.filter((r) => r.enabled).length > 0;` | 必须拦 |
| 只有函数调用的一行 | `saveResult(run, result, change)` | **已知拦不住**。调用签名和「技术标识符」分不开，后者是允许的 |
| 单个短条件 | `len>=3` | **已知拦不住**。运算符太少，和正文分不开 |
| 算术公式 | `alpha*tanh(dense1(x))+beta*tanh(dense2(x))` | **已知拦不住**。只有算术运算符 |
| 九种扩展名以外的语言的源码 | 一个 Go 文件里的一行 | **已知拦不住**。只有「整行源码」那一条规则不分语言 |
| 改写成自然语言 | 「连接状态不是 ready 时抛出 not ready 错误」 | **不拦**，这是允许的行为描述 |
| 跨字段拼接 | 左半句在一个字段，右半句在另一个字段 | **已知拦不住**。按字段、按行扫，看不到拼接 |
| 原样引用文案、接口路径、标识符 | `550 we do not accept mail for this domain`、`/agent-mail/pending-attribution` | 必须放行，这是允许的内容 |
| 注释里的文字 | 与源码注释相同的一句话 | 放行，注释行不进比对 |

表里「必须拦」的五类、「必须放行」和「放行」的两类，以及「已知拦不住」里的调用签名、短条件、公式、注释文字，我用一个一百多行的原型在 2026-11-26 逐个跑过，结果与表一致。跨字段拼接和九种扩展名以外的语言没有单独跑：扫描按字段、按行进行，比对又只收那九种扩展名，结构上就不在范围内。原型只说明规则可行，正式实现要有自己的测试，这十三类情形逐个变成用例。

**在真实输出上会误拦多少**（同一个原型）。样本是 AIRecord 的雷达快照：1,024 个功能、4,495 条场景、16,741 个文本字段；比对用的源码行取自快照里带的 5,296 段摘录，共 21,937 行。

| 规则 | 命中的文本字段 | 命中的是什么 |
|---|---|---|
| 按字符比：去空白后连续 24 个字符相同 | 405（2.4%） | 全是误拦：SMTP 应答文案、接口路径、表名。**所以不按字符比** |
| 代码片段（上表的规则） | 8（0.05%） | 3 条是带两个关键字参数的调用签名，2 条是带下标的简写条件，3 条撞上了注释和文档串里的行 |
| 整行源码 | 2 | 1 条是真实的代码行，1 条是引用的预处理指令 |

- 这个数偏小：原型只拿快照里带的源码行建索引，正式实现拿全部源码，命中可能更多。
- 撞上注释的那三条，是因为原型逐行判断注释，没有跟踪跨行的注释块和文档串。正式实现要跟踪。
- **误拦消除不完，而复审已裁定不给放行开关。所以命中的默认处理改为：命中的那一条场景（或那一个流程图）不上传，其余照常。** 客户端列出命中的字段和规则，重扫通过后才上传；回执和产品页上写明剔除了几条。用户可以选中止后调整。命中的内容不会离开本机。〔剔除后继续是我的默认。第二版写的是整份拒绝；按上面的实测，整份拒绝等于几乎每次全量都要重跑〕
- 服务端复查命中时拒绝整份提案，错误码 `artifact_contains_source`，带上规则和字段路径，不带命中的文本。客户端扫过而服务端还命中，说明客户端被改过或版本过旧，不替它剔除。〔服务端扫描是我的默认〕
- 「随机抽 200 行」降为辅助测试，不算隐私保障（评审裁决）。

**金丝雀断言**：在一个带唯一标记串的仓库上跑完整条链，断言标记串不出现在：服务端收到的请求体、每张接收数据的表、流程图、理解层、错误回执、应用日志。上传前扫描的单元测试就是上面的能力边界测试集。

**历史存量**

- 数据库里从来没有存过源码摘录，所以不需要清理存量，备份里也没有可清理的东西。能这么说是因为校验层在写库之前就剥掉了未声明的字段，并且服务端代码没有任何读取它的地方。
- 2026-11-19 那一次导入，源码摘录在请求体里到过服务端，随请求结束丢弃。对外的隐私说明要如实写这一句。
- 证明不了旧容器的日志和服务器以外的副本里没有；隐私说明只承诺「不存储」，不承诺「从未经过」。

**旧客户端迁移**

- 现有的 `/api/products/import-snapshot` 在第 1 期上线时拒绝带摘录的快照。**检查放在 schema 解析之前**（复审 P1-4）：现在的校验链第一步就是 schema 解析，`evidenceSnippets` 不在声明里，解析之后就被剥掉，看不到。所以改为先看原始 JSON 对象的顶层有没有非空的 `evidenceSnippets`，有就拒绝，不看版本号——`evidenceSnippets` 为空数组的快照照旧可以导入。返回 `artifact_contains_source`、`minClientVersion` 和「请升级」的提示，状态码沿用现有的错误映射（409）。
- 旧客户端的请求体仍然会到达服务端。多分片的上传要全部传完才校验，所以摘录会完整地到一次；它们在写任何表之前被拒绝，随请求结束丢弃。对外的隐私说明要如实写这一句。
- 同一次发布里发出新版的雷达 skill。旧版 skill 的本地功能（生成 `radar.html`）不受影响，只是不能再上传带摘录的快照。
- AIRecord 这个由导入产生的草稿，按原规格 §16.3 的路径 B 确定性回填成第一个版本：不调模型，只把已有的草稿行写成规格版本。之后租户想用新的管线重做，再用客户端跑一次全量。

### 4.3 提案契约

全量和增量共用一个形状。`proposal` 字段与服务端模型输出的结构相同（`lib/ai.ts:29-54`），这是「服务端用现有合并逻辑」的前提。

```jsonc
{
  "contractVersion": "2.0.0",
  "artifactKind": "codelphi-analysis-proposal",
  "idempotencyKey": "6f1c…",             // 客户端为每一次上传操作生成的 UUID，重试时沿用
  "proposalHash": "sha256:9d4b…",         // 提案内容的哈希，算法见 §4.6；客户端算，服务端重算
  "mode": "full",                          // full | incremental
  "repository": { "repositoryId": 57, "provider": "github", "host": "github.com", "owner": "…", "name": "…" },
  "revision": { "sha": "...", "treeSha": "...", "committedAt": "...", "title": "...", "branch": "..." },
  "base": { "specVersionId": 332, "sha": "..." },          // 基于已有版本时必填；首次发布为 null
  "window": {                                              // 增量必填；全量为空
    "files": [
      { "path": "lib/a.ts", "previousPath": null, "status": "modified", "behavioral": true,
        "hunks": [ { "oldStart": 10, "oldCount": 3, "newStart": 12, "newCount": 4 } ] }
    ],
    "analyzedPaths": ["lib/a.ts"],        // 实际交给模型的工作单范围
    "skipped": [ { "path": "README.md", "reason": "documentation" } ],
    "affectedFeatureKeys": ["..."]        // 客户端按基线算的受影响功能
  },
  "proposal": { "product": {}, "release": {}, "features": [], "changes": [] },
  "carryClaims": [ { "featureKey": "...", "reason": "anchors_untouched" } ],   // 见 §4.5
  "coverage": {},                          // 客户端算的覆盖率回执，只有整数计数
  "flows": [ { "featureStableKey": "...", "fingerprint": "...", "graph": {} } ],
  "presentation": {},
  "client": { "version": "...", "pipelineVersion": "...", "promptVersion": "...", "model": "...", "impactRulesVersion": "impact-v1" }

```

- `window.files[].hunks` 与服务端的 `PatchHunk` 同形，只有行号。字段名就用 `oldCount`、`newCount`。
- `fallbackReason`（增量退回全量的原因）不再需要：退回全量就按全量上传。
- 规模：CoDelphi 这个量级的产品约 8,000 条场景，载荷几 MB，沿用 4MB 分块上传。
- **数值**（复审 3.1）：契约里所有的数都是整数，schema 用整数约束，不接受小数。比例不上传：覆盖率由服务端用 `implBytesAssembled / implBytesTotal` 算，与客户端现在用的是同一个式子（`lib/analysis-coverage.ts:136`）。这样哈希的规范化不用处理浮点数。〔整数计数是我的做法〕
- **仓库身份**（复审 P1-3）：`repository` 有五个字段，含义、首次绑定和校验见 §6。
- `client` 里的每一项都是客户端的说法，服务端不核对（§6 的来源信息分两组）。

**变更文件的表示与 Git 边界情况**

**路径的语义**（复审 4.1）。每个文件项有 `path`、`previousPath`、`status`（`added | removed | renamed | modified`）：

| 状态 | `path` | `previousPath` | 进不进「变更路径」 |
|---|---|---|---|
| `added` | 新文件的路径 | `null` | 进 |
| `modified` | 文件的当前路径 | `null` | 进 |
| `removed` | **被删文件的路径** | `null` | 进 |
| `renamed` | 新路径 | 旧路径 | 进。只有新路径算，旧路径不算，与托管一致 |

`path` 是文件项的主路径：文件现在在哪，删除时是它原来在哪。所有按路径工作的环节都只用 `path`——服务端算受影响功能、建文件索引、核验沿用声明，客户端算受影响功能。`previousPath` 只用于改名判定和展示。

两个由客户端算出的输入——含行为变更的路径集合、行号区间——按下表得出。判据是把同一份文件清单交给两个入口（托管入口和适配层），结果必须逐项相同（§8 第 1 期的冻结测试集）。

| 情况 | 窗口里怎么表示 | 含行为变更的路径集合（实测） | 行号区间 |
|---|---|---|---|
| 修改，有代码行 | `status: modified`，带补丁 | 进 | 补丁头里的区间 |
| 修改，只有注释或空白 | 同上 | 不进 | 补丁头里的区间 |
| 新增 | `status: added` | 进（实现类路径） | `oldCount` 为 0 |
| 删除 | `status: removed`，`path` 是被删文件的路径 | 进 | 补丁头里的区间，覆盖整个旧文件；`newCount` 为 0 |
| 改名、内容不变、拿不到补丁文本 | `status: renamed`，`previousPath` 为旧路径，补丁填占位串 | 能识别注释的语言不进；其它语言进 | 无 |
| 改名且有改动 | 同上，带真实补丁 | 与「修改」相同 | 新路径上的区间 |
| 二进制文件 | 按实际状态，补丁填占位串 | 进（九种扩展名以外的文件一律算行为变更） | 无 |
| 九种扩展名的文本文件拿不到补丁文本 | 按实际状态，补丁填占位串 | 不进（第三版更正：第二版写成「进」） | 无 |
| 拿不到补丁的文档、测试 | 按实际状态，补丁填占位串 | 不进 | 无 |
| 只改文件模式 | `status: modified`，补丁只有 mode 行 | 能识别注释的语言不进；其它语言进 | 无 |
| 测试文件、迁移脚本、基础设施路径 | 任意 | 不进（在路径层排除） | — |
| 改名检测失败 | 表现为一删一增，按「删除」「新增」两行处理 | 同上 | 同上 |
| 只改大小写 | git 报 `renamed`，同改名 | 同改名 | 同改名 |
| 文件名含特殊字符 | 取路径时用 `-z` 或关闭 `core.quotePath`，载荷里是真实路径 | — | — |
| 窗口跨多个提交 | 三点 diff，与托管的 `compare/{before}...{after}` 一致 | — | — |
| 合并提交 | 三点 diff 从共同祖先起算，合并提交自身不算变更 | — | — |
| 浅克隆缺 base 对象 | 有远端先 fetch；补不齐就不增量，也不自动转全量（原规格 §7） | — | — |

取法：客户端用 `git diff --no-color --unified=0 base...head` 取每个文件的补丁，在本地跑与服务端相同的两个函数（`behavioralChangePaths`、`parsePatchHunks`），把结果填进窗口。**拿不到补丁文本时必须填占位串 `(binary or patch unavailable)`，不能填空串**：实测纯改名的 ts 文件，补丁为空串时进集合，填占位串时不进。删除的文本文件本地总能拿到补丁，不适用占位串。上表每一种情况都在第 1 期的冻结测试集里：同一份文件清单分别交给托管入口和适配层，两个输入逐项相同。

**改名是已知的局限**：旧路径上的锚点在托管分析里就是原样沿用的，链接会指向已经不存在的路径。本修订保持一致，不改这个语义；要改就两种模式一起改，另立工作项。复审的裁决是暂时赞成保持托管的旧语义，不在本次范围。所以旧路径上有锚点的功能不进受影响集合，按「确定性沿用」处理（§4.5）。

### 4.4 适配层与合并入口

客户端提案与合并入口之间有一个独立的适配层，不把映射散落在路由里。〔目录名 `lib/client-proposal/` 是我的默认〕

```text
提案 ──▶ contract.ts（schema） ──▶ scan.ts（隐私扫描） ──▶ verify.ts（§4.5 的核验）
                                                              │
                                                              ▼
                                                   adapt.ts：提案 → saveResult 的输入
                                                   { run, result, change, affectedKeys, coverage,
                                                     precomputed: { behavioralPaths, changedHunksByPath },
                                                     options: { expectedBaseSpecVersionId, provenance } }
                                                              │
                                                              ▼
                                                   saveResultInTransaction(connection, …)
```

合并入口的改动，全部是可选入参，不传时托管路径逐字节不变：

1. **`precomputed`**：`behavioralPaths` 和 `changedHunksByPath`。托管分析照旧从补丁算；提案带现成的。
2. **`options.expectedBaseSpecVersionId`**：事务里读到的当前版本与它不等就回滚，返回 `base_changed`（§4.6）。核对由发布事务做，不交给 `insertSpecVersion`（它取不到指定的版本时返回空，不报错）。版本号本身用 `insertSpecVersion` 已有的 `baseVersionId` 入参传进去（`lib/spec-versions.ts:420`），不新增。
3. **`options.provenance`**：随规格版本写入的来源信息（§6）。
4. **事务体可在外层事务里执行**：把 `saveResult` 的事务体抽成 `saveResultInTransaction(connection, …)`；托管路径仍在自己的事务里调用它，提案路径在发布事务里调用它（§4.6）。

两项证明（第 1 期的验收）：

- 同一份文件清单，适配层算出的两个输入与托管入口从补丁算出的逐项相同，覆盖 §4.3 表里的每一种情况。
- 不传新入参时，托管路径发给数据库的每一条语句和参数与改动前逐字节相同。

### 4.5 服务端核验：能保证什么

**先说质量承诺**

- **保证**：提案覆盖了服务端凭文件路径能识别的全部受影响功能；每一个没有重新分析、证据又落在变更路径上的功能，都带一条与所报行号区间自洽的沿用声明，而且它的锚点不在被删的文件上。
- **不保证**：所报的行号区间属实、行为变更的判定正确、沿用声明在代码层面成立。这些是客户端的判断。

**功能分三类**（取代第一版里「重新分析 ∪ 声明沿用」的两分法）

| 类别 | 判定 | 服务端怎么做 | 回执里怎么标 |
|---|---|---|---|
| `reanalyzed` | 提案里有这个功能 | 接受提案 | 客户端声明 |
| `deterministically_carried` | 证据路径与变更路径没有交集（服务端凭自己的文件索引算） | 现有合并逻辑自动沿用 | 服务端事实 |
| `client_declared_unaffected` | 证据路径与变更路径有交集，提案里没有它，客户端声明「改动没有碰到它的锚点」 | 核对声明与所报行号区间是否自洽，自洽才接受并沿用 | **未经服务端核验** |

**规则**（增量；全量没有这一步）

含行为变更的集合为空时走零行为变更分支（§5.5），不做下面的核验。否则：

1. 服务端算 `A`：当前版本里非人工的、证据路径落在**变更路径**里的功能。变更路径就是窗口里每个文件项的 `path`（迁移脚本除外），与托管算受影响功能用的是同一个函数。旧路径（`previousPath`）不算。
2. 对 `A` 里每个功能 `f`：
   - `f` 在提案里 → `reanalyzed`。
   - 否则客户端必须为 `f` 提交一条 `carryClaims`，理由只能是 `anchors_untouched`。服务端按下面的「锚点有效性」逐个锚点核对，全部有效 → `client_declared_unaffected`。
   - 不满足、没有声明、或者有锚点被判为受影响 → 拒绝，错误码 `coverage_incomplete`，带上功能键和原因（`missing` 或 `anchor_touched`）。
3. 不在 `A` 里的功能由现有合并逻辑沿用，记为 `deterministically_carried`。
4. 提案里有、`A` 里没有的功能照常接受，可引用集的规则不变。
5. `A` 里的人工功能不走这条规则，照现行规则打漂移标记。

**锚点有效性**（复审 P0-2）。一条沿用声明要成立，`f` 的每个非人工场景的每个锚点都必须是「有效」的：

| 锚点的情形 | 判定 | 和合并的关系 |
|---|---|---|
| 路径不在变更路径里 | 有效 | 与合并一致：路径不在含行为变更的集合里就原样沿用（`lib/spec-diff.ts:1001`） |
| 路径在变更路径里，但不在含行为变更的集合里，且文件没有被删除 | 有效 | 与合并一致（同上） |
| **文件被删除**（`status: removed`），不论它的路径在不在含行为变更的集合里 | **一律受影响，不得沿用** | **比合并严**。带真实删除补丁时，区间覆盖整个旧文件，锚点都会相交，合并的结果是对的。但被删的文件如果被判为不含行为变更，合并会原样沿用指向已删文件的锚点。核验不允许这种沿用 |
| 路径在含行为变更的集合里，文件没有区间（二进制，或拿不到补丁） | 受影响 | 与合并一致：没有区间就不沿用（`:1003`） |
| 有区间，锚点没有起始行 | 受影响 | 与合并一致（`:1003`） |
| 有区间，锚点有起始行 | 行范围与任一区间的旧侧范围相交 → 受影响；不相交 → 有效 | 与合并一致（`:1007-1009`） |

两处要写死的细节：

- **锚点的行范围**是 `[startLine, endLine]`；**没有 `endLine` 时是 `[startLine, startLine]`**，按单行算。
- **区间的旧侧范围**是 `[oldStart, oldStart + oldCount - 1]`；**`oldCount` 为 0（纯插入）时是空范围，不与任何锚点相交**。

「被删的文件被判为不含行为变更」只在九种扩展名的文本文件拿不到补丁、填了占位串时发生（§4.3 的表）。本地 `git diff` 对删除的文本文件总能给出补丁，所以客户端实际上碰不到；规则仍然写明，因为核验不能建立在「客户端总会给补丁」的假设上。这一条只看 `status`，不看区间。

**改名**（复审 P0-2，严格跟随托管）：变更路径只有新路径，旧路径不算。所以旧路径上有锚点的功能不进 `A`，属于 `deterministically_carried`；提案里指向新路径的证据按新路径算受影响、建索引。旧路径上的锚点会指向已经不存在的文件，这是托管分析已有的局限（§4.3 末段），本修订不改。

第 2 步的核对只证明声明与所报区间自洽，不证明区间属实。这一点在回执、版本来源和产品页上都写明。

**回执**：每个功能一条，带类别和原因；另给三个类别的计数。产品页的发布说明里列出 `client_declared_unaffected` 的功能，并提示「这些功能是按客户端的判断沿用的，建议优先人工核实」。

**沿用原规格 §10.3 的部分**：可引用集的规则只看路径，不看内容，原样保留。

### 4.6 事务、并发与幂等

**三种身份，不混用**

| 概念 | 是什么 | 存在哪 |
|---|---|---|
| 修订身份 | 仓库的一个代码提交 | `analysis_runs.repository_id` + `after_sha` |
| 提案身份 | 一份具体分析结果的内容 | `analysis_runs.client_proposal_hash`，`(repository_id, client_proposal_hash)` 唯一 |
| 幂等键 | 一次上传操作 | `analysis_runs.client_idempotency_key`，`(repository_id, client_idempotency_key)` 唯一 |

- **同一个幂等键**（网络重试）：返回第一次的回执，不产生新版本。
- **同一份提案内容**（`proposalHash` 相同；复审 3.1 问的「同哈希不同键」）：不论幂等键是否相同，都返回第一次的回执，不产生新版本。客户端换了一个新键重传同一份内容，结果是重放；重新分析同一个提交时模型给出的内容一字不差，也只算重放。哈希覆盖了基线和提交（见下），所以同哈希必然同基线、同提交。〔同哈希即重放是我的默认〕
- **同一个提交不自动等于复用旧结果**。重新分析同一个提交是允许的：`publish --full` 跳过「账本已是这个提交」的空操作判定，做一次带基线的全量分析；内容与上一次不同，就是新版本。
- 不带 `--full` 时，账本当前提交等于目标提交就是空操作，不上传。这是客户端的判定，不是服务端的幂等规则。
- 修订身份、提案哈希、幂等键、基线版本号都记在 run 行上，版本来源里也能查到。

**`proposalHash` 的规范化**（复审 3.1）

- **字段**：`proposalHash` 是载荷里的一个字符串，形如 `sha256:<64 位十六进制>`。客户端算好放进去，服务端重算，不一致就拒绝（`proposal_hash_mismatch`）。
- **覆盖范围**：整个载荷，除了 `idempotencyKey` 和 `proposalHash` 自己。所以基线（`base`）、提交（`revision`）、客户端元数据（`client`）、覆盖率、流程图、理解层都在内。同一份分析结果基于不同的基线，是不同的提案身份。
- **规则**：对象键按 UTF-16 码元升序；没有多余的空白；数组的顺序保留（场景和证据的顺序有语义）；`null` 保留。
- **数值**：载荷里只有整数（§4.3），不涉及浮点数的表示。
- 实现与适配层放在一起。

**发布是一个事务**

下面这些在同一个数据库事务里完成，任何一步失败全部回滚，包括已经插入的 run 行：

1. **锁仓库行**：事务的第一条语句是 `SELECT id FROM repositories WHERE id = ? FOR UPDATE`。同一个仓库的发布由此串行（见下面「并发」）。首次发布时还没有仓库行，改为先锁产品行，再按 §6 建立绑定。
2. 仓库身份与绑定校验（§6）。放在插入 run 行之前：run 行要指向仓库记录，首次发布的仓库记录是在这一步建的。回执丢了的重试也走这条路——它仍然带 `repositoryId: null`，这一步会认出已经绑定的记录，下一步再按幂等键重放。
3. 幂等检查：插入 `analysis_runs` 行（`trigger_type = 'client_upload'`，`status = 'running'`）。幂等键或提案哈希撞上唯一键就回滚，读出原来那次的回执返回。
4. **基线核对**：锁拿到之后再读当前版本，必须等于 `base.specVersionId`；首次发布时账本必须没有版本。不等就抛 `base_changed`，整体回滚。这一步不能交给 `insertSpecVersion`（§3）。
5. 完整性与三类功能的核验（§4.5）。
6. `saveResultInTransaction`：规格版本与来源信息、提交元数据、发布记录、文件索引、工作台投影、覆盖率回执、完整性账本、理解层候选、通过校验的流程图。
7. 把 run 置为成功。

- 因为 run 行的插入和置为成功在同一个事务里，事务外永远看不到 `client_upload` 的 run 处于 `running`。恢复逻辑仍然加上排除，作为第二道防线（§6）。
- run 行的 `account_id` 记上传 key 所属的账户，通知靠它找到收件人。

**并发**（复审 P1-2）

隔离级别本身不会让两次发布串行。所以加行锁，并且规定三条：

1. **同一个仓库的两次发布，不能都基于同一个旧版本成功。** 后到的事务等锁；拿到锁时，先到的那次已经提交，它读到的当前版本与自己的基线不等，返回 `base_changed`。
2. **后到的事务看到的是已提交的最新版本。** 靠的是「锁是事务的第一条语句」：锁定读读的是最新提交的数据，普通读的快照在这之后的第一条普通读时才建立。锁之前不能有任何普通读。
3. **基线过期就整体回滚**，返回 `base_changed`，不留任何写入。两次发布用的是同一个幂等键或同一份提案内容时，后到的按重放处理，不算冲突。

- 隔离级别显式声明，沿用身份层那次的发布事务的决定（`REPEATABLE READ`）。生产库的默认隔离级别是 `READ COMMITTED`（2026-11-26 只读查询），不显式声明就不是这个值。
- 锁仓库行而不是产品行，是因为版本和 run 都按仓库计。〔我的默认〕
- 写库以条件更新为准，不以「先读后写」为准。`saveResult` 把 run 置为成功时带 `AND status = 'running'`，影响行数为 0 就回滚（`lib/analysis.ts:290`），这种写法原样保留。并发验收必须用真实的 MySQL 连接跑：隔离级别和锁的问题，模拟的数据库测不出来。

**事务提交之后会丢什么**（复审 4.2）

事务提交之后只有三件尽力而为的事，与托管相同：结算捕获、分析通知、发布稿润色。发布失败时这些都不会发生。**会丢的只有通知**：

- 分析完成的邮件或 Slack 通知，这一次不发，也不重试。
- 结算捕获对本地分析的产品不产生扣费（§6 计费），实际上没有可丢的。
- 没有流程性的职责挂在通知上：回归任务在事务里生成（`upsertRelease`，`lib/analysis.ts:179`），版本、发布、文件索引、工作台投影也都在事务里。
- 所以第 1 期不做事务性的发件箱，通知失败记日志。〔不做发件箱是我的默认。复审的意见是它不是阻塞项，写明哪些可能丢〕

**`base_changed`：两种结果、三层处理**

事务里发现当前版本不是提案的基线时，回滚并返回：

```jsonc
{ "error": "base_changed",
  "current": { "specVersionId": 333, "revisionSha": "..." },
  "changedFeatureKeys": ["..."],      // 基线版本到当前版本之间，内容有变化的功能
  "verdict": "reusable" }             // reusable | reanalyze
```

- **谁来判断**：服务端。它有两个版本的全部内容，用现有的 `diffSpec` 算出基线到当前版本之间变化的功能。
- **`reanalyze`** 的条件（任一成立）：
  - 当前版本的提交不等于基线的提交，也就是代码也往前走了；
  - 变化过的功能与本次的范围有交集。范围 = 提案里的功能 ∪ 按当前版本重算的受影响功能 `A`。
- **`reusable`**：两个条件都不成立。
- **客户端的处理**，先回到状态判定，再分三层：
  0. **先回到状态判定**（§5.3）：重新取基线。账本当前提交已经等于目标提交、又没带 `--full`，就是空操作，不用再分析。两个人对同一个提交各做了一次全量，就是这种情形。
  1. **确定性重算**（两种结果都做）：重算受影响功能、沿用集合、流程图引用。不调模型。
  2. **兼容性检查**（`reusable`）：原提案不重跑模型，换上新的基线版本号重新上传。服务端会对新基线再做一遍完整的核验，所以这一步不会把依赖了旧内容的提案合并进去。
  3. **重新分析**（`reanalyze`）：只重跑范围里受影响的工作单；`changedFeatureKeys` 之外的工作单不重跑。代码往前走了的，先回到状态判定（§5.3）。
- **不允许的**：把基于旧基线生成的提案不经重算直接合并到新基线。第一版里「回到第 1 步，不重新分析已经完成的工作单」的说法作废。

### 5.2 模型凭证、服务端配置与 Key 的安全

- **凭证文件**：`~/.config/codelphi/credentials.env`（macOS、Linux），`%APPDATA%\codelphi\credentials.env`（Windows）。〔路径是我的默认〕
- **文件里放五项**：`AI_BASE_URL`、`AI_API_KEY`、`AI_MODEL`、`CODELPHI_SERVER_URL`、`CODELPHI_SNAPSHOT_KEY`。〔把上传用的两项也放进来是我的默认；第二版误写成「四项」〕
- **优先级**：进程环境 > `--env-file` > 凭证文件。写进文档，只保留这一种说法。
- **首次运行 `config`** 分两组逐项询问（复审 3.2）：
  1. 服务端：服务地址（默认 `https://codelphi.com`，自建的 CoDelphi 可以改）、上传 key（**关闭终端回显**）。
  2. 模型：服务商（给常见服务商的预设地址，也可以自己填）、API Key（**关闭终端回显**）、模型名。
- **两组保存前各验证一次，验的是真实调用**：
  - 上传 key：调用 `GET /api/client-analysis/context`（新端点，用这把 key 鉴权）。成功时返回组织名、契约版本和这个组织下的产品清单，`config` 显示「已连接到 <组织名>」，让用户确认是对的组织。失败就不保存，说明原因。〔新端点是我的默认；`publish` 也用它核对契约版本、解析产品别名〕
  - 模型：发一个最小的工作单并解析结果，不是只测网络通不通。失败就不保存，说明原因。
- **改单项**：再运行 `config`，列出五项的现状，选要改的那一项，只问那一项，保存前只验证受影响的那一组。非交互时用 `config --set <项>=<值>`；值从标准输入读（`--value-stdin`），免得 Key 留在 shell 历史里。〔逐项参数的形式是我的默认〕
- **告诉用户请求发到哪里**：填 Key 之前明确显示两句话——「模型请求将发送到 <服务商地址>，不经过 CoDelphi 服务端」；「分析提案将上传到 <服务地址>，不含源码文件和补丁」。租户的 Key 可能指向任何兼容服务，不能让人误以为模型调用发生在 CoDelphi。
- **写文件**：先写同目录的临时文件再原子改名；新建的文件权限 0600；文件已存在时不因覆盖而放宽权限；Windows 用当前用户的目录 ACL，不写别的用户的访问权。
- **日志与错误**：任何日志、错误信息、回执里不出现 Key；打印配置时只显示「已设置」。
- `AI_TIMEOUT_MS` 这类非密钥配置也能写进凭证文件。现在它只认进程环境（`lib/llm-client.ts:82`），和 SKILL.md 的说明不一致，顺手改掉。

### 5.3 状态判定

在客户端做，判定顺序沿用原规格 §7。会影响判定的标志只有 `--full`。〔第二版里的 `--reanalyze` 并入 `--full`，是我的默认：按复审列的四个测试，两个标志在每种情形下的结果都一样，没有理由留两个名字〕

| 账本当前提交与目标提交的关系 | 不带标志 | 带 `--full` |
|---|---|---|
| 没有基线 | 全量 | 全量 |
| 相等 | **空操作**，不上传 | 全量（带基线） |
| 当前提交是目标提交的**严格**祖先 | 增量 | 全量（带基线） |
| 互不为祖先 | 要求全量，由用户确认 | 全量 |
| 账本领先于本地 | 不发布，如实报告 | 不发布，如实报告 |

步骤：

1. 固定目标提交。有远端先 fetch，读不到就报 `remote_unavailable`。
2. 取账本当前提交。没有，或者带了 `--full`：全量。
3. 两个提交相等：带了 `--full` 就全量（带基线），否则空操作。
4. 当前提交是目标提交的**严格**祖先（两者不等，且前者是后者的祖先）：增量。
5. 互不为祖先：要求全量，由用户确认。
6. 账本领先于本地：不发布，如实报告。

- 「祖先」一律指严格祖先。一个提交是它自己的祖先，所以第 3 步必须排在第 4 步前面。第二版把「是祖先」直接写成增量，和第 3 步矛盾（复审 P1-1）。
- 第 1 期没有增量。第 4 步在第 1 期落到第 5 步：告诉用户「增量分析还没有提供」，要求带 `--full` 重来，或者中止。第 2 期才启用增量。

四个测试（前三个在第 1 期，第四个在第 2 期）：

| 账本当前提交 | 目标提交 | 标志 | 结果 |
|---|---|---|---|
| X | X | 不带 | 空操作，不发请求 |
| X | X | `--full` | 全量，带基线 X 所在的版本 |
| X | X 的子提交 | `--full` | 全量，带基线 |
| X | X 的子提交 | 不带 | 增量 |

### 5.4 全量流程

和服务端同一套函数，差别只在注入：

- 切片规划、逐分区提取、确定性合并、覆盖率回执：现有客户端已经这样跑，不变。
- **行为面枚举**：搬过来。改四处依赖（§3），然后和服务端一样对窗口里的行为变更文件做两步提取。
- **流程图**：搬过来。给 `generateFeatureFlowGraph` 加模型客户端入参，导出 `parseContent` 和 `normalizeEmptyLabels`；客户端按自己提交的场景算指纹。
- **理解层**：现有客户端已经生成，照旧作为候选上传。
- 所有提示词加上 §4.2 的硬约束，提示词版本号写进提案的 `client.promptVersion`。
- 隐私扫描（§4.2）：对整份提案扫一遍，命中的场景或流程图不上传，其余上传。

### 5.5 增量流程

1. 取基线：`GET /api/products/{slug}/analysis-baseline`，拿到当前规格全文（含人工编辑的内容）、当前版本号、当前提交、契约版本。不含任何源码。
2. 本地算 diff（§4.3 的取法），解析成行号区间；用 `behavioralChangePaths` 在本地做行为判定。补丁文本不出本机。
3. 算受影响功能：基线里的证据路径与变更路径取交集。
4. 放行判定与托管分析相同（`lib/incremental.ts:17-24`）：diff 不超过 200 个文件、受影响占比不超过 60%、有上一版、受影响集非空。不满足就转全量。
5. 切片规划只装必选路径（`requiredPaths` = 变更路径 + 受影响证据路径），提示词带增量范围段和上一版措辞锚。
6. 行为面枚举，只针对含行为变更的文件。
7. 合并、覆盖率回执；只为变动的功能生成流程图。
8. 为没有重新分析、但证据路径落在变更路径里的功能，逐个判断锚点有没有落进改动区间：没落进的生成一条 `anchors_untouched` 的沿用声明；落进了的回到第 5 步把它纳入分析。
9. 隐私扫描；命中的场景或流程图不上传（§4.2）；上传。
10. 服务端返回 `base_changed` 时按 §4.6 处理。

**零行为变更的窗口**

代码从提交 X 变到 Y，但没有行为变更时，客户端不调模型，上传一份增量提案：窗口里的每个文件 `behavioral` 都是 false，`proposal` 为空。服务端走托管的零行为变更分支（`lib/analysis.ts:521-547`）：

- **产生新版本 V+1 和一条发布**。规格内容、身份、证据原样沿用上一版；账本当前提交更新到 Y。
- 发布说明写「无行为变化」；覆盖率沿版本链继承。
- 人工编辑和墓碑保持不变。这一条有专项测试。
- 所以零行为变更的含义是「不产生新的模型分析结果」，不是「不产生版本」。账本不会停在 X，下一次增量从 Y 起算。

### 5.6 上传

`POST /api/products/{slug}/analysis-proposals`，沿用 4MB 分块协议和 `snapshot_write` 权限的 key。分块组装仍在单实例内存里：载荷里没有源码，日后要落盘或上对象存储不再有隐私障碍，但首期不做。上传中途服务端重启，整包从第 0 片重传，幂等键不变，已完成的提取不重做。

**回执**：`{ specVersionId, releaseId, replayed, repositoryId, verification: { reanalyzed, deterministicallyCarried, clientDeclaredUnaffected }, scanDropped, productUrl }`。首次发布的 `repositoryId` 是新分配的，客户端把它和产品别名写进本地 git 配置（§6）。`scanDropped` 是被隐私扫描剔除的条数，它是客户端声明的数。

## 6. 服务端的其余规则

**仓库身份是独立的概念**（评审对默认 4 的补充；复审 P1-3 补了字段）

提案里的 `repository` 有五个字段：

| 字段 | 含义 | 谁定 |
|---|---|---|
| `repositoryId` | 服务端的仓库记录 id。第一次发布时为 `null`，之后每次都带 | 服务端分配 |
| `provider` | `github`、`gitlab`、`gitee`、`gitea`、`local` | 客户端从远端地址判断 |
| `host` | 远端的主机名，小写。`github.com`、`gitlab.com` 这类公共主机和自托管主机一样写；纯本地为 `null` | 客户端 |
| `owner`、`name` | 从远端地址规范化出来的属主和仓库名。纯本地时 `owner` 为 `null`，`name` 是仓库目录名，只作显示 | 客户端 |

- **远端地址的规范化**：去掉协议、用户名和令牌，去掉末尾的 `.git`，主机名小写；自托管地址保留主机名。地址里出现令牌时，令牌不进身份，也不进任何记录。
- **`host` 用来区分自托管实例**：`gitlab.corp.com/team/api` 和 `gitlab.other.com/team/api` 是两个仓库。现在的 `repositories` 表没有主机名列，身份是 `(provider, owner, name)`，所以要加一列可空的 `host`，比对身份时带上它。
- **首次发布建立绑定**（发布事务的第 2 步）。`repositoryId` 为 `null` 时，服务端自己判断该用哪条仓库记录：
  - 有远端的仓库：按 `(provider, owner, name)` 找。找不到就新建。找到了，再看主机名：相同，或者记录里还没有主机名，就绑定到这个产品（一个仓库记录只绑定一个产品）；不同，拒绝，错误码 `repository_identity_conflict`。现有的唯一键不允许同一个 `provider/owner/name` 对应两个主机名，这是已知的局限（§11）。
  - 纯本地仓库：按产品绑定。这个产品还没有仓库记录就新建一个（`provider = local`）；已经有了就用它，不看目录名。
  - 绑定结果随回执返回 `repositoryId`。
- **之后的发布必须带 `repositoryId`**，服务端核对：
  - id 不存在，或者没有绑定到路径里的这个产品：拒绝，`repository_not_bound`。
  - 另外四个字段与记录不一致：拒绝，`repository_mismatch`。记录里还没有 `host` 的，这一次补写。
  - **客户端不能凭一个 `repositoryId` 写到别人的产品上**：鉴权用的是上传 key，key 属于组织，组织必须拥有路径里的产品。
- `provider` 只是身份的一个字段，不代表已经支持那个平台的托管分析。
- 仓库身份、远端地址、产品绑定是三件事，绑定关系显式建立，不从地址推断。

**客户端怎么保存绑定**：`repositoryId` 和产品别名写进本地 git 配置（`git config codelphi.repositoryId …`、`codelphi.productSlug …`），每个克隆各一份，不进提交。

| 本地仓库发生了什么 | 会怎样 |
|---|---|
| 复制整个目录（带着 `.git`） | 配置跟着走，副本指向同一个仓库记录和产品。这是对的：它就是同一个仓库 |
| 从远端重新克隆到另一台机器 | 配置不在，`repositoryId` 为 `null`；服务端按远端身份找到原来的仓库记录，返回同一个 id，账本接得上 |
| 纯本地仓库复制到别处 | 配置跟着走，指向原来的产品 |
| 重新 `git init`，或者 `.git` 损坏后重建 | 历史变了。有远端时身份不变，但账本当前提交多半不在新历史里，落到「互不为祖先」，要求全量并由用户确认（§5.3）。纯本地仓库丢了配置时，按产品找到原来的记录，同样走这条判定 |
| 改了远端地址，迁到另一个主机 | 身份变了，带旧的 `repositoryId` 会被拒绝（`repository_mismatch`）。第 1 期不提供自助的重新绑定；需要的话由运营处理，账本从新记录的第一次全量开始（§11） |

**本地分析与托管的隔离**（评审 P1-2、2.6；全部在第 1 期）

- 新增一列 `products.analysis_executor`，取值 `server | client`，默认 `server`。不复用 `analyze_mode`，它表示的是全量还是增量。〔列名是我的默认〕
- **模式判断放在统一入口**，不散在各个调用方：
  - 入队：`queueAnalysis`、GitHub webhook 的入队，产品是 `client` 时拒绝，错误码 `analysis_mode_is_client`，不创建 run、不预留。
  - 执行：`runAnalysis` 是所有触发最终调用的函数，在认领 run 之前再检查一次；`trigger_type` 是 `client_upload` 的 run 直接标为失败并写原因，不认领。
  - 恢复与补跑：候选查询排除 `client_upload`，并排除产品是 `client` 的 run。这是第二道防线。
- 覆盖的入口：GitHub webhook、手动分析、补分析、新建产品、启动恢复、每 10 分钟的补跑、每日与按次数的定时触发（它也走 `queueAnalysis`，`lib/analysis-trigger.ts:71`）、旧版客户端调用的接口。其它平台今天没有 webhook 接收器，它们的手动和定时触发同样走上面的入口；日后接入 webhook 时必须经过同一个入口。
- 第 1 期是受控试点：没有设置界面，这一列由运营逐个产品在数据库里改。设置界面在第 3 期。

**`client_upload` 的 run 的终态与恢复**

- 只在发布事务里创建，提交时就是 `succeeded`；事务外看不到它的中间状态。
- 失败的发布整体回滚，不留 run 行。
- **结构化的拒绝审计**（复审对「不留失败 run」有条件赞成，要求另有审计）：每次拒绝另写一行 `client_proposal_rejections`，在它自己的小事务里提交，所以不会被发布的回滚带掉。记的只有：时间、组织、产品、仓库 id（有则记）、提交号的前 12 位、提案哈希、错误码、机器可读的细节（例如被拒的功能键，最多 50 个）。隐私扫描的拒绝只记规则和字段路径，不记命中的文本。**不存请求体的任何内容。**保留 90 天。〔表名、条数上限和保留期是我的默认〕

**落库之后**

- 理解层：保存客户端候选，通过现有的校验，记为 `client_generated`，人工内容优先。现在的导入把它的 `spec_version_id` 写成 NULL（`lib/snapshot-import.ts:318-333`），改为跟随版本。
- 流程图：用 `validateFeatureFlowGraph` 对合并后落库的场景校验，通过才存。校验不过的不在服务端重生成，记为不可用并写原因。合并后的场景与客户端看到的不一致（有人工编辑）时会落到这一步。
- 发布稿润色、发布变化投影改写：不做，用确定性的版本。

**每一版的来源信息**（评审建议做成版本级；复审 3.3：分成服务端确认的和客户端声明的）

`spec_versions` 新增一列 `provenance_json`，里面分两组：

| 组 | 字段 | 说明 |
|---|---|---|
| `server`（服务端确认） | `executor`、`receivedAt`、`specVersionId`、`revisionSha`、`contractVersion`、`verification` | 服务端自己写下的事实。`revisionSha` 是这次发布登记的提交：服务端没法核对客户端是不是真的分析了这个提交，但「账本登记在这个提交上」是服务端的事实。`verification.scope` 是 `server_full`（托管）或 `file_level_paths`（本地）；本地分析的另有 `reanalyzed`、`deterministicallyCarried`、`clientDeclaredUnaffected` 三个计数，由服务端算 |
| `client`（客户端声明） | `model`、`clientVersion`、`pipelineVersion`、`promptVersion`、`impactRulesVersion`、`analyzedAt` | 原样记录客户端的说法，服务端不核对，任何地方都不把它当成已验证 |

- 数据库里两组分开存，读的时候也分两组返回，不合并成一个扁平对象。
- 产品页和发布页上，`client` 组的内容一律带「客户端声明」的标注。`model` 也是客户端声明，不写成「服务端确认使用的模型」。
- 托管的版本写 `server.executor = 'server'`，`client` 组为空。已有的历史版本不回填，`provenance_json` 为空就当它是托管分析。

**计费**

不预留、不扣 SAU、不产生服务端的模型调用回执。经本地分析首次建产品时的赠送，与一次性导入同口径（原规格 §16.3）。

**披露**

产品页、发布页、规格页和导出里标明「由租户的本地分析产出，模型是 X（客户端声明），服务端核验范围：文件级影响面」，并列出按客户端声明沿用的功能。工作台的来源用一个新的 `source` 值，和 `generated` 同属自动条目；版本层两张表的 `source` 列要先加宽（原规格 §20 已列）。

**可更新性（目的 3）**

- 分析不在服务端，上传只有一个事务，所以本地分析的产品不再受「在途分析不能部署」的约束。托管产品不变。
- **契约版本兼容**：一次全量分析可能跑几十分钟，期间服务端可能更新。服务端同时接受当前版本和上一个版本的提案；再旧的返回 `contract_version_mismatch` 和最低支持版本，客户端提示升级。
- **升级期间的兼容测试**：契约测试里固定一组矩阵——服务端在版本 N 时，N 和 N-1 的提案被接受，N-2 被拒绝并带回最低支持版本。每次提升契约版本都要跑。

**需要的数据迁移**（第 1 期，一次迁移）

- `analysis_runs`：`client_idempotency_key VARCHAR(36) NULL`、`client_proposal_hash CHAR(64) NULL`；`(repository_id, client_idempotency_key)` 和 `(repository_id, client_proposal_hash)` 两个唯一索引。
- `spec_versions.provenance_json JSON NULL`。
- `products.analysis_executor`，默认 `server`。
- `repositories.host VARCHAR(191) NULL`。只加列，不改现有的唯一键。
- 新表 `client_proposal_rejections`（拒绝审计）。
- 版本层 `source` 列加宽（原规格 §20）。

## 8. 分期与验收

每期做完都要跑 `npm run typecheck`、`npm test`、`npm run build`。

### 第 1 期：客户端全量分析与统一合并（受控试点）

**范围只有全量。** 复审的建议是先让客户端全量分析在真实仓库里跑通，验证账本对等、隐私边界、事务安全和托管零回归，全量成功后再进入增量。采纳：增量整体放在第 2 期。

**受控试点，不面向所有租户开放。** `analysis_executor` 由运营逐个产品改成 `client`。改之前确认这个租户知道三件事：分析在自己的机器上跑、用自己的模型 Key、服务端核验到哪一层。第 1 期不做设置界面，§11 第 5 项由此了结。

内容：

- 契约 2.0.0、隐私扫描（客户端与服务端共用，含能力边界测试集）、金丝雀（§4.2）。
- 新端点、适配层、合并入口的可选入参、发布事务与行锁（§4.4、§4.6）。
- 隔离：`analysis_executor` 列、统一入口的模式判断、恢复排除、`client_upload` 的终态规则、拒绝审计（§6）。**这些是新端点上线的前置条件。**
- 版本级来源信息，两组分开（§6）。
- 搬行为面枚举和流程图（§5.4）。
- 仓库身份五个字段、`host` 列、首次绑定与校验（§6）；`--full` 与空操作的判定（§5.3）。
- `config` 命令和凭证文件、`GET /api/client-analysis/context`（§5.2）。
- 旧导入端点在 schema 解析之前拒绝带摘录的快照，发布新版雷达 skill；AIRecord 的草稿回填成正式版本。

验收：

1. **分层对等**（同一冻结样本的同一提交；模型名与版本、温度、提示词版本、分区预算、枚举配置全部冻结并记录）：

| 维度 | 怎么比 | 通过标准 |
|---|---|---|
| 提取质量（模型生成的内容） | 功能、场景的重合度 | 不低于服务端自己跑两次的重合度 |
| 结构一致性 | 功能数、每功能场景数的分布、场景类别的分布 | 差异在服务端两次之间的差异范围内 |
| 证据质量 | 证据路径存在、行号在文件范围里的比例 | 不低于服务端 |
| 行为面覆盖 | 行为面枚举产出的场景数、覆盖到的文件 | 差异在服务端两次之间的差异范围内 |
| 产品表现 | 流程图校验通过率、理解层候选通过校验的比例 | 不低于服务端 |
| **确定性合并** | 把同一份提案分别经提案入口和托管入口写到同一基线上 | **逐项相同**：规格版本、场景、证据、变化清单、发布、文件索引、工作台投影、身份 |
| **托管零回归** | 不传新入参 | 合并入口发给数据库的语句和参数逐字节相同 |

   重合度的定义：场景的匹配键，严格版是（功能的名称键，证据锚点集合），宽松版是功能的名称键相同且至少有一个证据锚点（路径、起始行）相同。分母是服务端结果的场景数，报告「客户端覆盖了服务端的多少」，同时报告对称的 Jaccard。之前实测的复现带 40–52% 是用同一冻结样本量的宽松重合度，这次用同样的口径重新量服务端两次之间的带。

   确定性合并不拿模型的重合度当借口：模型生成的内容允许有差异，合并不允许。

2. **隐私**：
   - 能力边界测试集（§4.2）里「必须拦」的全部拦住，「必须放行」的全部放行。「已知拦不住」的几类在测试里固定为放行并注明原因；规则改了要显式改测试。
   - 金丝雀断言通过：标记串不出现在服务端收到的请求体、任何一张接收数据的表、流程图、理解层、错误回执和应用日志里。
   - 对等试验的每一份提案都记录扫描命中数，逐条归成「真泄漏」或「误拦」，写进试验结果。命中数明显高于 §4.2 的实测（每千条场景 3 条以上）时，先回头调规则再继续。
   - 被剔除的条数在回执和产品页上能看到。
   - 旧客户端带摘录的快照被拒绝（`artifact_contains_source`），用例要证明拒绝发生在 schema 解析之前；`evidenceSnippets` 为空数组的快照照旧可导入。
3. **服务端模型调用审计与源码拉取审计**（独立验收项）：不只看回执为零。集成测试里监视每一个模型调用入口——服务端运行时只有 `lib/ai.ts:540` 一处，连同它上面的各个调用函数一起监视——断言提案发布的过程中调用次数为 0，包括事务提交之后的步骤。同样监视源码拉取的出口（GitHub、GitLab 的文件树和内容接口），断言本地分析的产品在全流程里调用次数为 0。
4. **隔离**：产品是 `client` 时，§6 列的每一个入口都不能启动托管分析；`client_upload` 的 run 不会被恢复和补跑认领；上传途中重启服务，客户端重传后成功。
5. **并发**（复审 P1-2）：用真实 MySQL 的两个连接。两个客户端基于同一个版本发布，一个成功，另一个得到 `base_changed`，回执里的 `current` 是前一个写入的版本，账本里只多一个版本。同一份提案内容换一个幂等键重传，按重放处理，不产生第二个版本。
6. **仓库身份**：首次发布返回 `repositoryId` 并建立绑定；之后带错的产品、带错的字段、未绑定的 id 各自被拒绝；同一个 `provider/owner/name` 换一个主机名，得到 `repository_identity_conflict`，不会并成一个仓库；在另一台机器上克隆后发布，账本接得上。
7. **状态判定**：§5.3 的前三个测试通过；新提交不带标志时，提示增量尚未提供，不发请求。
8. **页面**：产品页的各个面（行为清单、理解层、流程图、证据链接）都能打开，带来源披露；客户端声明的字段带「客户端声明」的标注。
9. **托管零回归**：托管分析的现有测试一个不改、全部通过；`insertSpecVersion` 按下标断言的测试不改。

### 第 2 期：客户端增量分析与基线冲突

前提：第 1 期在真实仓库上验收通过。

内容：基线端点；客户端的增量流程（§5.5）；服务端的三类功能核验和锚点有效性（§4.5）；`base_changed` 的两种结果和三层处理（§4.6）；零行为变更的版本语义；启用增量后的状态判定。

验收：

1. 可用率试验的口径在真实仓库上复测：增量窗口的占比不低于原规格 §22.1 的门槛（70% / 50%）。
2. 零行为变更的窗口不调模型，并且产生新版本、账本当前提交前进；人工编辑和墓碑不变。
3. 人工条目不被覆盖、墓碑不复活、身份连续：用冻结的真实窗口重放，结果与托管分析同一窗口的结果逐项相同。
4. **状态判定**的第四个测试：新提交不带标志 → 增量。另外在客户端分析期间做一次人工编辑：结果里人工内容优先，不触发 `base_changed`（人工编辑不产生新版本）。
5. **核验**，按情形各验一遍：
   - 少分析了一个受影响功能，且没有沿用声明：拒绝，`coverage_incomplete`，原因 `missing`。
   - 有沿用声明，但声明的锚点落进了所报的改动区间：拒绝，原因 `anchor_touched`。
   - 有沿用声明，锚点在一个**被删除**的文件上：拒绝，原因 `anchor_touched`。那个文件没有进含行为变更的集合时也一样。
   - 有沿用声明，改动只有纯插入（`oldCount` 为 0），锚点不相交：接受。
   - 锚点没有 `endLine`：按单行判，只看 `startLine` 那一行。
   - 文件改名：旧路径上有锚点的功能不进受影响集合，记为 `deterministically_carried`；新路径上的证据按新路径核验。
   - 有沿用声明，且与所报区间自洽：接受，回执和版本来源里记为 `client_declared_unaffected`，产品页列出这个功能。任何地方都不把它写成服务端已验证。
6. **基线冲突**（第三版更正）：在客户端分析期间，让**第二个发布者**产生一个新版本（V10 → V11），比如同事在另一台机器上发布了一个增量。第二个发布者改动的功能与本次的范围无关时，得到 `reusable`，客户端只做确定性重算后上传成功；有关时得到 `reanalyze`，客户端只重跑受影响的工作单；当前提交也前进的情况回到状态判定。三种情形下合并后的结果都与「直接在 V11 上分析」的结果逐项相同。不拿人工编辑做这个测试：它不产生新版本，不会让基线过期。

不回填的话，试点时有一个必须处理的问题：合并入口只更新 `generated` 的行，租户第一次 `publish --full` 之后，工作台里导入的行既不会被更新，也不会下线——同名功能留着导入时的旧文字，这次没有分析到的功能也不消失。所以让首次发布接住草稿（13.3 第 14 条）。这样不需要编一个「登记在 `014d4785…` 上」的版本，而那个提交其实不是当时分析的内容。

**回填的做法**（`scripts/backfill-import-draft.ts`，逻辑在 `lib/import-draft-backfill.ts`）：

- 不读源码、不调模型、不访问网络。走托管分析同一个合并入口，所以写出来的东西和一次托管的首分析同形：一条 run、一个版本、一条发布。
- **演练是在事务里真做一遍，再回滚。** 合并入口里有确定性的去重和「人工条目优先」的规则，不真做一遍就说不准哪些草稿行进不了版本。演练报告给的是实际结果。
- **写入必须给出提交时间**（`--committed-at`）。服务端不知道那个提交是什么时候提交的，发布上显示的时间不拿导入时间冒充。
- 草稿行的来源在同一个事务里改成 `generated`，行号不变。合并入口只更新 `generated` 的行；不改来源，之后的发布既更新不了这些行，也不会下线已经消失的功能。人工改过的行不碰。
- 合并入口会去掉「文字、证据路径都完全一样」的重复场景，去掉的行也会从工作台上消失。所以演练点出有几条，**写入要有人明确接受**（`--accept-dedupe`）。
- 条件是原规格 §16.3 列的那几条，外加「工作台里已经有分析的痕迹」。不满足就拒绝，整个事务回滚。
