## 调查项（已结项 2026-11-07）

### I1 · 规格瘦身旁根因调查 —— ✅ 已完成（0.5d → 实际 0.5d）

**现象**：公开 demo 的功能数在一天内实测 1 → 2 → 14（走查时点 2，同日晚 14，发布变化 30 → 35）——绝对数量是移动目标，真正的问题是**形态随 push 剧烈波动**：功能数与内容由「最近几次 push 碰了什么」决定，而非产品真实面貌。代码与数据证据如下。

**结论：根因确认，是流水线缺陷，不是仓库小。三层机制叠加，且每一层都有代码与数据证据：**

1. **AI 的可见范围被 slice 预算锁死在 diff 邻域**。`analysisSliceBudgets`（`lib/remote-analysis.ts:29-38`）把每次分析的上下文限制在 ≤80 文件 / 160KB 源码；`assertEvidence`（`lib/analysis.ts:31-42`）强制所有证据路径必须来自本次 slice + diff 文件，AI 看不到的代码无法为其输出功能；prompt 也只要求「覆盖**输入代码里**的全部主要用户功能」（`lib/ai.ts:133`）。小步推送 → slice 小 → 当次输出只有 1–3 个功能。**所谓「全量」模式本质仍是单次 diff 邻域分析。**
2. **每次分析把未重新提取的功能全部下线，且没有任何恢复路径**。`upsertGeneratedSpec`（`lib/analysis.ts:79-95`）把不在本次 AI 输出中的 generated 叶子功能 `active=0`；全库搜索确认唯一的重新激活路径是 `upsertFeature` 的 ON DUPLICATE KEY（`lib/analysis.ts:58、73`），只对 AI 输出中的功能生效。而工作台 UI（功能树、概览计数、spec.json）读的正是 features 表 `active=1`（`lib/product-details.ts:91`）。结果：**工作台功能集 = 最近被 push 触碰过的功能的滑窗**。一天内功能数 1 → 2 → 14 的实测轨迹就是该机制的现场演示——push 集中在少数模块时滑窗收缩到 1–2，push 触及面宽时反弹到 14。
3. **版本层的 carry-forward 存在设计缺口**。全量模式下 `insertSpecVersion` 的 `carried=[]`（`lib/spec-versions.ts:165-167`），版本内容 = AI 当次输出——生产库实测最近 9 个版本的功能数在 7–10 之间波动、从不累积。增量模式（M9）虽设计了 carried 合并，但**只写 spec_versions 层，不修 features 表**——即使部署 M9，工作台滑窗问题依旧。
4. **次要放大器：命名漂移 churn**。DB 中累计 64 个流失功能，其中大量近义重复名（如「AirPlay 服务发现与注册」/「AirPlay 服务注册与发现」/「AirPlay 接收服务启动与 mDNS 注册」为同一功能被改名重建），旧名下线、新名新建，加剧流失堆积。`lib/ai.ts:101-109` 的命名连续性约束（B 阶段修复）已缓解但未根除。

**附带发现**：生产库尚未应用 migration 019（`analyze_mode` 列不存在），线上目前全部走全量模式。
**（2026-11-07 晚更正）**：此条有误——本地 `.env` 指向的是 localhost 开发库；生产库 `analyze_mode` 列存在，且 codelphi 产品已设为 `incremental`，M9 增量模式已在生产运行。

### I1 生产级确认（2026-11-07 晚，只读查询生产库 + 线上实测）

对生产库（codelphi 产品，analyze_mode=incremental）的只读验证**完全证实**滑窗机制，且暴露出比预判更严重的两层分叉：

1. **版本层健康**：最近 19 个 spec_versions 功能数稳定为 14（v32 时从 10 → 14 后不再变）——M9 的 carry-forward 合并在 `spec_versions` 层正确工作。
2. **工作台层坍缩**：`features` 表 `active=1` 只有 **1 个功能**（「发布通知渠道」，最新 push f2e138e 触及的模块）；等价测试显示最新版本 v55 的 14 个功能中有 **13 个仅存在于版本层、工作台不可见**。累计流失 58 个 generated 功能。
3. **实时复现**：走查当日工作台功能数实测 14（≈13:00），13:08 的 run 75（窄推送，触及通知渠道）落库后即坍缩为 1——线上 demo 页角标随之从「产品规格 14」变为「产品规格 1」。一天内 1 → 2 → 14 → 1 的完整轨迹全部为实测记录。
4. **运行记录佐证**：当天 12 次分析运行中 4 次失败、多次 manual 触发；窄推送（run 75）触发坍缩，与「受影响占比 ≤60% 放行增量」的判定一致（`lib/incremental.ts:22`）。

**严重性重估：P0 级数据缺陷，且影响所有产品**（生产库共 8 个产品同用此机制），不止 demo：
- 每次窄推送都会把工作台规格清到只剩本次触及的功能——规格视图、功能树、概览计数、spec.json、Explainer 导出全部失真；
- 用户视角是「功能无故消失」，直接打击「可追溯」的产品承诺；
- 版本层（14）与工作台层（1）持续分叉，回归清单等以 features 表为源的功能同样失真。

**对另一工作区（M9：影子对比、增量决策、carry-forward 合并语义）的协调警示**：
- M9 的合并语义在**版本层是对的**（14 稳定为证），问题出在 `upsertGeneratedSpec` 接收的是 AI 原始输出 `result` 而非合并结果（`lib/analysis.ts:132`）——**carry-forward 语义必须延伸到 features/scenarios 工作台层**，仅改 `mergeSpecSources`/`insertSpecVersion` 无法修复；
- **影子对比会掩盖此缺陷**：`compareIncrementalShadow` 以合并后的版本层为对比对象，工作台坍缩不在其观测范围内——影子对比 ≥98% 一致率与工作台只剩 1 个功能可以同时成立（当时生产即为该状态）；
- 修复落地后需要**一次性对账**：以最新 spec_versions 的 spec_features 回填 features/scenarios 的 active 状态（或触发一次宽触及的重建）。

### I1 修复验证（2026-11-07 晚）—— ✅ 已修复并验证

M9 工作区已落地修复并完成对账，生产只读验证结果：

- 线上 demo 页角标恢复「产品规格 14」（发布变化 39）；
- 最新版本 v58（sha 20930c3）：**版本层 14 = 工作台 14，双向差集均为空**——两层重新等价；
- 协调说明见 `docs/m9-workbench-carry-forward-handoff.md`（含影子对比盲区警示与回归测试要求）。

**路线判定：修流水线。** 「预置内容」路线被证伪——预置的 generated 功能会在下一次分析中被 `upsertGeneratedSpec` 清洗掉，只有 `source='manual'` 功能可幸存；而要求用户手工录入演示数据违背产品意图。A1 据此重写如下。

## M1 · 演示说服力（本周）

### A1 · 修分析流水线，让规格收敛到产品全貌 —— ✅ 已完成（2026-11-07 晚，M9 工作区落地）

I1 生产确认后由 P0 升级，当日由 M9 工作区修复并完成对账；验证结论见上文「I1 修复验证」。剩余跟进项：把「两层集合等价」断言固化为常驻回归测试（交接说明 `docs/m9-workbench-carry-forward-handoff.md` 第 3 条），防止后续改动复发。

**问题**：I1 已确认根因在流水线（滑窗机制 + 全量模式无 carry-forward），且「预置内容」路线被证伪——预置的 generated 功能会被下一次分析的 `upsertGeneratedSpec` 清洗。

**方案（三个修复，按依赖排序）**：

1. **工作台层对齐合并结果**（核心修复，~1d）：`upsertGeneratedSpec` 的下线基准从「AI 当次输出」改为「`insertSpecVersion` 合并后的完整规格」（merged features）。实现上把合并结果传入 `saveResult` → `upsertGeneratedSpec`，carried 功能显式保持 `active=1`。此修复让增量模式（M9）落地后工作台不再滑窗。
2. **全量模式引入版本层 carry-forward**（~1d）：全量模式下 AI 输出受 slice 预算限制（≤80 文件），无法枚举全貌。给全量模式也计算 affected 集（基于 spec-file-index 反查 diff 文件），未受影响的功能从上一版 spec_versions 沿用——与增量模式共用同一条 carried 合并路径（`lib/spec-versions.ts:163-168`），差异仅在放行门槛。
3. **部署 migration 019 并启用增量模式**（~0.5d + 部署）：生产库尚无 `analyze_mode` 列，线上全是全量模式；前两项修复完成后此步才有意义。

**配套测试**：新增回归测试——模拟「连续多次小步 push，每次只触及同一模块」后，断言工作台功能数不低于基线（防滑窗收缩）；模拟「push 触及面由窄变宽」后，断言不产生重复功能行（防命名 churn）。

**验收**：
- 连续 ≥5 次真实 push 后，工作台功能数相对基线波动 ≤20%，且无功能数单调下降；
- 概览页「功能 / 场景」计数、功能树、spec.json 三处一致；
- demo 产品功能数稳定覆盖 CoDelphi 的主要功能面（参照当前 14 个功能的清单，含统一登录、工作区、规格编辑等）。

### A2 · Demo 数据策略决策 —— ✅ 已决策（2026-11-07，用户裁决：保持 live）

**决策：维持跟随演进（现状）**——demo 产品继续随真实仓库 push 实时更新，不加快照固化、不做版本锚定。理由：演示数据永远新鲜，本身是「每次 push 自动总结行为变化」承诺的活证据；滑窗坍缩缺陷（A1）已修复，live 数据的形态风险已消除。

决策项存档（供未来回看）：

| 选项 | 做法 | 代价 |
|---|---|---|
| **维持跟随演进（已选）** | 不改 | 演示内容随仓库演进，对外截图会过期 |
| 快照固化 | demo 产品停收 webhook，A1 完成后冻结 | 每次想更新演示要手动触发 |
| 半固定 | 保留演进，但锁定一版「基线规格」供文档/截图引用 | 需要产品页支持版本锚定访问 |

**问题**：历史遗留——GitHub App webhook 的 URL 曾误写为 `codelph.com`（少个 i），存在投递丢失记录；走查当天的 v49 更新说明投递链路当前可用，但未做过系统性核对。
