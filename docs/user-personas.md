# 用户画像：四类角色的理想使用方式

> 2026-11-06 基于竞品调研与代码现状整理。产品定位：把 GitHub 仓库变成一份可追溯的产品规格——功能清单、用户场景、每次 push 的行为变化，每条结论附源码证据（`README.md:9`、`lib/analysis.ts:24-35`）。
>
> 标注约定：**【已有】**= 当前代码已支撑该用法（附证据文件）；**【缺口】**= 理想状态需要但尚未实现。

## 背景：我们在竞争格局中的位置

| 赛道 | 代表产品 | 用户群体 | 与 CoDelphi 关系 |
|---|---|---|---|
| A. 版本通知 | NewReleases.io、GitWatchman | 个人开发者、平台团队；盯**别人维护的仓库** | 参照系（分发渠道），非竞品 |
| B. AI Release Notes | GitHub 原生、Marketplace Actions | OSS 维护者、产品/DevRel | 单次写作工具，无知识资产 |
| C. AI 仓库理解 | DeepWiki、Greptile、CodeRabbit | 开发者（理解代码实现）；付费验证在工程组织 | 视角是"实现"，与我们的"行为"受众几乎不重叠 |
| D. 规格驱动开发 | GitHub Spec Kit | 使用 AI agent 的开发者（绿地项目） | spec→code 正向；反向提取（CoDelphi 方向）无主流工具 |

核心判断：不卷赛道 C；把「可信的行为规格时间线」做成品类。CoDelphi 当前形态为单公司内部工具（Chandler OAuth + 邮箱白名单，`app/auth/callback/route.ts:20-44`）。

## 产品经理

**核心痛点**：不知道研发到底做了什么；问研发要被打断；写需求时不知道现状边界。

**理想旅程**：

1. **接手新产品**：打开产品页，看功能树（两级）+ 场景清单（正常/边界/异常三分类），半天建立产品全貌，全程不读代码。
   【已有：`lib/feature-tree.ts`；场景 HP-n/EC-n/ER-n 分类 `lib/ai.ts:13-20`】
2. **每天上班**：Slack/邮件收到昨晚 push 的行为变化摘要，点进去看前后对比。不用开会问，也不用自己翻 commit。
   【缺口：通知分发】
3. **写需求前**：查该功能现有场景（"超时后用户看到什么"），在新需求里引用场景 ID 作为基线。
   【已有：场景三列结构；缺口：场景 ID 的稳定链接/引用】
4. **发现 AI 说错了**：直接在页面上改正，人工内容永不被自动分析覆盖。
   【已有：manual 保护 `lib/analysis.ts:50-79`、tombstone `lib/spec-versions.ts:90-101`】
5. **写周报/汇报**：引用某版本的行为变化 diff 作为素材，每项带证据链接。
   【已有：`components/release-card.tsx` 规格行为变化优先展示】

**理想状态的标志**：PM 对"上个版本改了什么"的认知速度 = 研发 merge 的速度，且从不为这个去问研发。

## 开发者

**核心痛点**：接手陌生代码库；改动前不知道影响面；文档永远过时。

**理想旅程**：

1. **接手项目（第一次）**：读功能树 + 场景 + 行为变迁史建立行为全貌；每条结论点开证据直达源码。这是目前唯一能真实跑通的开发者场景。
   【已有：证据可点击 `components/evidence-links.tsx:7-9`；spec 版本链 `lib/spec-versions.ts:160-172`】
2. **写代码时**：在 Cursor/Claude Code 里问 agent，agent 经 MCP 引用 CoDelphi 的规格事实与证据路径。
   【缺口 E：MCP server】
3. **提 PR 时**：机器人评论"此 PR 触碰的文件涉及功能 X（场景 EC-3、HP-2），预期行为变化：……"。每个 PR 都和 CoDelphi 打一次交道。
   【缺口 B：反向影响索引 + PR 预演；现状 webhook 只处理 push，`lib/github-webhook.ts` 非 push 事件 202 忽略】
4. **合并后**：AI 生成的行为变化就是"这次改动对外说明"，只需校对不用手写。
   【缺口：双向闭环导出】
5. **写测试时**：按功能导出 EC-n 场景 → 测试骨架，看哪些场景还没有测试覆盖。
   【缺口 C：测试骨架导出】
6. **日常查"改这个功能要动哪里"**：功能页一屏列出该功能证据文件聚合。
   【缺口 A：功能→实现聚合视图】

**理想状态的标志**：CoDelphi 出现在 PR 流里（高频），而不是只在交接文档里（低频）。

## QA

**核心痛点**：回归范围拍脑袋；测试用例和代码现实脱节；新版本来了不知道测什么。

**理想旅程**：

1. **发版时（杀手场景）**：看发布页行为变化 diff——变了哪些功能/场景，这个 diff 就是回归范围；"未发现规格行为变化" = 本版本可瘦身回归。
   【已有：`lib/product-details.ts:20-43` 联表取 spec_changes；前后对比 `components/behavior-change-item.tsx:34`】
2. **建测试计划**：按功能树导出场景清单作用例骨架，HP-n/EC-n/ER-n 本来就是用例 ID 方案。
   【已有：场景数据；缺口 C：导出格式】
3. **日常**：行为变化流 = 待测队列，每条变化自动成为待验证项。
   【已有数据；缺口：通知 + 待办视图】
4. **回归通过后**：把确认过的场景改标 manual，成为"QA 验证过的可信基线"，AI 更新不覆盖。
   【已有：manual 语义 `lib/spec-editor-service.ts:94-173`；缺产品化入口】

**理想状态的标志**："测什么"由 spec diff 决定，而不是由"上次事故吓到了谁"决定。

## CTO / 技术负责人

**核心痛点**：团队互相打断；新人上手慢；对上说不清进展；知识都在个人脑子里。

**理想旅程**：

1. **基建决策**：规定所有产品接入 CoDelphi（注册即自动分析），作为团队知识基建。
   【已有：GitHub App manifest 全自动接入，`app/integrations/github/manifest|install|callback`】
2. **看团队全貌**：首页产品卡片看每个产品的分析状态、功能数、发布节奏。
   【已有：`app/page.tsx`】
3. **跨部门/向上沟通**：把产品页链接发给老板和其他部门；对外项目用 demo 只读链接。
   【已有：demo 模式 `lib/env.ts:24-31`】
4. **进展汇报**：按版本的确定性 diff 说明团队产出，每项有源码证据背书。
   【已有】
5. **事故复盘**：查"这个行为最后一次变化是哪个版本、证据是什么"，定位是设计如此还是回归。
   【已有：spec 版本链；~~缺口：按功能/场景的时间线视图~~ 已补齐（功能行为变迁史，2026-11-11 baa5bab：功能页折叠区按发布分组时间倒序）】
6. **知识风险管理**：成员离职后，其产品认知至少留有一份 AI 提取 + 人工修订的基线。
   【已有：manual 语义】

**理想状态的标志**：规格知识成为公司资产，不复存在于个人记忆和过时 wiki 里。

## 对照矩阵

| 角色 | 高频场景 | 核心时刻 | 现有覆盖率 | 最大缺口 |
|---|---|---|---|---|
| PM | 看变化、查边界 | 发版后认知同步 | ~80% 已有 | 通知分发 |
| QA | 定回归范围 | 发版 → 测试计划 | ~80% 已有 | 通知 + 用例导出 |
| CTO | 汇报、跨部门 | 接入与复盘 | ~90% 已有 | 按功能的时间线视图（锦上添花） |
| 开发者 | PR 流、IDE | 接手（唯一已有场景） | ~20% 已有 | PR 预演 + MCP + 功能聚合 |

## 结论

1. **PM / QA / CTO 的理想用法八成已落地**——瓶颈不在功能而在触达。通知分发（Slack/email）是全局第一优先级，一份投入同时解锁三个角色。
2. **开发者是唯一需要"新引擎"的角色**（缺口 B/C/E），但共享同一份数据资产，可作第二阶段；做完后 dogfooding 收益最大。
3. **QA 的"发版 → 回归范围"是性价比最高的杀手场景**：数据、视图、语义全部现成，只差把行为变化流包装成 QA 的工作界面。对外传播时最适合当 Demo——"每次发版，AI 告诉你该测什么，每条有源码证据。"

## 缺口编号速查

- **A**：功能→实现聚合导航（跨场景聚合 evidence 文件）
- **B**：反向影响索引 + PR 预演（`pull_request` 事件、file→features 反向索引）⭐ 唯一能改变开发者使用频率的功能
- **C**：场景→测试骨架导出（Gherkin/测试名）
- **D**：规格漂移提醒（manual 条目可能过时的主动信号）
- **E**：MCP server（结构化 spec 喂给开发者的 agent 工具）
- **通知分发**：分析完成后推 Slack/email/webhook（PM/QA/CTO 三条旅程的共同入口）
