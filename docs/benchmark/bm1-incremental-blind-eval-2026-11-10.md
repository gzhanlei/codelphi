## 3. 缺陷模式（Failure Gallery）

**F1 · stable key 身份劫持（P0，新发现）**
同一 stable key 跨版本被整体置换为无关内容，旧真实行为从该键下消失：
- run #1：`databricks sql lab`（Databricks SEA 查询执行/取消）→ 内容整体变为「SQL Lab 无 schema 表 RLS」；`图表构建与可视化`（无代码图表构建）→ 变为「XY 图表配置映射与时序类型处理」（a131fcb623 的 mcp xy.py 行为）
- run #2：`图表构建与可视化` 再次被同族内容置换（劫持目标随机、模式复现）；新键 `sql lab 查询取消` 仿冒 Databricks 取消的命名模式但内容为 RLS 域
- 机制推断：增量 prompt 允许输出清单外新发现，模型把窗口行为错误匹配到既有功能名/stable key；合并层按 stable key 覆盖，无身份一致性校验。Databricks 取消内容因 v48 存在三重重复键而侥幸在兄弟键存活——无重复键时即为净丢失。

**F2 · 跨域放置（可复现）**
新行为写进语义不相关的功能：restore_impact 端点细节两轮均落在 `REST API`（而非常见的 仪表盘/版本历史）；缩略图访客隔离 run #2 落在 `嵌入式访客凭据回退`；run #1 的 SQL Lab RLS 场景落在 `发布流程工具`。

**F3 · 特性内重复爆炸**
run #1 REST API 新增 EC-1..5 五条近似重复（仅标点差异）+ HP-2..5 四条重复；SQL 编辑器 EC-4≈EC-8、EC-5≈ER-1（v48 ER-1 逐字保留的同时又新增同内容 EC-5）——重提取通道不与已保留场景做行为等价去重（`scenarioBehaviorEqual` 只吸收同趟重复，不跨 carried 集去重）。

**F4 · 场景位移/置换（受影响功能内容丢失）**
受影响功能重提取时既有场景被窗口内容顶掉：数据库连接配置 EC-2（EncryptedField 掩码）被 Athena 校验置换、HP-3/HP-6（OAuth2/嵌入式凭据提交）被 Athena 表单置换；安全角色与认证 promiscuous 系列轮转引用位且改写；发布流程工具 HP-6（catalan labeler）被 Polish 置换；语义视图批量删除两轮分别删 8 条/改 3 条（GT 判行为未变——机械命中下的锚定违约，单功能 -61% 未触发总场景 >30% 的坍缩护栏）。

**F5 · 噪音功能键**
run #2 出现 `CI 与许可证检查`（CI 脚本行为）、`KebabMenuButton`（组件名当功能名）——与四跑「前端构建类提升为功能级」同族的噪音模式。

**F6 · 新键命名不稳定**
同一逻辑行为两轮产出不同键名组合（软删除归档 run #1 6+ 键 / run #2 5 键；Athena 表单 run #1 2 键 / run #2 1 键换名）——stable key 只在键内稳定，跨 run 键集不稳定，直接破坏「按功能订阅变更」的产品语义。

## 4. 正向确认（机制有效面）

1. **增量模式判定与机械面按预测运行**——「有上一版 ∧ diff ≤200 ∧ 受影响非空 ∧ ≤60%」四条件真实闸门化，W0-6 虚设闸门被本窗口实化。
2. **静默 unaffected = 0**：预标最担心的机械盲区（缓存层/嵌入式仪表盘）经②新发现/③未归属文件核对通道全部进入规格——「宁可多写一条」的判定偏向在跨通道下仍成立。
3. **affected 六功能（A1–A6）两轮同集变更**，SQL 编辑器的 RLS 场景族内容质量高（含预标未覆盖的 RLS 缓存键行为 EC-12）。
4. **确定性层零漂移**：枚举计数、账本维度、覆盖率回执两轮逐位一致；4 条枚举截断如实 partial。
5. **W0-10 三类输出契约**工作：21/20 个新键全部源自②通道，③未归属文件（mcp_service/*、sql/* 等）有显式核对产物。

## 5. 判定

- **首轮基线（验收线按 benchmark 规格 §4.3 在本数据后冻结）**：AFR-行为 100% / FUR 0% 达标；AFR-原位 75% 未达提案参照线 90%（根因 = 机械盲区 + ②通道替代原位更新，属定位问题非遗漏）；UP-内容完整 86–90% 未达 95%（F1/F4 根因）；NFR 语义 100%。
- **合格项**：增量模式与红线语义成立，真增量可用于生产。
- **不合格项**：F1 身份劫持破坏 append-only 信任（读者会读到「Databricks 查询取消变成了 SQL Lab RLS」的假变更）；F3/F5/F6 使规格规模与键集不可控膨胀。**在 F1 修复前，增量模式的输出不应未经人工核实直接采信功能级变更**——人工核实签发的产品定位在此刚好兜底，但机制侧必须收口。

## 8. 与四跑盲评的关系

四跑（full 模式）测的是「读得窄→行为面枚举」的召回递进（46.7→86.7%）；本报告测的是「改得对不对」：增量模式的 affected/unaffected/new 三分类正确性。两者互补，共同构成 benchmark 规格 §5 变更矩阵的第一批实测数据点。
